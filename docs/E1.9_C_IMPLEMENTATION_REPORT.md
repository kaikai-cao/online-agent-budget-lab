## 2. 完整执行链路（C1 + C2）

### 2.1 C1 — Executor → Journal Service IPC
- `JournalClient.for_pipe()` 使用 E1.9-B 正式 `NamedPipeClient.call(method, params)`，不另造协议。
- Executor **不直接读写 Journal SQLite**、**不持有或调用 Journal 私钥**、**不自行提供公钥或可信身份**。
- 请求携带的 `executor_id` 是声明值（claim），由服务端 `IdentityAuthorizer` 按固定 OS 身份映射
  鉴权（E0 §9.1）。生产路径为 `identity_mode="impersonation"` + OS-backed（沿用 E1.9-B，未改）。
- 类型化封装覆盖六 API：`verify_integrity` / `append_intent` / `append_result` /
  `get_entry` / `get_checkpoint` / `get_head`；失败一律转 `JournalClientError(code, message)`，fail-closed。

### 2.2 C2 — 执行顺序
`JournalBackedExecutor.execute_with_journal()` 在共享 `E1CLocalState` 写锁（`BEGIN IMMEDIATE`）内：

1. `verify_integrity()` —— Journal 完整性门禁，失败即 `E1CIntegrityFailure`（不 dispatch）。
2. 本地 `e1c_status` 幂等命中 → 直接返回原 Receipt（不 dispatch）。
3. G2 三态判定 → `DIVERGED` / `ROLLBACK_SUSPECTED` 即 fail-closed。
4. 查权威 RESULT entry → 命中走恢复路径（见 §3），**先于任何 dispatch 决策**。
5. `append_intent`（冻结三字段 envelope：operation_id / binding_digest / executor_id）。
6. `executor.execute_e1(...)` —— 四门禁 + dispatch + v2 Receipt 签名 + 本地落库全部在此既有冻结链路内，
   编排层**不改其内部**、不插入 hook，只传 `pending_execution` 与门禁所需参数。
7. `append_result`（冻结四字段 envelope：operation_id / binding_digest / result / execution_receipt），
   绑定第 6 步返回的**原始 Receipt**；服务端复用 E1.9-B 强制 v2 + 四方绑定 + B-F1 result 双向绑定 + 固定公钥验签。
8. 权威先、本地后（Saga）：RESULT 入 Journal 后才更新本地 `e1c_status` 与全局 `last_applied_seq` / `last_checkpoint_digest`。
9. 返回原始 Receipt 原件（逐字节一致）。

**顺序验证**：测试断言 INTENT.seq < RESULT.seq、RESULT.envelope.execution_receipt == 原始 Receipt、dispatch_count==1。

## 3. 故障恢复（C3）与三态

| 场景 | 实现行为 | 测试 |
|---|---|---|
| RESULT 已写、本地状态未提交（本地落后/新实例） | `get_entry(RESULT)` 命中 → 取回原始 `result` + `execution_receipt` → 重算 `e1-result-envelope-v1` 摘要比对、Receipt v2 验签（固定公钥）+ operation_id/binding_digest/result 绑定 → 写回本地 → 返回原件，**不 dispatch、不重签** | R01 / 真实 G02 |
| 恢复出的 Receipt 被篡改 | envelope 摘要不符或 B-F1 result 绑定不符 → `E1CReceiptInvalid` fail-closed | R02 |
| INTENT 已写、无 RESULT（dispatch 前崩溃 / 四门禁拒绝） | 按 INTENT 后续重放；不声称 G1b（确定性本地工具无外部副作用） | E03（记录 INTENT、无 RESULT、不包装 exactly-once） |
| `LOCAL_STATE_BEHIND`（本地序号落后且同序号检查点一致） | 判为正常落后，不判回滚；补齐期间不 dispatch（本阶段本地状态按已知 operation_id 经 `get_entry` 逐条对齐） | R07 |
| `LOCAL_STATE_DIVERGED`（同序号检查点摘要不符） | `E1CStateDiverged` fail-closed，不 dispatch | R03 / R07 |
| `ROLLBACK_SUSPECTED`（本地游标超前或无同序号证据） | `E1CRollbackSuspected` fail-closed，表述为"疑似"而非"确认回滚" | R04 |
| Journal 完整性验证失败 | `E1CIntegrityFailure`，拒绝继续，错误码保留诊断证据 | R05 |
| Receipt 验签失败（错误公钥/篡改签名） | 服务端拒绝追加 RESULT，`INTENT_/RESULT_` 前缀错误 fail-closed，无 RESULT entry | R06 |

**恢复不重建**：`recover_result_from_entry()` 只返回 Journal 中原始签署的 Receipt 对象；代码路径中不存在
`make_receipt` 重建（E0 §9.2 约束 6）。比较对象严格为同序号历史检查点，不是最新 head（E1.8 §7.4）。

## 6. 未实现能力与明确不保证事项

**未实现 / 未验证**：
- 多 Executor **进程**并发共享同一本地状态库 + 同一 Journal 的组合压力场景（X01 是单进程内两线程）。
- 真实第二 Windows 账户的 Named Pipe / 文件 ACL 拒绝（管理员环境依赖，未冒充通过）。
- `LOCAL_STATE_BEHIND` 全量历史补齐：即时对账通过；跨 seq 全量回放受限于当前六 API 无 `entries_from`，未新增服务 API（避免改冻结服务）。
- A2 执行权授权服务、A3 工具端幂等、fencing token 校验、远程权威/单调锚点、WORM、HSM/TPM、密钥轮换/撤销。
- 具备外部副作用的工具（如外部 API）的 exactly-once；本链路仅针对确定性本地工具。
- Executor 侧原样保留的 `execute_e1` 四门禁未在本阶段重写；本阶段证明的是编排层与其兼容，不是重新证明四门禁。

**明确不保证**：
- G1b（至多一次真实 dispatch）：INTENT-only / 崩溃窗口仍可能二次 dispatch，不包装为 exactly-once。
- 完整 G1a、外部副作用 exactly-once。
- 管理员联合控制 DB + 私钥时的回滚可检测性；无外部单调锚点，不声称不可回滚。
- Journal TCB（服务进程/账户/私钥）失陷后的历史可信。
- 执行真实性：Journal 记录 + Receipt 验签 ≠ 工具真执行；私钥泄露者可伪造自洽回执。
- 工程测试通过 ≠ 形式化安全证明。
