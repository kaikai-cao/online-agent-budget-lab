# E1.9 实施任务包设计

> 依据：冻结的 E1.8 设计文档（提交基线 `42e5ec4`），尤其 §2.2、§5.2、§5.3、§7.1、§7.3–7.5、§11。
> 范围：A1（共享执行存储并发串行化）+ B2（独立权威追加日志与状态抗回滚），仅针对确定性本地工具的执行。
> 本文件为实施任务包设计，尚未包含实现代码；实现后按第 9 节清单逐项验收。

## 1. 目标、非目标、安全假设与保障边界

### 1.1 两个目标严格分离（与 E1.8 一致）

- **A1 — 共享执行状态并发串行化（只到 G1a 存储层形态）**：多个 Executor 实例指向**同一个执行数据库**（现有 `executions` 表，`operation_id` 为主键），借 SQLite `BEGIN IMMEDIATE` 事务串行化查重与记录写入，使相同 `operation_id` 在共享库内只被接受一次。**只保证并发串行化，不保证 G1b（至多一次真实 dispatch）**：dispatch 与 commit 不在同一原子操作，崩溃窗口下仍可能二次 dispatch（E1.7 T03 基线）。
- **B2 — 独立权威日志与状态抗回滚（G2）**：引入**独立于 Executor 本地执行数据库**的追加式可信 Journal，使用全局单一 `seq`、前序摘要 `prev_digest` 与签名检查点，记录执行意图与结果。**其存在意义正是在本地数据库被恢复为旧快照时仍有独立历史作为恢复依据**；因此 Journal 绝不能随本地执行库一起回滚。
- **A1 与 B2 互不替代**：共享执行库串行化不提供抗回滚；Journal 抗回滚不裁决两实例谁获得执行权。二者组合时仍须分别测试。

### 1.2 目标

- **并发串行化**：共享库下相同 `operation_id` 只提交一次执行记录（A1）。
- **抗回滚**：本地状态落后或分歧时，以权威 Journal 的同序号历史检查点判定，按 `LOCAL_STATE_BEHIND` 补齐、`LOCAL_STATE_DIVERGED` / `ROLLBACK_SUSPECTED` 失败关闭（B2，E1.8 §7.4）。
- **恢复一致性**：从 Journal 恢复的回执必须是**原始签发对象**（逐字节一致），不重新 `make_receipt`、不重算签名字段。

### 1.3 非目标

- 不支持具有外部副作用的工具；仅针对本地确定性函数调用（或模拟工具）的并发与崩溃容忍。
- 不实现 A2（执行权授权服务）或 A3（工具端幂等接口）；不声称 G1b（至多一次真实 dispatch）。
- **不把 B2 的权威 Journal 实现成 Executor 本地 SQLite 库中的一张表**，也不把它与执行记录放进同一个可整体回滚/原子提交的事务。

### 1.4 安全假设与保障边界（E1.8 §2.2 的子集）

- 沿用 E0 §8.2：Issuer、D10/D11 Coordinator、可信 Executor 的计量签名与工具执行可信；SQLite 事务原子性与持久性正确。
- **B2 新增信任组件**：存在一个独立可信 Append-only Journal，其追加写不可被攻击者回滚或篡改、提供按 `seq` 签名的历史检查点、其签名密钥安全。若进入实现须按 E0 级流程冻结该信任假设并扩充 TCB（E1.8 §2.2）。
- Journal 与执行库**物理或逻辑上分离**：本地 `executions` 表回滚时 Journal 仍完整；不允许用“同一个 SQLite 事务同时写 Journal 与执行记录”来声称二者原子提交。
- 恢复阶段只从 Journal 恢复原始回执与检查点摘要，不生成新的签名凭据；数据不符即 fail-closed。
- 不保证对外部 API 的 exactly-once；保证仅限本地工具执行幂等性与日志核验。
- **Journal 自身若被回滚或丢失，在本设计内没有更上层独立锚点**（信任根只能移动不能消除）。

## 2. A1/B2 架构与数据流映射

```
Agent / Runtime ──提交经 E1.5 四门禁的 PendingExecution──▶ TrustedToolExecutor
                                                              │
   A1 共享执行状态（本地/共享 SQLite，executions 表，operation_id 主键）
       ├─ 作用：共享库内并发查重、执行记录唯一
       └─ 边界：只串行化，不保证崩溃窗口至多一次 dispatch（非 G1b）
                                                              │
   B2 独立权威 Journal（独立服务或独立存储，待勘察）
       ├─ 全局单一 seq / prev_digest 链 / 签名 Checkpoint
       ├─ 追加 INTENT、RESULT envelope（含原始 result + 原始 Receipt）
       └─ 边界：不随本地执行库回滚；本地表落后时作为补齐依据
```

### 2.1 A1 共享执行状态（非权威 Journal）

- 实现方式：需要共享的 Executor 实例指向**同一个 SQLite 数据库文件**（实际构造参数为文件路径，见 `ExecutionStore(database_path)`）；利用 `BEGIN IMMEDIATE` 与 `operation_id` 主键约束串行化并去重。
- 数据表：复用现有 **`executions`** 表（不是 `operations`）：`operation_id` 已是主键，含 `binding_digest`、`state`、`result_json`、`receipt_json` 等字段。无需新建等价表。
- 合规性：依 E1.8 §5.3，只称"共享存储层并发串行化"，**不称 G1b**。

### 2.2 B2 独立权威 Journal

- **不是本地表**：Journal 必须独立于可被整体回滚的 `executions` 数据库。可先做单机原型，但存储/服务形态（独立 SQLite 文件 + 独立签名检查点，或常驻 Journal 服务）须在 §3 标注为**待勘察**，不得默认塞进 `ExecutionStore` 的事务。
- 逻辑条目：`seq`（全局单一、连续无缺号）、`prev_digest`（链接前序）、`operation_id`、`phase ∈ {INTENT, RESULT}`、`payload_digest`、`executor_id`、`result_ref`/`receipt_ref`、日志条目签名 `entry_signature`。
- Checkpoint：`seq`、`journal_head_digest`、`checkpoint_signature`（权威对该序号处日志前缀的签名承诺，是**历史快照**）。
- 追加接口与响应语义（**待勘察**）：`append(phase, operation_id, envelope) → (seq, prev_digest, entry_signature)`；`head() → (seq, head_digest, checkpoint_signature)`；`checkpoint_at(seq)` 与 `entries_from(seq)`。E1.8 §7.1 要求**权威日志先推进、本地状态后推进**，因此追加接口必须先把 RESULT 与检查点落到 Journal，之后才更新本地 `executions`。
- 恢复验证：Executor 用本地 `last_applied_seq` 取权威**同序号**历史检查点比对（不是与最新 head 比），按 E1.8 §7.4 三态处理；`LOCAL_STATE_BEHIND` 逐条补齐，`LOCAL_STATE_DIVERGED` / `ROLLBACK_SUSPECTED` fail-closed。

### 2.3 数据流与关键字段映射（对照 E1.8）

- **执行状态**：现有 `executions` 表，记录执行意图与结果，`operation_id` 为主键。
- **权威 Journal**：独立实现（形态待勘察），记录 `seq` / `prev_digest` / `phase` / `payload_digest` / `result_ref` / `receipt_ref` / 签名与 Checkpoint。
- **`payload_digest`**：对完整 RESULT envelope 的摘要，域标签与字段以 E1.8 §5.2 为准：`canonical_digest("e1-result-envelope-v1", {operation_id, binding_digest, result, execution_receipt})`。`result_ref`/`receipt_ref` 是该 envelope 内的分段引用，不是各自独立的摘要根。
- **`receipt_ref`**：原始 Execution Receipt 字节（或 Base64）；恢复时验签与字段绑定，不重签。
- **不设 fencing `token` 必需字段**：E1.9 选择 A1、不实现 A2，fencing token 属 A2 才有语义的机制（E1.8 §6）。若日志条目为将来扩展预留字段，可留空并注明"本阶段无语义"，**不得**把它变成必需校验或声称具有防重放作用。
- **权威优先的事务顺序**（E1.8 §7.1，权威在前、本地在后）：
  1. 四门禁验证通过；检查执行状态与历史检查点（G2 判定）
  2. 追加 INTENT 到**权威 Journal**（E1.8 §7.1）；取得 `seq`
  3. 调用 `registry.dispatch()` 得到 `result`
  4. 调用 `make_receipt()` 生成并签名原始 `ExecutionReceipt`
  5. 构建 RESULT envelope、计算 `payload_digest`，追加 RESULT 与**新检查点**到权威 Journal
  6. 更新本地 `executions`（`last_applied_seq` / `last_checkpoint_digest`），返回**原始 Receipt 原件**

## 4. 实施顺序与依赖关系

建议分阶段实施，**先建立独立权威 Journal，再接入本地执行状态与 A1 共享库**；每阶段实现后立即编写或更新测试。

1. **建立独立权威 Journal（先做）**：
   - 确定 Journal 形态（独立存储 or 服务，待勘察），实现全局单一 `seq`、`prev_digest` 链、条目签名 `entry_signature` 与签名 Checkpoint（`seq`、`journal_head_digest`、`checkpoint_signature`）。
   - 提供追加接口 `append()` 与查询接口 `head()` / `checkpoint_at(seq)` / `entries_from(seq)`（具体签名待勘察）。
   - 硬要求：与 `executions` 库分离、不随本地快照回滚；信任边界按 E0 级流程冻结。
   - 提交边界：Journal 组件与其单元验证（链连续、签名可验、检查点可查）。

2. **接入权威优先的执行流程**：
   - 按 E1.8 §7.1 顺序接入：门禁与 G2 检查 → 追加 INTENT（权威）→ `registry.dispatch()` → `make_receipt()` → 构建 RESULT envelope 并追加 RESULT + 新检查点（权威）→ 更新本地 `executions`（`last_applied_seq`/`last_checkpoint_digest`）→ 返回原始 Receipt。
   - **权威日志先推进、本地后推进**；不得把权威 Journal 追加塞进 `ExecutionStore.execute_once()` 的同一 `BEGIN IMMEDIATE` 事务来声称二者原子提交。
   - 提交边界：验证正常流程中 Journal 条目与检查点被写入、回执为原始签发。

3. **实现本地状态与三态恢复**：
   - 本地 `executions` 增加 `last_applied_seq` / `last_checkpoint_digest`；`recover_from_journal()` 用本地序号取权威**同序号历史检查点**比对，按 E1.8 §7.4 三态处理：
     - `LOCAL_STATE_BEHIND`（序号小且同序号摘要一致）→ 从 `last_applied_seq+1` 逐条补齐，逐条校 `prev_digest` 链，补齐期间不 dispatch，**不判回滚**；
     - `LOCAL_STATE_DIVERGED`（同序号摘要不一致）→ fail-closed（`E1ExecutionDenied`）；
     - `ROLLBACK_SUSPECTED`（有迹象但证据不足）→ 按分歧处理并明确标注"疑似"，**不声称已确认回滚**。
   - 补齐只恢复原始结果/回执并重算 envelope 摘要 + 验签，**不重新 `make_receipt`**（E1.8 §5.2 硬规则）。
   - 提交边界：覆盖"先落后后同步""同序号分歧拒绝""疑似回滚不误判"。

4. **A1 并发访问测试**：
   - 两 Executor 共享同一 `database_path` 并发调用 `execute_e1()`；断言共享库内只有一个真正 dispatch（计数=1）、另一走幂等返回。
   - **明确此 dispatch=1 只证明共享存储层并发串行化，不是 G1b 保证**（§1.1、E1.8 §5.3）。

5. **B2 恢复测试（按三场景，不再照搬 T03 的 dispatch=2）**：
   - 场景 A：dispatch 后、RESULT 尚未写入权威 Journal → 本地确定性工具允许按 INTENT 重放，**可能再次 dispatch，不声称 G1b**（此为 E1.7 T03 的无独立 Journal 基线对照）。
   - 场景 B：RESULT 已写入权威 Journal、本地 `executions` 尚未更新 → 从 Journal 恢复原始 result 与 Receipt，**dispatch 不增加**，回执与原件逐字节一致。
   - 场景 C：本地数据库恢复旧快照、权威 Journal 完整 → 按同序号历史检查点判 BEHIND（补齐，已有 RESULT 不重新 dispatch）或 DIVERGED/SUSPECTED（fail-closed）。
   - 三场景均须用数据库记录 + dispatch 计数 + Journal 状态三重确认。

6. **端到端验收**：
   - 执行 E1.5–E1.7 全部回归，确认 A1/B2 改动未破坏既有测试。
   - 新增端到端用例：正常路径写 Journal；注入故障后从 Journal 恢复的回执与历史原件一致。

7. **文档与配置**：
   - 更新 README/注释，说明 A1 共享库模式、B2 独立 Journal 的启用与信任边界，标明仅单机共享文件、不适用分布式数据库。

## 5. 测试场景与安全性质

对应每项变更要有覆盖**安全性质**的测试场景。**E1.7 T03 的 dispatch=2 是"无独立 Journal"的基线结果，不是 B2 的验收目标**；B2 要证明的是在权威 Journal 完整可信的假设下改善相应恢复行为。

- **并发串行化（A1）**：两 Executor 共享同一 `database_path` 并发执行同一操作。预期：仅一次工具调用、回执一致。此 dispatch=1 **只证明共享存储层并发串行化，不是 G1b**。
- **正常流程**：单实例执行。预期：与 E1.5/E1.6 相同的回执生成与计数，且权威 Journal 写入 INTENT/RESULT 与签名检查点。
- **恢复场景 A — RESULT 未入权威 Journal**：dispatch 后、RESULT 追加前崩溃。预期：本地确定性工具按 INTENT 重放，**可能再次 dispatch，不声称 G1b**；对应 E1.7 T03 基线对照。
- **恢复场景 B — RESULT 已入 Journal、本地表未更新**：预期：从 Journal 恢复原始 result 与 Receipt、重算 envelope 摘要+验签，**dispatch 不增加**，回执与原件逐字节一致。
- **恢复场景 C — 本地旧快照、Journal 完整**：预期：按本地序号处历史检查点 vs 权威同序号判定——摘要一致为 `LOCAL_STATE_BEHIND`（补齐，已有 RESULT 不重新 dispatch）；摘要不一致为 `LOCAL_STATE_DIVERGED`（拒绝）；证据不足为 `ROLLBACK_SUSPECTED`（标注疑似、按分歧处理，不称"已确认回滚"）。
- **日志链与检查点完整性**：连续 `seq` 无缺号、`prev_digest` 链可验、条目签名与检查点签名可验；篡改任一环即 `LOCAL_STATE_DIVERGED` / fail-closed。
- **重复提交**：同一 `operation_id` 在共享执行库重试走幂等返回（选做：INTENT 已存在时的处理策略）。
- **三重确认**：所有 dispatch 次数由 registry 计数、本地 `executions` 行、权威 Journal 状态共同确认，不只看线程返回值。

## 6. 故障注入矩阵

表中"权威 Journal"指独立于 `executions` 库的可信追加日志；"本地表"指 `executions`。dispatch 次数均由计数 registry + 本地行数 + Journal 状态三重确认。

| 故障类型 | 注入位置 | 预期行为 | G2 判定 / 可恢复 | 测试场景 |
|---|---|---|---|---|
| 追加 INTENT 后、dispatch 前崩溃 | 权威 Journal 已有 INTENT、无 RESULT | 重启按 INTENT 重放；RESULT 未入日志前可能再次 dispatch，**不声称 G1b** | 可恢复（重放） | 构造仅含 INTENT 的日志前缀，恢复后执行 |
| dispatch 后、RESULT 入 Journal 前崩溃 | 工具已执行、权威 Journal 无 RESULT | 事务未形成 RESULT 条目；本地确定性工具按 INTENT 重放，可能二次 dispatch（E1.7 T03 基线） | 状态未知，不声称 G1b | 依赖权威日志无 RESULT 判定，执行 2 次 |
| RESULT 已入 Journal、本地表未更新 | 权威日志有 RESULT+检查点，`executions` 落后 | 用本地序号取同序号历史检查点：一致→`LOCAL_STATE_BEHIND`，逐条补齐、恢复原始 Receipt、**dispatch 不增加** | 可恢复（补齐） | 恢复测试检查本地表补齐、回执逐字节一致 |
| 本地数据库恢复旧快照、Journal 完整 | 恢复 `executions` 旧文件，Journal 未动 | 同序号摘要不一致→`LOCAL_STATE_DIVERGED` fail-closed；证据不足→`ROLLBACK_SUSPECTED`（疑似，按分歧处理）；一致但序号小→BEHIND 补齐 | 分歧拒绝 / 落后补齐 | 真实复制/恢复 SQLite 文件后执行 |
| 权威 Journal 条目或检查点被篡改 | 改 `prev_digest` / `payload_digest` / 签名 | 验签或链校验失败→`LOCAL_STATE_DIVERGED`，拒绝 dispatch | 否，fail-closed | 篡改日志字段后执行，确认拒绝 |
| 权威 Journal 写入失败 | 追加接口异常 / 存储不可用 | 不推进本地 `executions`、不返回未完成回执；按 E1.8 §8 远程服务不可用一律 fail-closed | 否，fail-closed | 模拟追加异常，确认异常传播且无执行表落库 |
| A1 共享库并发竞争 | 两 Executor 同 `operation_id` 并发 | SQLite 锁串行化，仅一次 dispatch；非 G1b，只证明共享库并发串行化 | 是（幂等返回） | 并发测试，数据库 + 计数 + Journal 三重确认 |
| 权威 Journal 自身回滚或丢失 | 日志被整体替换/清空 | 本设计内无更上层独立锚点→**不能保证检测**，fail-closed 停机并报警（E1.8 §8） | 否，fail-closed | 记录为信任边界，不作为可恢复承诺 |

## 7. 持久化规格与协议遵循

- **权威 Journal 独立于 `executions` 库**：不改变 D10/D11 回执结构；Journal 存储形态待勘察，但必须满足与本地执行库分离、不随本地快照回滚。
- **日志条目签名（必需）**：每条 `JournalEntry` 含 `entry_signature`（权威对条目签名）；`seq` 为全局单一连续无缺号，`prev_digest` 链接前序，验证时逐条校验链连续性与签名。不得将条目签名标为可选（E1.8 §2.2、§5.2）。
- **签名检查点**：Checkpoint 含 `seq`、`journal_head_digest`、`checkpoint_signature`；Executor 必须用本地 `last_applied_seq` 取权威**该序号**的历史检查点验证，不得无条件用最新 head 摘要（否则正常落后被误判为回滚）。
- **摘要承诺对象**：`payload_digest = canonical_digest("e1-result-envelope-v1", {operation_id, binding_digest, result, execution_receipt})`；`result_ref` / `receipt_ref` 是 envelope 内分段引用。恢复时按引用取回原始对象→重组 envelope→**重算摘要比对**→独立验证原始回执签名与字段绑定（operation_id / binding / budget_receipt_digest / auth_digest）。
- **恢复而非重建（硬规则）**：只能返回权威 Journal 中**原始签发的回执对象**（或经摘要校验的副本），禁止用恢复字段重新 `make_receipt`；原始回执不可恢复即 fail-closed。
- **G2 三态恢复规则**：`LOCAL_STATE_BEHIND` 按序补齐（补齐期间不 dispatch）；`LOCAL_STATE_DIVERGED` fail-closed；`ROLLBACK_SUSPECTED` 证据不足只记疑似并按分歧处理，不声称已确认回滚。比较对象恒为"本地序号处历史检查点 vs 权威同序号"。
- **兼容性**：不修改 `ExecutionReceipt`、`BudgetReceipt` 格式，仍用 `make_receipt` 与原有签名机制；fencing/seq 若要入回执属另行冻结的独立扩展。
- **token 字段**：`token INTEGER` 仅作 A2 fencing 的预留占位，本阶段无语义、可空，**不得**作为必需校验或据此声称防重放。
- **Migration**：已有数据不迁移；新增 Journal 与本地状态字段对历史记录无操作，历史测试不变。

## 8. 兼容策略

- **不破坏现有测试**：所有 E1.5–E1.7 测试仍应通过。新实现必须被测试覆盖，无破坏。
- **一次性复核**：实现后运行完整回归（Python 全量、Rust all-targets、`cargo fmt --check`、`git diff --check`）。
- **回滚方案**：如实现问题，恢复至 E1.8 状态；需同时移除权威 Journal 组件与本地状态字段，不能只删一张本地表——因为 Journal 是独立组件。

## 9. 验收标准与开发执行清单

- **开发清单**：依 §4 阶段顺序实施（先权威 Journal，再执行状态与 A1），完成后编写/更新对应测试。
- **测试步骤**：
  1. 迁移后，运行原有 **194/194** 测试全通过（E1.7 后基线；E1.6 为 191）。
  2. 新增并发与恢复测试覆盖：A1 共享库并发串行化、§5 三场景恢复（A/B/C）、G2 三态判定。
  3. 故障注入按 §6 矩阵测试，含真实 SQLite 快照恢复、日志条目/检查点篡改、权威写入失败。
- **验收标准**：
  - A1 共享库并发竞争只 dispatch 1 次——**仅此并发实验成立，不是 G1b 保证**；
  - 恢复场景 B（RESULT 已入 Journal、本地未更新）dispatch 不增加，回执与原件逐字节一致；
  - 恢复场景 C 按三态判定：BEHIND 补齐、`LOCAL_STATE_DIVERGED` / `ROLLBACK_SUSPECTED` 拒绝；
  - 日志条目/检查点篡改触发拒绝，且 Journal 不随本地 `executions` 快照一起回滚；
  - 未影响无故障路径的正确性，全部回归与新测试通过。

## 10. 风险与未决问题

- **分布式一致性**：本阶段只支持单机共享同一 SQLite 文件，不考虑多进程缓存冲突，不适用分布式数据库。
- **权威 Journal 可靠性与信任**：假设独立 Journal 的追加写持久、不可回滚/篡改，签名密钥安全；该信任组件须按 E0 级流程冻结并扩充 TCB。Journal 自身若回滚或丢失，本设计无更上层独立锚点（信任根只能移动不能消除）。
- **G1b 未解决**：至多一次真实 dispatch 仍为开放问题，不在 E1.9 承诺；本地工具崩溃窗口的二次 dispatch 是可接受的基线行为。
- **外部副作用**：未支持，需 A3 才能覆盖，不在本阶段范围。

以上任务包以 E1.8 设计为蓝本：**A1 负责共享存储下的并发串行化，B2 负责独立权威日志与状态抗回滚**，两者组合但不共置于可被整体回滚的本地数据库。分阶段实现并通过测试验证安全边界；完成后即可交由开发者分工实施，并按第 9 节清单逐项验收。
