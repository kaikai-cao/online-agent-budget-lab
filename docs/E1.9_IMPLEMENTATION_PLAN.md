# E1.9 实施任务包设计

> 依据：冻结的 E1.8 设计文档（提交基线 `42e5ec4`）。
> 范围：A1（共享权威存储串行化）+ B2（追加式可信日志），仅针对确定性本地工具的执行。
> 本文件为实施任务包设计，尚未包含实现代码；实现后按第 9 节清单逐项验收。

## 1. 目标、非目标、安全假设与保障边界

- **目标**
  - **并发串行化**：多个 Executor 实例使用**相同 SQLite 数据库**时，共享执行状态，保证相同 `operation_id` 只会提交一次。依赖 SQLite 的 `PRIMARY KEY (operation_id)` 和事务串行化来防止并发重放。
  - **抗回滚**：引入**追加式执行日志（Journal）**，将每次执行意图、结果和执行回执写入一个可靠日志。通过日志序号和摘要检测本地数据库是否落后或分歧，恢复时补齐遗漏或拒绝可疑状态。
  - **恢复一致性**：保证恢复后生成的回执**与原始签发一致**（逐字节相同），不重新签发或重算字段。

- **非目标**
  - 不支持具有外部副作用的工具。仅针对本地确定性函数调用（或模拟工具）进行并发和崩溃容忍。
  - 不实现 A2（执行权授权服务）或 A3（工具端幂等接口）。不声称"至多一次执行"（G1b）。只保证在共享存储层的并发串行化和日志核验下的容错。

- **安全假设与保障边界**
  - 假设 Executor 进程间可共享 SQLite 文件，且 SQLite 实现提供正确的事务原子性和互斥锁。
  - 追加式日志存储为可靠的、不可篡改（至少追加）存储，日志写入原子且被正确同步。
  - 分布式场景下仅支持**同步写入同一数据库文件**，不考虑跨进程缓存冲突。
  - 恢复阶段只从日志恢复回执和检查点摘要，不额外生成新的签名凭据；如果数据不符，则执行失败关闭。
  - 不保证对外部 API 的 exactly-once；保证仅限于本地工具执行幂等性和日志验证。

## 2. A1/B2 架构与数据流映射

- **A1: 共享权威存储串行化**（只实现并发串行化，不保证 G1b）
  - 实现方式：所有 Executor 实例使用相同的 **SQLite 数据库文件**（`ExecutionStore` 的 `database_path` 指向同一个目录），利用数据库的 ACID 保证并发请求串行化、利用主键约束避免重复执行。
  - 数据表：复用现有 `operations` 表（或等价表）以记录执行意图和结果。确保 `operation_id` 字段为主键。
  - 合规性：根据 E1.8 §5.3，只称串行化效果，不承诺崩溃恢复时只执行一次。

- **B2: 追加式执行日志（Journal）**
  - 引入新表（**执行日志表**），记录每次执行的关键信息（意图、结果、回执摘要、序号、前序摘要等）。
  - 结构草案：`(seq INTEGER PRIMARY KEY, operation_id TEXT, phase TEXT, payload_digest TEXT, result_ref BLOB, receipt_ref BLOB, prev_digest TEXT, token INTEGER, signature BLOB)`。其中 `phase` 区分 INTENT/RESULT，`payload_digest` 为完整 `RESULT` envelope 的摘要，`result_ref`/`receipt_ref` 存储原始 `result` 及签名回执。
  - 流程：每次执行调用时，事务内依次写入 INTENT（可选）、执行并生成回执、写入 RESULT（并取得新 `seq`、`digest`）到日志，然后提交。（具体顺序见下）
  - 恢复验证：重启或并发时，Executor 拉取日志头及对应摘要，与本地 `last_applied_seq` 对比。若落后且摘要匹配，则从日志补齐本地记录；若分歧或日志被攻击则 fail-closed。
  - 日志与执行记录需保持一致性：写入日志的操作与写入执行表事务性结合，以免部分失败导致状态不一致。

- **数据流与关键字段映射**（对照 E1.8）
  - **ExecutionStore (`operations` 表)**：原有表，用于记录 INTENT/RESULT。新增或确保包含 `operation_id` 主键。
  - **Journal 表**：新增日志表，实现 B2 设计。记录 sequence、摘要、引用等。
  - **`payload_digest`**：对完整 RESULT envelope 的哈希。Envelope 应包含：`(operation_id, binding_digest, result, execution_receipt)`。
  - **`receipt_ref`**：存储原始 Execution Receipt 的字节（或 Base64）。恢复时需验证签名、字段一致。
  - **`token`**：如有 fencing 需求，可记录本次执行的"令牌"编号，暂无使用（A3 之外范围）。
  - **事务顺序**：详见状态机
    1. 写入 INTENT（若支持恢复，非必需）
    2. 调用 `registry.dispatch()` 得到 `result`
    3. 调用 `make_receipt()` 生成并签名 `ExecutionReceipt`
    4. 构建 RESULT envelope 并计算 `payload_digest`
    5. 写入 Journal 一条 RESULT（含原始 result、回执、摘要、前序摘要等）
    6. 将原始 Receipt 返回、操作表落库并返回。

## 4. 实施顺序与依赖关系

建议分阶段实施，每阶段实现后立即编写或更新测试：

1. **准备数据库结构**：
   - 在现有执行数据库中添加日志表（`execution_journal`）。
   - 确保 `operations` 表具有 `operation_id` 主键。
   - 提交边界：仅数据库表变更脚本。

2. **实现日志写入逻辑**：
   - 在 `ExecutionStore.execute_once()` 内部的事务中插入两步：
     a) 写 INTENT（`phase="INTENT"`）到日志表（可选，根据 E1.8 可省略）。
     b) 写 RESULT 到日志：在执行工具并生成回执后，写入 `payload_digest`、`result_ref`、`receipt_ref`、`prev_digest` 等。
   - 更新 `last_applied_seq` 为新日志的 `seq`。
   - 提交边界：测试仪表板中的单元测试需覆盖写日志前后的功能。

3. **实现恢复与同步**：
   - 在 `ExecutionStore` 初始化或每次执行前调用 `recover_from_journal()`：
     - 查询日志头 (`MAX(seq)`) 和本地 `last_applied_seq`。
     - 如果 `last_seq < head`, 检查相应序号的日志摘要与本地检查点摘要是否一致。
       - 一致→执行串行化补齐：从 `last_seq+1` 开始逐条读取日志，恢复每条（插入或更新本地执行记录表）。
       - 不一致→立即 fail-closed（抛 `E1ExecutionDenied`）。
     - 若 `last_seq` 对应本地检查点无记录（回滚快照），亦为 fail-closed。
   - 确保恢复过程在事务内执行，并更新 `last_applied_seq`。
   - 提交边界：测试需要覆盖"先落后后同步"、"状态分歧拒绝"等场景。

4. **并发访问测试**：
   - 验证两个 Executor 共享同一 `database_path`，分别同时调用 `execute_e1()`。
   - 确认两个线程/进程并发时，通过 SQLite 加锁保证只有一个真正 dispatch（计数器=1），另一抛 `IDEMPOTENCY_CONFLICT` 或类似幂等错误。
   - 调整配置，使其并发时仍然记录第二次尝试（测试设计时可尝试捕获异常）。

5. **故障恢复测试**：
   - 重复 E1.7 T03：在写日志后模拟进程崩溃（如进程 kill、SQLite 刷新前异常），然后用原始 `PendingExecution` 重试，检查 dispatch 变成2（因为上次记录丢失），并在日志中找到两条记录和两条原始回执。
   - 增加断言：第二次执行生成的回执**must**与第一次日志中记录的 `receipt_ref` 数据**相同**，而非重新签名。

6. **端到端验收**：
   - 执行所有 E1.5–E1.7 测试，确保 A1+B2 改动未破坏原有测试。
   - 新增多线程/多进程流水线测试，模拟一个真实环境下的 SLA：如两个 Executor 分别读取同一待执行队列项。

7. **文档与配置**：
   - 更新 README、注释，说明如何启用共享模式（如环境变量或启动参数）。
   - 标明**测试协议**：如只能支持 SQLite 本地，不适用于分布式数据库。

## 5. 测试场景与安全性质

对应每项变更要有覆盖**安全性质**的测试场景：

- **并发串行化**：两个 Executor 同操作并发执行。预期：仅一次工具调用。测试**全程**保障本地数据库主键/事务。
- **一致性恢复**：数据库回滚后重试。预期：两次工具调用，日志中记录2条结果、签名一致。
- **日志补齐**：Executor2 在本地执行停止后重启。预期：从日志中读取缺失结果并恢复 `last_applied_seq`。
- **日志分歧拒绝**：手动篡改本地数据库或日志。预期：执行拒绝（`E1ExecutionDenied`）。
- **正常流程**：单实例执行。预期：与 E1.5/E1.6 相同的回执生成和计数。
- **重复提交**：对同一个 `operation_id`，如果日志已有 INTENT记录（选做），后续请求是否无效（可不强制）。
- **日志不可篡改**：假设写入日志后立即杀死，重启仍可读取正确数据。

## 6. 故障注入矩阵

| 故障类型 | 注入位置 | 可恢复？ | 预期行为 | 测试场景 |
|---|---|---|---|---|
| 崩溃前仅写 INTENT | 写入日志INTENT后崩溃 | 是 | 再启动时，从日志INTENT补齐或忽略（无 RESULT），仍可执行。 | 模拟INTENT日志存在，恢复后执行。 |
| 崩溃后写 RESULT 前 | 工具dispatch后崩溃，事务未commit | 否（状态丢失） | 重试会再次dispatch（log首条应记录INTENT或无INTENT）。 | 正常恢复测试复现：执行2次，LOG有2条RESULT。 |
| 崩溃写 RESULT 后未更新执行表 | 写完日志但未写表 | 是（日志为锚） | 恢复后执行表落后，触发补齐路径，使用日志恢复前次结果，工dispatch=1。 | 恢复测试检查local state补齐。 |
| SQLite故障回滚 | 恶意恢复旧DB文件 | 否 | 日志seq前后不一致或分歧，抛错停机。 | 修改db文件后执行，应fail-closed。 |
| 日志表写入失败 | 磁盘满或事务失败 | 否 | 事务回滚，Executor终止，不写执行表。 | 模拟写入异常，确认异常传播。 |
| 并发写冲突 | 两Executor同seq写 | 是 | SQLite锁串行化，一个成功一个阻塞，最终一个写入。 | 并发测试，确认串行结果。 |

## 7. 持久化规格与协议遵循

- **Journal 数据表**按设计新增，不改变 D10/D11 回执结构。
- **摘要签名**：`payload_digest` 使用已有 `canonical_digest("e1-result-envelope-v1", envelope)` 算法。Envelope 应严格包含 `(op_id, binding_digest, result, execution_receipt)`。
- **恢复规则**：从日志中恢复回执时，只校验原始签名及摘要，不重新 `sign`。原始回执字节直接从 `receipt_ref` 取得。
- **兼容性**：不修改已有 `ExecutionReceipt`、`BudgetReceipt` 格式，仍用 `make_receipt` 生成、原有签名机制。日志条目签名字段可省略或使用现有密钥。
- **Migration**：如数据库已有数据，新增日志表后应对老记录无操作。历史测试不变。

## 10. 风险与未决问题

- **分布式一致性**：本阶段不支持多进程并行访问同一文件时可能的缓存影响，只考虑单机共享文件。
- **日志可靠性**：假设磁盘或文件系统可靠，日志条目追加操作持久，不再回滚。
- **日志安全**：当前不讨论日志条目篡改或伪造（无额外签名或 HSM）。
- **G1b 未解决**：至多一次真实执行仍为开放问题，不在 E1.9 承诺。
- **外部副作用**：未支持，需额外机制（A3）保证。

以上任务包以 E1.8 设计为蓝本，分阶段实现 A1+B2 要求，并通过丰富的测试验证安全边界。完成后即可交由开发者分工实施，并按此清单逐项验收。
