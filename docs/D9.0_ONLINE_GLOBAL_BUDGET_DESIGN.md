# D9.0 — Online Global Budget Coordination Protocol Design

**Status:** Accepted design baseline for D9.1 reference implementation; not a freeze record

**Repository baseline:** `kaikai-cao/offline-agent-budget-lab`

**Branch baseline:** `experiment/tool-capability-contract`

**Offline baseline:** `10577ab5d53181aef522b7c8f920e4dc7251a124`

**Scope:** online, centrally coordinated budget consumption by multiple Gateways

This design starts from the frozen D8.0–D8.4 Offline Global Budget model. It does not modify that baseline. The first Online version is a network-facing reference service with one logical coordinator and one authoritative transactional database. It is not yet a replicated, highly available, multi-region coordinator.

## 1. Research question

D8 established how multiple Leases share one finite budget when all participating processes cooperate through one host-local Broker, journal, counter emulator and lock. D9 asks:

> How can Gateways on separate machines consume from one global budget through an online authority, while preserving global and per-Lease bounds under concurrent requests, retries, revocation, timeouts and coordinator restarts?

The key new trust boundary is the network-facing Budget Coordinator. A Gateway must not decide locally that budget is available. The Coordinator is the only authority allowed to commit a new budget consumption.

## 2. Proposed Online v1 architecture

```text
                    Issuer
             signs Online Lease Grants
                       |
                       v
              +------------------+
              | Budget           |
              | Coordinator      |
              |                  |
              | - Grant verifier |
              | - Gateway auth   |
              | - Admission FSM  |
              | - Receipt signer |
              +--------+---------+
                       |
              one authoritative DB
               (transactional state)
                       ^
                       | HTTPS / authenticated API
           +-----------+-----------+
           |                       |
      +----+-----+            +----+-----+
      | Gateway A|            | Gateway B|
      | Lease A  |            | Lease B  |
      +----+-----+            +----+-----+
           |                       |
       Tool Adapter            Tool Adapter
```

### 2.1 Authority model

- One logical Coordinator owns one immutable `global_budget_id` and the authoritative global usage ledger.
- All Gateways call the Coordinator for every **new** budget-consuming operation.
- Gateways never maintain an independently spendable copy of the global budget.
- The Coordinator verifies Issuer-signed Lease authorization and Gateway request authentication; it does not trust caller-supplied usage counters, Lease state, quota values or sequence values.
- The Coordinator returns a signed Budget Receipt. A Gateway must verify that receipt before it dispatches the tool.
- The Coordinator's database transaction commit is the linearization point for a consumption operation.

### 2.2 D9.1 reference deployment boundary

To make the first implementation practical in the current Python repository:

- Run one HTTP Coordinator service process.
- The service alone opens and owns a local SQLite database in WAL mode.
- Gateway clients communicate with the service over HTTP; they never open or mount the SQLite file.
- Different Gateway processes can send concurrent requests to the same service. SQLite's write transaction serialization provides the prototype's single-writer admission order.
- Use `BEGIN IMMEDIATE` for the short consume transaction so the service acquires the write transaction before reading and changing budget state.

This is a networked multi-Gateway reference model, not a multi-replica service. SQLite WAL requires database users to be on the same host and is not suitable as a database file shared by remote Gateway hosts; only the Coordinator host touches the file. The official SQLite documentation describes both the single-writer serialization behavior and the same-host WAL constraint: https://www.sqlite.org/isolation.html and https://www.sqlite.org/wal.html.

Production deployment would use a client/server transactional database or a consensus-backed replicated database. D9.1 will not implement database replication or consensus itself.

## 3. Deliberate semantic change from Offline v1

Offline v1 reserves each Lease quota at registration:

```text
A = SUM(Q_i) <= G
0 <= U_i <= Q_i
S = SUM(U_i) = C - C0
S <= A <= G
```

This is conservative and necessary for offline holders: the Broker cannot ask a central authority whether another Lease has already spent the shared pool.

For Online v1, the proposed interpretation changes:

- `G`: hard global consumption ceiling for the budget epoch.
- `Q_i`: hard **per-Lease consumption cap**, not a reservation of global capacity.
- `U_i`: committed consumption by Lease `i`.
- `S`: global committed consumption.

Online v1 invariants become:

```text
0 <= U_i <= Q_i                       for every registered Lease i
S = SUM(U_i)
0 <= S <= G
```

There is deliberately no `SUM(Q_i) <= G` reservation invariant. The sum of per-Lease caps may exceed `G`; the Coordinator checks the global ceiling atomically at the moment of each consume. This removes stranded unused reservations and allows utilization to follow actual demand.

**Trade-off:** a Lease's `Q_i` is an upper bound, not a guarantee that those units will remain available. Two Leases may each have a cap of 8 while `G=10`; in aggregate they can consume only 10. Under contention, one Lease may consume the remaining pool before another. D9.0 gives no fairness or minimum-share guarantee. If the product requires guaranteed per-Lease shares, use a separate reservation policy (`SUM(Q_i) <= G`) rather than silently mixing the two meanings.

This is a protocol-version boundary, not a claim that the Offline invariant was wrong. Offline v1 remains frozen and unchanged.

## 4. Signed objects and identities

### 4.1 Online Global Lease Grant v4 (proposed)

Use a new versioned object rather than overloading the meaning of the D8.1 v3 grant. The Issuer signs at least:

- `version = 4`
- `issuer_id`, `grant_id`, `lease_id`, `nonce`
- `global_budget_id`
- `quota_limit` (per-Lease cap, not reserved quota)
- `issued_at`, `expires_at`
- `coordinator_audience` (the intended Coordinator identity)
- `allowed_gateway_ids` (explicit Gateway identities allowed to use this Lease)
- `subject_id`, `context_digest`
- `allowed_tools: tool_name -> schema_hash`

The Grant has a canonical payload digest and an Ed25519 signature. The Coordinator independently verifies the signature against its configured Issuer public key. `allowed_gateway_ids` is sorted and canonicalized before signing. Grant ID, Lease ID and nonce remain unique within the global budget epoch.

### 4.2 Per-operation Execution Grant

The existing E4.8.3 Execution Grant remains the Gateway-side authorization for one exact operation. It binds the operation ID, Gateway audience, subject, context, tool/schema permission and parent authorization fields.

The Online Coordinator checks that:

- the Execution Grant signature is valid under the configured Issuer key;
- the Execution Grant audience is the authenticated Gateway ID;
- that Gateway ID appears in the registered Online Global Lease Grant's `allowed_gateway_ids`;
- issuer, grant ID, Lease ID, nonce, quota cap, validity interval, subject, context digest and tool/schema permissions agree between the paired grants;
- the Online Global Lease Grant is registered under the requested `global_budget_id`.

This allows one Online Lease to authorize multiple explicitly listed Gateways without making a caller-provided `lease_id` authoritative. The Coordinator resolves the Lease from the signed Grant digest and the authenticated Gateway identity.

### 4.3 Gateway authentication

Each Gateway has a stable `gateway_id` and an Ed25519 key pair. The Coordinator maintains a trusted registry mapping `gateway_id -> public_key / key_id / enabled state`; a caller cannot register or substitute its own public key in a consume request.

Every consume request carries a Gateway signature over a canonical request envelope. Transport TLS is required for a real deployment. D9.1 may use local development transport for tests, but must still verify the application-level Ed25519 request signature so the identity binding is exercised.

### 4.4 Coordinator-signed Budget Receipt

A committed consume returns a Coordinator-signed receipt containing:

- `receipt_version`, `coordinator_id`, `coordinator_key_id`
- `global_budget_id`, `global_sequence`
- `gateway_id`, `lease_id`, `global_lease_grant_digest`
- `execution_grant_digest`
- `operation_id`, `request_digest`
- `lease_used_count`, `global_used_count`
- `committed_at`

The Gateway verifies the Coordinator signature, epoch, Gateway ID, Lease/Grant digests, operation ID, request digest and positive sequence before moving to its local `BUDGET_CONFIRMED` state. The Gateway's final execution receipt should bind the digest (or exact canonical object) of this Coordinator Budget Receipt, rather than only trusting unsigned metadata returned by an adapter.

## 5. Coordinator state and invariants

### 5.1 `budget_meta`

One row per immutable budget epoch:

- `global_budget_id`
- `global_quota_limit` (`G`)
- `global_used_count` (`S`)
- `next_global_sequence`
- configured Issuer public-key digest
- Coordinator signing key ID / public-key digest
- `health` and `health_reason`
- schema/protocol version

Changing the epoch ID, global cap or Issuer trust root requires a new epoch or an explicit administrative migration protocol. D9.0 does not define in-place reset.

### 5.2 `leases`

- `lease_id`, `grant_id`, `nonce`, `grant_digest`
- immutable `quota_limit` (`Q_i`)
- `used_count` (`U_i`)
- issued/expiry times, subject, context, tool permissions
- allowed Gateway IDs
- `state = ACTIVE | EXPIRED | REVOKED`

Registration does not reserve global capacity. The Coordinator rejects a Lease whose signature, epoch, validity, identifier uniqueness or policy is invalid. Exact registration replay is idempotent; conflicting reuse is rejected.

### 5.3 `operations` and `receipts`

- globally unique `operation_id` within the epoch
- authenticated `gateway_id`
- `lease_id`, global Lease Grant digest, Execution Grant digest
- exact `request_digest`
- committed status, global sequence and per-Lease usage count
- canonical Coordinator receipt and signature

An operation ID is globally bound to one tuple:

```text
(gateway_id, lease_id, global_lease_grant_digest,
 execution_grant_digest, request_digest)
```

Exact replay returns the exact stored receipt. Reuse with any different binding is rejected as `OperationBindingConflict`.

### 5.4 Required invariants

While the Coordinator reports `READY`:

```text
0 <= U_i <= Q_i                         for every registered Lease i
S = SUM(U_i)
0 <= S <= G
COUNT(committed operations) = S         (one unit per operation in v1)
COUNT(durable receipts) = S
committed global_sequence values are unique and contiguous
```

D9.0 assumes one budget unit per accepted operation, matching D8. If variable-cost operations are later needed, `cost_units` must be signed/bound into the request and receipt, and invariants/sequence semantics must be revised before implementation.

## 6. Consume protocol and linearization point

For `POST /v1/budget/consume`:

1. Authenticate the Gateway using its configured public key; verify the Gateway signature over the canonical envelope.
2. Verify the Issuer signatures and shapes of the Online Global Lease Grant and per-operation Execution Grant. Verify coordinator audience, Gateway scope, and all paired authorization fields.
3. Validate canonical arguments and request digest at the Gateway. The Coordinator validates digest syntax and binds it to the signed grants and request envelope; it does not reconstruct the business tool result.
4. Begin one write transaction (`BEGIN IMMEDIATE` in the D9.1 SQLite service).
5. Check the global `operation_id` index first. If the stored tuple is identical and committed, return its stored signed receipt without checking current Lease activity or charging again. If the tuple differs, reject. This preserves safe exact replay after later expiry/revocation.
6. For a new operation, load the registered Lease and verify exact Grant digest, `ACTIVE` state, validity under Coordinator/database time, authorized Gateway ID and `U_i < Q_i`.
7. Check `S < G`.
8. In the same transaction, allocate the next global sequence, increment `U_i` and `S`, create the committed operation row, construct/store the exact receipt payload, and store its signature.
9. Commit the database transaction. **The successful transaction commit is the operation's linearization point.**
10. Return the stored receipt. The Gateway verifies it and only then dispatches the tool.

No state that represents a partially consumed budget is committed: the usage counters, sequence, operation row and receipt are one database transaction. A process crash during the transaction therefore leaves either the pre-operation state or the fully committed operation, subject to the database's stated durability assumptions. A lost HTTP response is handled by exact idempotent retry.

In a PostgreSQL-backed implementation, the transaction must use a correct row-locking or serializable strategy, handle serialization failures with bounded retries, and keep the global cap check and all related writes in the same transaction. PostgreSQL documents both explicit row locks and serialization-failure behavior: https://www.postgresql.org/docs/current/explicit-locking.html and https://www.postgresql.org/docs/current/transaction-iso.html.

## 7. Retry, timeout and failure semantics

### 7.1 Client timeout / unknown outcome

A Gateway timeout does not mean the Coordinator rejected the operation. The server may have committed and the response may have been lost.

- Keep the Gateway operation in `ALLOCATING_ONLINE` / unresolved state.
- Retry the **same** `operation_id` with the exact same binding tuple and request digest.
- If the first attempt committed, the Coordinator returns the exact receipt.
- If the first attempt did not commit, the retry may commit it once.
- Never create a new operation ID merely because the HTTP response timed out.
- Never dispatch the tool until a valid signed Coordinator receipt is obtained.

### 7.2 Coordinator unavailable / network partition

- No new budget allocation is allowed without a valid online Coordinator receipt.
- No Gateway-side fallback counter, stale cache, locally inferred remaining balance or offline spending is permitted in Online v1.
- An already committed operation with a locally persisted and verified Coordinator receipt may continue through the existing E4.8.3 tool recovery rules. A Gateway that only has an `ALLOCATING_ONLINE` row must wait/retry the same operation when service connectivity returns.
- Availability is intentionally sacrificed during a partition to preserve the global spending ceiling.

### 7.3 Denials

Distinguish at least:

- `GLOBAL_BUDGET_EXHAUSTED`
- `LEASE_CAP_EXHAUSTED`
- `LEASE_REVOKED` / `LEASE_EXPIRED`
- `GRANT_INVALID` / `GATEWAY_NOT_AUTHORIZED`
- `OPERATION_BINDING_CONFLICT`
- `COORDINATOR_UNAVAILABLE` / `OUTCOME_UNKNOWN`
- `COORDINATOR_INDETERMINATE`

A definite denial is persisted only where it is part of the protocol state. A transport timeout is not converted to a definite denial.

## 8. Revocation and expiry ordering

Consume and revoke operations execute through the same Coordinator transaction authority.

- If a consume transaction commits before a revoke transaction, that operation is valid and its receipt remains replayable.
- If a revoke commits first, a new consume for that Lease is rejected.
- Exact replay of an already committed operation returns its original receipt even after revocation/expiry; it does not consume again or reactivate the Lease.
- New operations are checked against Coordinator/database time and current Lease state.
- Gateways must not rely on a locally cached `ACTIVE` state for new consumption.

This creates a clear commit-order rule and removes the Offline v1 limitation where a remote Gateway cannot learn a revocation until it receives the signed record.

## 9. Threat model

### Modeled in Online v1

- Concurrent requests from multiple Gateway processes/hosts through one Coordinator endpoint.
- Duplicate and delayed HTTP requests, client retries after unknown outcomes and lost responses.
- Operation ID collisions across Leases and Gateways.
- Lease-local cap exhaustion and global cap race at the final unit.
- Revocation/expiry racing with consumption.
- Forged or mismatched Issuer Grants, unauthorized Gateway IDs and request-signature tampering.
- Coordinator restart during or after a database transaction.
- Coordinator receipt tampering or wrong signing key.
- Network outage causing fail-closed behavior.

### Trusted components / assumptions

- Issuer signing key and its issuance policy.
- Coordinator process, its trusted configuration, signing key and runtime.
- Coordinator database and its transactional durability contract.
- Gateway private keys and trusted Tool Adapter implementations.
- Correct TLS deployment and Gateway public-key enrollment for a real network deployment.

### Explicit non-goals for D9.0/D9.1

- Replicated/high-availability Coordinator, leader election, consensus implementation or multi-region writes.
- Byzantine or malicious Coordinator, malicious database administrator, host-kernel compromise, or rollback of the entire authoritative database and its trust state.
- TPM NV Counter, TEE, remote attestation or hardware anti-rollback.
- Offline budget consumption while the Coordinator is unreachable; no hybrid fallback.
- Fair scheduling, minimum per-Lease shares, priority queues or reserved quota guarantees.
- Variable-cost operations, multi-unit atomic batches, refunds or quota reclamation.
- Multi-Issuer federation and automated key rotation protocol.
- Exactly-once external tool effects without the external provider's idempotency/authoritative lookup contract.

## 10. Failure and attack matrix for D9.1/D9.2

| Attack / failure | Expected behavior | Evidence to add |
|---|---|---|
| Two Gateways race for the final global unit | Exactly one consume commits; the other gets global exhausted | Concurrent final-unit test |
| Two requests race with same operation ID and exact tuple | One commit; both receive identical receipt | Duplicate same-op race test |
| Same operation ID, different Lease/request/Gateway | Conflict; no second charge | Cross-Lease and cross-Gateway collision tests |
| HTTP response lost after DB commit | Retry returns original receipt, no extra usage | Commit-then-drop-response test |
| Coordinator process killed during transaction | DB shows either zero or one committed operation; retry resolves | Process-kill transaction-boundary test |
| Lease revoked races with consume | Commit ordering determines one unambiguous result | Consume/revoke race test |
| Gateway request signature or Grant tampered | Reject before budget mutation | Authentication/tamper tests |
| Coordinator response/receipt tampered | Gateway rejects and does not dispatch tool | Receipt-signature rejection test |
| Coordinator unavailable | No new allocation and no local fallback | Service-down fail-closed test |
| Client submits stale cached `ACTIVE` Lease | Coordinator current state wins; revoked/expired denied | Stale-state test |

After each successful or rejected operation, assert the D9 invariants from Section 5.4. Tests must verify both the service ledger and Gateway/tool effect count.

## 11. Stage plan

### D9.0 — protocol design and threat model (this document)

Agree on authority model, quota semantics, API trust, idempotency, transaction and failure rules before implementation.

### D9.1 — single-node Online Coordinator reference implementation

- Add a new Online package; do not edit the frozen Offline source or tests.
- Implement one HTTP Coordinator service with a Coordinator-owned SQLite WAL database.
- Implement v4 Online Global Lease Grants, Gateway Ed25519 request authentication, signed Coordinator Budget Receipts, register/revoke/consume/lookup APIs.
- Integrate a narrow Online adapter with E4.8.3 Gateway; preserve the Offline adapter and its regression suites unchanged.
- Test multiple independent Gateway processes against one service process.

### D9.2 — adversarial network and recovery validation

- Inject delayed, duplicate, dropped and reordered requests/responses.
- Kill/restart the Coordinator around transaction commit boundaries.
- Race consume against revoke and expiry.
- Test global-final-unit, per-Lease cap, operation-ID cross-binding and receipt tampering.
- Prove fail-closed behavior when service is unavailable.

### Later, separately scoped: Coordinator HA / replication

Only after D9.1/D9.2, evaluate a replicated SQL database or replicated state machine. If a Raft-style replicated log is selected, committed entries must be replicated to a quorum and state-machine safety must hold; a minority partition must not continue committing budget consumption. The Raft paper describes these safety properties and the quorum/availability trade-off: https://raft.github.io/raft.pdf. D9.0 does not implement or claim those guarantees.

## 12. D9.0 acceptance decisions

The following decisions are accepted as the D9.1 reference-model baseline:

1. **One logical online authority.** No Gateway may spend locally; the Coordinator is the sole admission point.
2. **Online v1 uses per-Lease caps, not pre-reservations.** `SUM(Q_i)` may exceed `G`; atomic consume enforces `SUM(U_i) <= G`. This improves utilization but gives no minimum-share guarantee.
3. **One operation equals one budget unit.** Variable cost is deferred.
4. **Global operation ID and exact idempotent retry.** The binding tuple includes Gateway, Lease, both Grant digests and request digest.
5. **Database commit is the linearization point.** Counter increment, Lease/global usage, sequence, operation row and signed receipt are one transaction.
6. **Coordinator outage means fail closed.** No offline fallback or stale cached allowance.
7. **Single-node Coordinator first.** HTTP service + local SQLite WAL database; Coordinator HA/consensus is a later stage.
8. **New Online Grant version.** Use a v4 Online Global Lease Grant with explicit allowed Gateway IDs; do not change the frozen v3 Offline Grant semantics.

These decisions were accepted as the D9.1 implementation baseline. They do not authorize changes to the frozen Offline repository.
