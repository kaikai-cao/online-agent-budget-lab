# D11.3-A — 隐私预算状态协议设计

> 状态：**设计稿（协议冻结候选）**。本阶段不写 Halo2 代码、不修改生产代码、不实现电路。
> 目的：把协议定义、状态机与安全边界固定下来，供后续 D11.3-B 电路、D11.3-C Coordinator、D11.3-D Python 参考模型直接引用，避免各自实现时语义不一致。
> 上游：D11.0（隐私目标与关系草案）、D11.1（uint32 数学基准）、D11.2（Halo2 最小电路）。

## 0. 一条必须先说清楚的隐私边界

**如果每次转移的消费量 `c` 都公开，且转移记录可以相互关联，那么累计消费量可以由历史求和推导出来：**

\[
u_n=\sum_{i=1}^{n} c_i
\]

因此，即使 `u_old` / `u_new` 在电路中是私有见证，观察者只要看到全部的 `(c_1, …, c_n)` 并确认它们属于同一预算实例，就能算出当前累计消费。

**本阶段的隐私目标因此被明确限定为：**

- 隐藏：工具名称、工具参数、调用内容、状态随机数 `r`、状态承诺的内部开口 `(u, r, K)`。
- 公开：总配额 `Q`、每次消费量 `c`、预算周期、`budget_id`、状态承诺 `C`、Nullifier `N`、策略摘要 `P`，以及**可相互关联的转移序列**。

**不宣称**：隐藏累计消费量、隐藏单次消费量、隐藏转移次数/时间/频率、完全隐藏消费历史。

第一版是「隐藏调用明细与承诺开口」，不是「隐藏消费历史」。任何后续把协议描述成完全隐私的表述都必须先回到这一节核对。未来增强（批量提交、只公开周期聚合消费量、进一步隐藏单次 `c`）属于 D11.3 之后的独立阶段，不在本设计范围内。

## 1. 研究目标与非目标

### 1.1 目标

定义一个可供电路与 Coordinator 共同遵守的**预算状态转移协议**，使 Coordinator 能接受「确实基于当前状态、未超额、未重复、未回滚」的转移，同时不获知状态承诺的内部开口与具体工具调用内容。

本阶段要回答五个问题：

1. 什么是一个预算状态（§2、§3、§4）。
2. 如何证明新状态承接旧状态（§5）。
3. Nullifier 如何绑定状态转移、且密钥不可中途更换（§6）。
4. Coordinator 如何防止重复提交与并发竞争（§7、§8）。
5. 哪些信息泄露、哪些可以隐藏（§0、§10）。

### 1.2 非目标（本阶段明确不做）

- 不实现 Halo2 电路（D11.3-B）。
- 不实现 Coordinator 原子存储与并发测试（D11.3-C）。
- 不实现 Python 参考状态机（D11.3-D）。
- 不证明工具调用获得了合法授权、不证明工具确实按要求执行（沿用 D11.0 边界；见 D10.4–D10.7 的授权/回执工作）。
- 不证明 Executor 计量 `c` 的真实性——本阶段把 `c` 当作已由可信来源给定的公开输入（见 §9 信任假设）。
- 不定义 Poseidon 的具体参数、域分离常量取值、输入编码细节（§6.4 列为待决）。

## 2. 符号表与数据可见性

金额沿用 D11.1 / D11.2 的 **uint32** 约束：`0 ≤ Q, u, c, s ≤ 2³²−1`，`Q ≥ 1`，`c ≥ 1`。本阶段不扩大数值范围。

| 符号 | 含义 | 可见性 |
| --- | --- | --- |
| `budget_id` | 预算实例唯一标识 | 公开 |
| `period_id` | 预算周期标识 | 公开 |
| `Q` | 总配额 | 公开 |
| `c` | 本次消费量 | 公开 |
| `u_old` | 消费前累计消费 | 私有 |
| `u_new` | 消费后累计消费 | 私有 |
| `r_old` | 旧状态随机数（盲化因子） | 私有 |
| `r_new` | 新状态随机数（盲化因子） | 私有 |
| `C_old` | 旧状态承诺 | 公开 |
| `C_new` | 新状态承诺 | 公开 |
| `N` | Nullifier | 公开 |
| `P` | 策略版本或策略摘要 | 公开 |
| `nf_secret` | Nullifier 密钥（实例级长期秘密） | 私有 |
| `K` | 与实例关联的隐藏 Nullifier 密钥承诺 | 隐藏（嵌入承诺内部） |
| `D_state`, `D_key`, `D_nf` | 各用途域分离常量 | 公开常量 |

### 2.1 `budget_id` 与 `period_id` 的作用域

这两个标识共同界定一个 Nullifier 与一个状态承诺的**唯一作用域**，必须精确定义，否则跨实例/跨周期重放无法被正确检测：

- **`budget_id`**：标识一个预算实例。它在一个 `period_id` 内唯一，标识"谁/哪一项预算"。作用域是「单个周期内的一个预算主体」。
- **`period_id`**：标识预算周期（如时间窗口编号、epoch 号）。它给出状态与 Nullifier 的时间边界。**换周期即换命名空间**：同一 `budget_id` 在不同周期是两个互不相干的状态与 Nullifier 集合。
- **联合作用域**：协议中一切唯一性约束都作用在二元组 `(budget_id, period_id)` 上——初始状态唯一、当前状态指针、已用 Nullifier 集合均按此二元组分区。

**与现有 D9 系列的衔接（仅为对齐术语，不强制耦合）**：现有在线预算系统用不可变的 `global_budget_id` 与 budget epoch 表达"一个全局预算周期"。本协议的 `(budget_id, period_id)` 可分别对应到该系统的 `global_budget_id` 与 epoch。D11.3 实验独立运行，不依赖该映射成立；做 D11.3-E 集成验证时再确认映射细节。

**强制规则**：

1. `budget_id` 与 `period_id` 都进入状态承诺、Nullifier 派生与 ZKP 公开输入（§3、§6）。
2. Coordinator 的当前状态表与已用 Nullifier 表都以 `(budget_id, period_id)` 为分区键。
3. 改变 `period_id` 必须走新周期的初始化流程（§4），不得就地重置旧周期状态。

## 3. 状态承诺设计

### 3.1 承诺语义

状态承诺绑定预算实例、周期、配额、累计消费、随机盲化因子与隐藏密钥承诺：

\[
C = \operatorname{Poseidon}\big(D_{\mathrm{state}},\ budget\_id,\ period\_id,\ Q,\ u,\ r,\ K\big)
\tag{1}
\]

其中：

- `D_state`：状态承诺专用域分离常量，防止与其他用途的 Poseidon 输出混淆。
- `r`：随机盲化因子。同一个人以相同 `u` 生成状态时必须用新的 `r_new`，否则两个状态承诺相同、可被关联。
- `K`：与该预算实例关联的隐藏 Nullifier 密钥承诺（见 §3.2）。

**输入顺序固定为**：`(D_state, budget_id, period_id, Q, u, r, K)`。字段顺序、编码与长度在 D11.3-B 之前必须冻结（编码细节见 §6.4 待决项）；输入顺序变更会使所有已注册承诺失效，属于协议破坏性变更。

### 3.2 隐藏密钥承诺 `K` 与密钥绑定

\[
K = \operatorname{Poseidon}\big(D_{\mathrm{key}},\ nf\_secret,\ budget\_id,\ period\_id\big)
\tag{2}
\]

`nf_secret` 必须在**同一个预算实例的整个生命周期内保持一致**；`K` 由它派生并嵌入旧、新两个状态承诺（式 (1) 的最后一个输入）。

**作用域必须区分清楚**：`nf_secret` 是**预算实例级长期秘密**；`K = Poseidon(D_key, nf_secret, budget_id, period_id)` 是**预算实例与周期共同作用域下的派生密钥承诺**。由于 `period_id` 进入派生，即使 `nf_secret` 不变，换周期也会得到不同的 `K`。因此：

- 新周期必须按 §4 重新注册新的初始状态（含新的 `K`）；
- 旧周期状态不能直接迁移到新周期（分区键与承诺内部字段都不同，§2.1）；
- "长期秘密不变"与"密钥承诺不变"是两件事，不得混同。

**为什么 `K` 必须纳入状态承诺？**（这是本设计的关键安全点）

Nullifier 用于检测"同一状态是否被重复消费"。它的派生输入之一是 `nf_secret`（§6）。如果 Prover 能在每次转移时任意更换 `nf_secret`，它就能对**同一个旧状态**生成**不同的 Nullifier**，从而让 Coordinator 的"Nullifier 未使用"检查永远通过——重复消费检测被彻底绕过。

把 `K` 嵌入 `C_old` 与 `C_new`，并在电路里约束两个承诺使用**同一个 `K`**（进而同一个 `nf_secret`），就把密钥钉死在状态上：Prover 诚实地打开旧状态承诺时，只能取出注册时确定的那个 `K`，无法换密钥。更换 `nf_secret` 会导致算出的 `K` 与旧状态承诺里承诺的 `K` 不一致，式 (2) 的约束失败。

> 注意：`K` 是承诺的**内部开口**，对 Coordinator 隐藏；Coordinator 只看到 `C_old`/`C_new`，看不到 `K` 或 `nf_secret`。密钥一致性由 ZKP 在电路内保证，而不是由 Coordinator 读明文比较。

### 3.3 盲化因子要求

- `r_old`、`r_new` 是私有随机值，参与状态承诺。
- **初始 `r_0` 同样必须由密码学安全随机源独立生成**（§4.1 步骤 2），与 `nf_secret` 独立采样，不复用任何历史状态随机数或其他用途的随机数。
- **每次生成新状态时，必须用密码学安全随机源独立生成新的 `r_new`**：随机数须具有足够熵、不可预测，且不复用任何历史随机数。
- **不要求在电路中证明 `r_new ≠ r_old`**。真正重要的是随机数的不可预测性与独立性，而不是两个值的简单不等；仅满足 `r_new ≠ r_old` 并不构成充分的随机性保证。只要 `r_new` 由安全随机源独立采样，相邻状态承诺相同的概率可忽略。
- `r` 的具体位宽与生成方式列为 §12 待决，留到 Poseidon 参数与字段编码冻结时一并确定；第一版要求至少与承诺域的安全参数匹配。

## 4. 初始状态注册协议

\[
C_0 = \operatorname{Commit}\big(D_{\mathrm{state}}, budget\_id, period\_id, Q, 0, r_0, K_0\big),\qquad K_0=\operatorname{Poseidon}(D_{\mathrm{key}}, nf\_secret, budget\_id, period\_id)
\tag{3}
\]

### 4.1 初始密钥建立（本轮冻结：方案 B / Prover 生成、Issuer 授权、Coordinator 注册）

协议起点必须回答"谁生成、谁持有 `nf_secret` 与 `r_0`、Issuer 如何注册"。第一版采用**方案 B：Prover 本地生成秘密，Issuer 只授权预算注册而不接触秘密，Coordinator 验证签名后注册状态**。这样可信方掌握的秘密最少，与"Coordinator 不知道状态开口"的隐私目标一致。

1. **Issuer 分配字段**：分配 `budget_id`、`period_id`、`Q` 和策略摘要 `P`（预算额度与身份由可信方决定，不由 Agent 自定）。
2. **Prover 本地生成秘密**：用密码学安全随机源独立生成 `nf_secret` 与 `r_0`（§3.3），二者只保留在 Prover 本地。
3. **Prover 计算承诺**：本地计算 `K_0 = Poseidon(D_key, nf_secret, budget_id, period_id)` 与 `C_0 = Commit(D_state, budget_id, period_id, Q, 0, r_0, K_0)`。
4. **提交注册请求**：Prover 向 Issuer 提交 `C_0` 及预算注册请求（含 `budget_id`、`period_id`、`Q`、`P`）。
5. **Issuer 签发注册授权**：Issuer 验证预算授权、配额与策略，签发绑定 `(budget_id, period_id, Q, P, C_0)` 的注册授权。第一版用 **Issuer 的签名注册授权**，不为注册单独引入 Halo2 电路。
6. **Coordinator 验证并注册**：Coordinator 验证 Issuer 签名后，注册 `C_0`、`Q`、`P` 及注册授权记录（§7.1），设置当前指针。
7. **Prover 保留秘密**：`nf_secret`、`r_0` 由 Prover 留存，后续通过状态转移证明（§5）证明自己知道正确开口，无需再次向任何可信方披露。

**职责边界**：

- Agent **无权**自行决定预算额度与预算身份（`Q`、`budget_id`、`period_id`、`P` 由 Issuer 分配）。
- Agent **可以**自行生成隐藏状态秘密（`nf_secret`、`r_0`）。
- Issuer **授权**预算注册，但不掌握状态开口。
- Coordinator **保存**当前状态与注册授权，但不掌握秘密。

**注册授权的性质与边界（不得夸大）**：第一版注册请求**不含知识证明**，因此 Issuer 签发的只是"对某个 `C_0` 的注册授权"，**并未在密码学上验证 Prover 知道该承诺的开口** `(u_0=0, r_0, K_0)`。若 Prover 不知道秘密，其后果只是**无法生成后续有效的状态转移证明**（§5 的承诺开口约束不满足），而不是可以绕过预算约束。这是**可用性性质**，不是**安全性质**——不得把"注册成功"描述为"Issuer 已验证 Prover 持有秘密"。若未来需要注册时的知识证明，属后续独立阶段。

### 4.2 注册规则

1. **初始累计消费为 0**：`u_0 = 0`。
2. **实例唯一初始状态**：每个 `(budget_id, period_id)` 只允许注册一个初始状态。Coordinator 维护 `initial_registered[(budget_id, period_id)]` 标志，重复注册拒绝，冲突注册（相同键不同 `C_0`）视为错误。
3. **注册授权是生效前提**：`C_0` 虽由 Prover 计算，但只有在 Issuer 签名授权、Coordinator 验证通过后才生效；Agent 自行生成但未获授权的 `C_0` 一律不接受。Issuer 需验证 `Q ≥ 1`、实例标识合法。
4. **Coordinator 保存当前指针**：注册成功后设置 `current_commitment[(budget_id, period_id)] = C_0`，`current_version[(budget_id, period_id)] = 0`。
5. **注册时登记策略摘要**：同一注册步骤中设置 `registered_policy[(budget_id, period_id)] = P_0`，供后续转移按 §5.2 约束五（方案 B）精确比较。策略摘要不进入状态承诺，其正确性由本次可信注册保证。
6. **后续转移必须承接已注册状态**：第一次转移的 `C_old` 必须等于该已注册的 `C_0`；不允许从任意自造状态开始。

**为什么禁止 Agent 自建初始状态**：若 Agent 能自行决定 `budget_id` 或让未授权的 `C_0` 生效，它就能把一笔消费分散到多个配额实例上，绕过单实例 `Q` 的限制。`budget_id` 的分配权与注册授权签发权必须属于可信方，Coordinator 只接受已验证授权的注册。

## 5. 状态转移关系

### 5.1 公开输入与私有见证

公开输入（ZKP instance 与提交请求携带）：

\[
x = (budget\_id,\ period\_id,\ Q,\ c,\ C_{\mathrm{old}},\ C_{\mathrm{new}},\ N,\ P)
\tag{4}
\]

私有见证：

\[
w = (u_{\mathrm{old}},\ u_{\mathrm{new}},\ s,\ r_{\mathrm{old}},\ r_{\mathrm{new}},\ nf\_secret)
\tag{5}
\]

其中 `s = Q − u_new` 是 §5.2 约束一使用的非负 slack 辅助见证，与其余见证一样不进入公开输入。

### 5.2 电路必须证明的约束

**约束一 — 预算正确性与状态承接**（uint32 范围约束全部生效）：

必须在电路内用**两条独立等式**实现，不能只用一条含 slack 的等式：

\[
\boxed{u_{\mathrm{old}} + c - u_{\mathrm{new}} = 0}
\tag{6a}
\]

\[
\boxed{u_{\mathrm{new}} + s - Q = 0}
\tag{6b}
\]

并约束：`1 ≤ c`、`0 ≤ u_old`、`0 ≤ u_new`、`0 ≤ s`、`1 ≤ Q`。`u_old`、`u_new`、`c`、`s`、`Q` **五个值全部做 32 位范围约束**，`Q ≥ 1`、`c ≥ 1` 另加非零约束（§11）。`s` 为非负 slack 私有见证。式 (6a) 保证新累计消费正确承接旧状态并加上本次消费，式 (6b) 配合 `s ≥ 0` 保证新状态未超配额。

**为什么必须是两条等式（关键）**：若只写 `u_old + c + s − Q = 0`（D11.2 的 slack 形式）而不约束 `u_new = u_old + c`，Prover 可取 `u_old=10, c=5, s=85, Q=100`（等式成立），却令 `C_new` 打开为 `u_new=90` 而非 15。预算等式成立但状态连续性被破坏——后续转移将从 90 继续，凭空多出 75 单位额度。式 (6a) 直接封住：`C_new` 承诺的 `u_new` 必须等于被约束的 `u_old + c`。

**无模回绕论证**：两个 uint32 数之和最大为 `2³³−2`，远小于 Pasta 标量域模数（约 `2²⁵⁵`），因此式 (6a)(6b) 的域等式不会因模运算回绕而成立。再叠加 `u_new`、`s` 的 32 位范围约束：`u_old + c` 若超过 `2³²−1`，式 (6a) 在整数意义下无合法的 32 位 `u_new` 可满足；`u_new + s` 若超过 `2³²−1`，式 (6b) 同理。故域等式与范围约束共同等价于整数预算关系。

**约束二 — 旧状态开口正确**：

\[
C_{\mathrm{old}} = \operatorname{Poseidon}(D_{\mathrm{state}}, budget\_id, period\_id, Q, u_{\mathrm{old}}, r_{\mathrm{old}}, K),\quad K=\operatorname{Poseidon}(D_{\mathrm{key}}, nf\_secret, budget\_id, period\_id)
\tag{7}
\]

**约束三 — 新状态开口正确**：

\[
C_{\mathrm{new}} = \operatorname{Poseidon}(D_{\mathrm{state}}, budget\_id, period\_id, Q, u_{\mathrm{new}}, r_{\mathrm{new}}, K)
\tag{8}
\]

**约束四 — 同一密钥承诺**：式 (7)、(8) 使用**同一个 `K`**（同一 `nf_secret`）。这是 §3.2 的密钥绑定约束，必须显式成立；它同时阻止换密钥绕过 Nullifier 检测。

**约束五 — 策略摘要 `P` 的绑定（本轮冻结：方案 B / Coordinator 绑定）**：

第一版 `P` **不进入状态承诺、不在电路内参与密码学约束**；`P` 仅作为公开输入（式 (4)），由 Coordinator 与注册时保存的策略摘要精确比较：

```
验证时检查：proof.public_inputs.P == registered_policy[(budget_id, period_id)]
```

- `registered_policy[(budget_id, period_id)]` 在初始状态注册时由可信方写入（§4.2 规则 5）。
- 比较失败则拒绝整个转移请求；策略变更必须走新的注册或显式迁移流程，不得就地修改已注册摘要。
- **明确的边界**：在此方案下 `P` 的正确性由 Coordinator 的策略注册与比较保证，**不宣称状态承诺本身绑定了 `P`**。仅把 `P` 放进 Instance Column 不构成电路内的策略证明——电路若不使用该字段，Prover 可填入任意值。这是单一可信 Coordinator 模型下的有意取舍，用于把第一版电路复杂度控制在 D11.2 量级。
- 若未来需要密码学绑定（方案 A：把 `P` 纳入状态承诺并约束新旧状态使用同一摘要），属后续独立阶段，需重新冻结协议。

> 与 D11.0 / D11.2 的关系：D11.0 草案与 D11.2 电路使用单条 `u+c+s=Q`；本设计把 `u_new` 显式化为见证，并用 (6a)(6b) 两条等式把它钉在旧状态与配额上，数学基准不变但状态承接更严格。域分离常量、编码与字段顺序在 §6.4 列为待决，写出公式不等于已完成密码学安全证明。

## 6. Nullifier 派生规则

### 6.1 派生公式

\[
N = \operatorname{Poseidon}\big(D_{\mathrm{nf}},\ nf\_secret,\ budget\_id,\ period\_id,\ C_{\mathrm{old}}\big)
\tag{9}
\]

其中 `D_nf` 是 Nullifier 专用域分离常量，`nf_secret` 为实例长期秘密（§3.2），`C_old` 为本次消费的旧状态承诺。

### 6.2 为什么这样绑定

- **绑定 `budget_id` + `period_id`**：不同预算实例、不同周期即使使用相同状态数值或相同 `nf_secret`，也产生不同 Nullifier，阻止跨实例/跨周期重放（Cross-Budget / Cross-Period Replay）。
- **绑定 `nf_secret`**：外部观察者无法仅凭公开字段预测或伪造 Nullifier；且配合 `K` 绑定（§3.2、§5.2 约束四）防止 Prover 换密钥。
- **绑定 `C_old`**：同一实例内，不同旧状态产生不同 Nullifier，使每次转移有唯一标识，便于 Coordinator 检测重复提交。同一 `(nf_secret, budget_id, period_id, C_old)` 必产生同一 `N`，因此重放同一转移会被"N 已使用"拒绝。

### 6.3 派生不泄露秘密，但不提供转移链不可关联性

`N` 是公开值，但由 Poseidon 单向性，从 `N` 无法反推 `nf_secret` 或 `u`，Coordinator 也无法从 `N` 本身得知具体工具调用内容。

**必须避免的误解**：不能说"同一实例的不同转移产生不可关联的 Nullifier"。虽然每次转移的 `C_old` 不同、因而 `N` 不同，但公开数据同时包含 `C_old → C_new` 的状态链，而 `N = Poseidon(D_nf, nf_secret, budget_id, period_id, C_old)` 直接绑定该 `C_old`。观察者可以把每个 `N` 对上它对应的旧状态承诺，进而沿状态链把同一实例的多次转移串起来。

**准确表述**：Nullifier 的公开值不直接泄露 `nf_secret`，但由于状态承诺与转移序列公开，同一预算实例内的状态转移仍然可以关联。**本协议不提供转移链不可关联性。**这与 §0、§10 的隐私边界一致。

### 6.4 待决（不得直接视为已安全）

- `D_state` / `D_key` / `D_nf` 的具体取值与相互独立性。
- Poseidon 参数（t、rounds、rate/capacity）、输入域元素的编码与填充、字段长度（uint32 金额与 id 如何装入域元素）。
- 字段顺序在式 (1)(2)(9) 中已固定为候选，但需在 D11.3-B 前冻结并与实现一一对应。
- `nf_secret` 与 `r` 的位宽、生成与生命周期管理（尤其密钥泄露/轮换策略）。
- `P` 的绑定已冻结为方案 B（Coordinator 注册比较，§5.2 约束五），不再作为待决项。策略迁移流程细化留待 D11.3-C。

## 7. Coordinator 状态机

### 7.1 持久化状态

Coordinator 为每个 `(budget_id, period_id)` 维护：

| 结构 | 含义 |
| --- | --- |
| `initial_registered` | 是否已注册初始状态（布尔） |
| `current_commitment` | 当前状态承诺 `C_current` |
| `current_version` | 当前状态版本号 `v`（初始 0，每次成功转移 +1） |
| `used_nullifiers` | 已使用 Nullifier 集合 |
| `registered_policy` | 注册时登记的策略摘要 `P`（§4.2 规则 5、§5.2 约束五） |
| `registration_authorization` | Issuer 签名的初始注册授权（绑定 `budget_id`/`period_id`/`Q`/`P`/`C_0`），验证通过后留存（§4.1 步骤 5–6） |

### 7.2 一次转移的接受流程

> **前置条件**：任何转移请求只能针对已完成 §4.1 注册流程的 `(budget_id, period_id)`——即 Issuer 签名的注册授权已由 Coordinator 验证通过、`initial_registered == true`。未完成注册或授权验证失败的实例，其请求在步骤 2 直接拒绝，不进入后续验证。

1. **收到转移请求**：接收证明 `π`、公开输入 `x=(budget_id, period_id, Q, c, C_old, C_new, N, P)`。
2. **检查状态已注册（含注册授权验证）**：`initial_registered[(budget_id, period_id)] == true`，且留存的 `registration_authorization` 与注册字段一致；否则拒绝（未注册实例 / 注册授权无效）。
3. **检查当前状态**：`C_old == current_commitment[(budget_id, period_id)]`，否则拒绝（过期 `C_old` / 状态回滚 / 分叉）。
4. **检查 Nullifier 未使用**：`N ∉ used_nullifiers[(budget_id, period_id)]`，否则拒绝（重复消费 / 重放）。
5. **检查策略摘要**：`P == registered_policy[(budget_id, period_id)]`，否则拒绝（策略不匹配；§5.2 约束五方案 B）。
6. **验证 ZKP**：验证证明满足 §5.2 全部约束，且公开输入与请求字段一致（证明绑定公开输入，沿用 D11.2 验证结论）。
7. **原子提交**：在**同一事务**内执行 `used_nullifiers.insert(N)`、`current_commitment = C_new`、`current_version += 1`；任一步失败则整体回滚。

### 7.3 状态机规则表

| 情况 | 预期行为 |
| --- | --- |
| 正常状态转移 | 接受 |
| 重复提交相同 Nullifier | 拒绝（步骤 4） |
| 使用过期的 `C_old` | 拒绝（步骤 3） |
| 伪造 `C_new` | 证明验证失败（步骤 5，承诺开口约束） |
| 伪造 Nullifier | 证明验证失败（步骤 5，Nullifier 派生约束） |
| 两个请求同时使用相同 `C_old` | 只允许一个成功，另一个因 `C_old` 过期或原子提交冲突失败 |
| 状态更新成功但 Nullifier 未登记 | 不允许出现（同一事务，§8） |
| Nullifier 登记成功但状态更新失败 | 不允许出现（同一事务，§8） |
| 未注册 `budget_id`/`period_id` | 拒绝（步骤 2） |
| 公开输入 `P` 与注册策略摘要不符 | 拒绝（步骤 5，方案 B） |
| 跨周期使用该周期的状态承诺 | 拒绝（步骤 2/3，分区键不同） |

## 8. 并发与原子提交规则（本设计的关键点）

### 8.1 原子性要求

**Nullifier 登记与状态指针更新必须原子完成。** 仅在 Python 中先检查 `N` 是否存在、再单独更新状态是**不安全的**：两个并发请求可能同时通过"N 未使用"检查，随后各自提交，造成同一状态被消费两次。

第一版参考模型（D11.3-C/D）用事务或锁模拟原子提交；生产实现用数据库 CAS / 唯一约束 / 事务。无论实现形态，逻辑上等价于一个**比较并交换（CAS）**：

```
CAS( key=(budget_id, period_id),
     expected_commitment = C_old,
     expected_nullifier_unused = N,
     commit = { used_nullifiers += N,
                current_commitment = C_new,
                current_version += 1 } )
```

仅当 `current_commitment == C_old` 且 `N ∉ used_nullifiers` 时提交成功；否则整笔拒绝。CAS 的原子性由底层存储保证。

### 8.2 并发冲突的判定

两个请求 `A`、`B` 若指向同一 `(budget_id, period_id)` 且 `C_old` 相同：

- 它们产生相同 `N`（§6.2 的确定性派生），因此无论靠"N 唯一"还是靠"C_old 等于当前承诺"，最多一个能通过 CAS。
- 先提交者成功；后提交者要么在步骤 4 因 `N` 已登记被拒，要么在 CAS 阶段因 `current_commitment` 已变为 `C_new` 而失败。
- 不允许出现"两个都成功"。

### 8.3 事务边界

事务内只允许三类写操作，且必须全成功或全回滚：

1. 插入 Nullifier `N` 到 `used_nullifiers`（唯一约束保证不可重复）。
2. 更新 `current_commitment = C_new`。
3. 更新 `current_version += 1`。

`current_version` 语义上是单调递增的序列，用于可观测性与审计；它的正确性同样依赖原子提交，不允许在事务外单独更新。

### 8.4 崩溃一致性

若在事务提交过程中崩溃，数据库事务的原子性保证上述三项要么全部生效、要么全部不生效，不会出现"有状态无 Nullifier"或"有 Nullifier 无状态"的不一致半提交状态。参考模型须以同样语义模拟（例如用单一互斥锁包住整个检查+提交段）。

## 9. 威胁模型与安全假设

### 9.1 攻击者能力

假设攻击者控制 Agent 的 Planner/Prover，可以：任意构造见证、修改公开输入、重复提交旧证明、并发提交多个转移、跨实例/跨周期重放、尝试自选 Nullifier、尝试中途更换 `nf_secret`、尝试从公开数据推断隐藏状态。

### 9.2 攻击 → 安全性质

| 攻击 | 希望达到的安全性质 | 本设计的防御 |
| --- | --- | --- |
| Budget Overflow | 无法超过总配额 | 约束一中的两条独立等式 (6a)(6b) 与五个变量的 uint32 范围约束（不得沿用 D11.2 的单条 slack 等式） |
| State Forgery | 无法伪造旧/新状态开口 | 约束二、三（承诺开口必须在电路内成立） |
| Nullifier Forgery | 无法自行选择有效 Nullifier | 约束 `N = Poseidon(D_nf, nf_secret, budget_id, period_id, C_old)`（§6） |
| Replay | 同一状态转移不能重复接受 | `N ∈ used_nullifiers` 检查（步骤 4） |
| Concurrent Double Spend | 两个竞争请求最多一个成功 | CAS 原子提交（§8） |
| State Rollback | 不能从旧状态覆盖新状态 | `C_old == current_commitment` 检查（步骤 3）+ 原子更新 |
| Cross-Budget Replay | 不同预算实例间不能重放 | `budget_id` 进入 `N`、承诺与分区键 |
| Cross-Period Replay | 不同预算周期间不能重放 | `period_id` 进入 `N`、承诺与分区键 |
| Nullifier-Key Swap | 不能通过换密钥绕过重放检测 | `K` 嵌入新旧承诺 + 同一 `K` 约束（§3.2、§5.2 约束四） |

### 9.3 信任假设（不得夸大）

- **可信**：Issuer 的初始状态签发与 `budget_id` 分配；Coordinator 的证明验证、状态存储与原子提交；Poseidon 参数与域分离规则正确；Executor 的真实计量（本阶段把 `c` 视为已给定的公开输入，不证明其真实性）。
- **不可信**：Planner / Prover，可恶意构造见证与公开输入。
- **密码学保证依赖**：承诺绑定性、ZKP 完备性/可靠性/零知识性、Poseidon 的抗碰撞与单向性、底层事务的原子性与持久性。
- **不在范围内**：Coordinator 与 Executor 串通或被攻陷时，隐私与计量正确性都不再成立（沿用 D11.0 的信任边界）。

## 10. 隐私泄露分析（独立结论）

1. **可隐藏**：工具名称、工具参数、调用内容、状态随机数 `r`、状态开口 `(u, r, K)`、`nf_secret`。这些只作为私有见证出现在证明中，不进入公开输入。
2. **公开**：`Q`、`c`、`period_id`、`budget_id`、`C_old`、`C_new`、`N`、`P`。
3. **可由公开信息推导**：累计消费 `u_n = Σ c_i`（§0）。**因此不得宣称累计消费被隐藏。**
4. **可关联性**：因为转移链（`C_old → C_new`）与公开 `c` 序列，同一实例的多次转移可被关联；状态版本 `v` 与稳定的 `budget_id` 进一步提供关联线索。第一版不隐藏转移次数、时间与顺序。
5. **零知识保证的边界**：ZKP 保证公开输入之外的见证不被泄露，但不改变"公开输入本身已经足够推导 `u`"这一事实。零知识 ≠ 公开数据不泄露信息。
6. **未来增强方向**（非本阶段）：批量提交多个消费事件、只公开周期聚合消费量、隐藏单次 `c`、打散转移关联。任何增强都必须重新做本节分析。

**第一版隐私承诺的准确表述**：

> 在可信 Issuer、Coordinator、Executor 的前提下，面对恶意 Prover，本协议使 Coordinator 能验证预算状态转移的正确性、唯一性与不可回滚性，而不需要获知状态承诺的内部开口与具体工具调用内容；但公开消费量序列允许推导累计消费量，转移之间保持可关联。

## 11. D11.3-B 电路约束清单（可直接据此实现）

电路输入沿用式 (4)(5)。D11.3-B 需在 D11.2 的 32 位预算电路基础上增加：

1. **uint32 范围约束**：`Q`、`u_old`、`u_new`、`c`、`s = Q − u_new` **五个值全部**做 32 位 bit 分解 + boolean 约束；`Q ≥ 1`、`c ≥ 1` 另加非零约束（沿用 D11.2 的 `x·x⁻¹=1`）。注意 `Q` 也必须做范围约束，仅有非零约束不足以排除越界值。
2. **预算状态承接（两条独立等式，不可合并为一条）**：
   - `u_old + c − u_new = 0`：保证 `C_new` 承诺的 `u_new` 正确承接旧状态与本次消费。
   - `u_new + s − Q = 0`：配合 `s ≥ 0` 保证新状态未超配额。

   两者都是域等式；无回绕论证见 §5.2 约束一（两个 uint32 之和最大 `2³³−2 ≪ |Fp|`，叠加 `u_new`/`s` 的 32 位范围约束后与整数语义等价）。**不得**用单条 `u_old + c + s − Q = 0` 代替——它没有约束 `u_new`，会让 `C_new` 打开为任意值（§5.2 的 `10+5+85=100`、`u_new=90` 反例）。
3. **旧状态承诺开口**：在电路内计算 `Poseidon(D_state, budget_id, period_id, Q, u_old, r_old, K)`，约束等于公开 `C_old`。
4. **新状态承诺开口**：同样计算 `Poseidon(D_state, budget_id, period_id, Q, u_new, r_new, K)`，约束等于公开 `C_new`。
5. **密钥承诺一致性**：两次 Poseidon 使用同一 `K = Poseidon(D_key, nf_secret, budget_id, period_id)`，约束同一 `nf_secret` 贯穿旧新状态（防换密钥）。
6. **Nullifier 派生**：约束 `N = Poseidon(D_nf, nf_secret, budget_id, period_id, C_old)` 等于公开 `N`。
7. **公开输入绑定**：`budget_id`、`period_id`、`Q`、`c`、`C_old`、`C_new`、`N`、`P` 均作为 instance（沿用 D11.2 证明绑定公开输入的验证结论）；`u_old`、`u_new`、`s`、`r_old`、`r_new`、`nf_secret` 仅作 witness，不进 instance。`P` 虽在 instance 中，但按第 8 条由 Coordinator 比较，电路内不对其施加密码学约束。
8. **策略绑定（方案 B：Coordinator 绑定）**：电路内**不**对 `P` 加约束；Coordinator 在验证流程步骤 5 检查 `proof.public_inputs.P == registered_policy[(budget_id, period_id)]`（§5.2 约束五、§7.2）。不宣称状态承诺绑定了 `P`。
9. **测试基准**：沿用 D11.1/D11.2 数值语义；新增 **`u_new ≠ u_old + c` 的状态承接攻击负例**（§5.2 的 `u_old=10,c=5,s=85,Q=100,u_new=90`）、换密钥攻击、`C_old` 不匹配、跨实例/周期 Nullifier 复用等负例。

> 实现顺序建议：第 1 条的 32 位 bit 分解组件可沿用 D11.2；但第 2 条**必须按两条独立等式重新实现**，D11.2 的单条 `u+c+s=Q` 不满足状态承接要求。之后按 3–4（承诺开口）→ 6（Nullifier）→ 5、7、8（绑定一致性）推进。Poseidon 参数与编码须先按 §6.4 冻结。
