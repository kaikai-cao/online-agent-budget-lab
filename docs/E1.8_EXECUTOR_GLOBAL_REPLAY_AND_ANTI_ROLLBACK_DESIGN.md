# E1.8：Executor 全局防重放与状态抗回滚设计

> 阶段性质：**纯设计论证，不修改生产实现。**
> 本文档提出并论证一个待审查的逻辑架构，不是已冻结的实现方案，也不是安全证明。
> 基线：`main` @ `91f870e`（E1.7 已复核通过并封存）。

---

## 1. 研究目标与 E1.7 实测依据

### 1.1 两个独立的安全目标

本阶段针对 E1.7 实测暴露的两个边界，分别给出可验证机制。**两个目标都必须先把“能保证什么”精确分层，不得把较弱保证写成较强保证：**

- **G1 跨实例唯一执行**，分两层：
  - **G1a 唯一有效执行权**：Authority 保证同一 `operation_id` 在任一时刻至多一个**当前有效执行权持有者**（有单调 fencing token 与原子裁决证据）。这一层 A2 可以提供。
  - **G1b 唯一实际 dispatch**：被保护的执行资源**至多被真实 dispatch 一次**。这一层**不能仅靠 Executor 本地检查 token 得到**（存在 §5.3、§6 的 TOCTOU 窗口），**也不能仅靠 A1 的 SQLite 共享事务得到**（dispatch 与 commit 非原子，崩溃窗口下可二次 dispatch，T03 实测）；必须另加“执行资源原子校验并拒绝旧 token”或“原子消费不可重放执行许可（消费后不可因租期到期/崩溃回滚重新发放）”。见 §5.3。
  - **G1a 成立不蕴含 G1b**。仅采用 A2 而无执行资源侧协同时，只能声称 G1a，不能写成“至多一个真实 dispatch”。
- **G2 状态抗回滚**：Executor 恢复旧数据库快照后，系统能检测状态分歧，并给出恢复或失败关闭的确定行为；必须区分“状态落后”与“状态分歧/回滚疑似”（§4.2、§7.4）。

**这两个目标必须分别论证、分别测试，不得互相替代。** 它们可以共享同一个可信服务，但“存在唯一执行机制”不蕴含“已抗回滚”，反之亦然；“唯一执行权”也不蕴含“唯一实际执行”。典型反例：一个只维护“当前 operation_id 是否已执行”的权威库能解决 G1a，却无法发现本地库被整体换回旧快照（G2），也无法阻止旧持权者在检查后暂停再恢复所导致的双 dispatch（G1b）；一个只维护外部单调计数的方案能发现本地版本倒退（G2），却无法决定两个并发申请者谁有权执行（G1a）。

### 1.2 E1.7 实测依据

E1.7 在真链路（真 D10 + 真 Rust `e1_service` + 真 Halo2）产出的 `PendingExecution` 上实测（`tests/test_e1_executor_state_scope.py`，结果见 `tests/E1_7_EXECUTOR_IDEMPOTENCY_BOUNDARY.md`）：

| 实验 | 实测结果 | 暴露的边界 |
| --- | --- | --- |
| T01 共享库双实例（同进程两线程） | dispatch = 1，回执逐字节一致 | 单库内 `BEGIN IMMEDIATE` 可串行化（G1 的局部解） |
| T02 独立库双实例（同身份/密钥） | dispatch = 2，两份回执均有效且相同 | 无跨 Executor 状态 → G1 不成立 |
| T03 真实 SQLite 文件回滚后重试 | dispatch = 2，回执与库均无法显示第二次执行 | 无外部单调锚点 → G2 不成立 |

T03 尤其关键：它**不是 mock 查询，而是真实恢复 SQLite 文件**；`execute_e1()` 的四道凭据门禁在回滚后仍全部通过，第二次 dispatch 才发生。这证明当前凭据体系只回答“本次调用是否获授权”，不回答“该操作历史上是否执行过”。

### 1.3 研究方向定位

真正值得研究的不是“再加一层签名”，而是：

> 如何把**密码学授权**（E1.5 四门禁）、**全局执行唯一性**（G1）与**可验证的持久化状态**（G2）三者联系起来，使 Agent 的工具执行具有可审计、可恢复、可检测回滚的可信执行语义。

这自然衔接已有的 Ed25519 授权、Halo2 状态承诺与 Agent 执行可信性工程，比单纯增加一个防重放字段更接近一个有研究价值的问题。

## 2. 攻击者能力、信任假设与明确排除项

### 2.1 攻击者能力（沿用并扩展 E0 §8.1）

假设攻击者：

- 控制 Planner/Prover，可构造任意见证、重放旧证明与旧凭据；
- 能让多个持有**相同 Executor 身份与私钥**的实例处理同一 `operation_id`（配置错误、进程克隆、密钥复制，E1.7 T02 前提）;
- 能对 Executor 的 SQLite 文件做文件层快照/恢复（E1.7 T03 前提）；
- 能使网络分区、延迟、重复投递，或使某个实例在任意指令处崩溃；
- 能重放旧的 `execution_right`、fencing token 与日志条目。

### 2.2 信任假设（必须显式，不得夸大）

- **沿用 E0 §8.2**：Issuer、D10/D11 Coordinator、可信 Executor 的计量签名与工具执行可信；Planner/Prover 不可信；承诺绑定性、Ed25519、底层 SQLite 事务原子性与持久性正确。
- **E1.8 新增的信任组件（若实施需 E0 级冻结扩充 TCB）**：存在一个 Execution Authority 与 Append-only Journal，其（a）按 `operation_id` 原子裁决唯一执行权；（b）签发严格单调递增的 fencing token 与日志序号；（c）追加写不可被攻击者回滚或篡改；（d）其签名密钥安全。
- **日志/权威服务自身的回滚不在本层自动解决**：若该服务整体丢失或被回滚，则在本设计内**没有更上层的独立锚点**（详见 §8 与 §10）。可通过复制（共识）、外部水印服务把信任下移一层，但无法消除“信任根”，只能改变其位置。

### 2.3 明确排除项（本阶段不做）

- 不写任何 Python/Rust 生产代码；不引入 Redis/PostgreSQL/区块链/TPM 依赖。
- 不修改 E0/E1.0–E1.7 冻结文件、凭据格式、签名字段与 E1.5 四道门禁。
- 不宣称已实现全局 exactly-once；不把设计论证当作安全证明。
- 不解决任意外部 API 的副作用 exactly-once（见 §3.3、§8）；不在本阶段做密钥轮换。

## 3. 跨实例唯一执行（G1）方案比较

### 3.1 A1 — 共享权威执行库

- **原理**：所有 Executor 指向同一个权威 SQLite 库，按 `operation_id` 主键原子查重并落结果（可复用 E1.7 T01 已验证的 `BEGIN IMMEDIATE` 语义）。
- **优点**：改动最小；T01 已实测同库双实例在**并发**下 dispatch=1，适合当前单机原型。
- **代价与局限**：依赖权威库可用；两个实例必须真共享同一文件/路径；**不能自动解决 G2**（本地库整体回滚仍不可见，除非权威库本身即被所有实例视为唯一真相源且不可回滚）；跨主机不成立。
- **不能单独保证 G1b（崩溃窗口）**：`BEGIN IMMEDIATE` 只串行化“并发查重与状态更新”，**dispatch 不是 SQLite 操作，与 commit 不在同一原子边界内**。若 `registry.dispatch()` 已发生而进程在 commit 前崩溃，事务回滚使执行记录消失，重试会对同一 `operation_id` 再次 dispatch。T01 只证明并发串行化，T03 已实测恢复旧快照后 dispatch 由 1 增至 2——都**不能**据此声称崩溃恢复下“至多一次真实 dispatch”。要 G1b 须额外引入 §5.3 的原子许可消费或执行资源侧原子 fencing，A1 事务本身不够。

### 3.2 A2 — 独立 Execution Authority 服务

- **原理**：Executor 不自行决定是否执行，向独立服务申请执行权；服务维护全局唯一操作记录与状态机，返回带 fencing token 的执行权。
- **优点**：可集中裁决多实例竞争；执行权、状态、序号统一；便于审计与恢复；是 A1 的自然泛化（A1 可视为 Authority 与库同进程共置的特例）。
- **代价与局限**：新增可信服务与网络依赖；服务端故障恢复复杂；服务自身成为 G1 的信任根（§2.2）。

### 3.3 A3 — 工具端幂等键

- **原理**：把全局唯一的 `operation_id`（或由其派生的幂等键）传给工具服务，由工具端保证相同键不重复产生外部副作用。
- **优点**：**唯一能覆盖“有外部副作用工具”的方案**；把 exactly-once 的正确位置放在真正产生副作用的资源处。
- **代价与局限**：要求下游工具支持并正确实现幂等；无法假设所有 API 支持；**必须在工具接口层改动，超出 E1.5 当前确定性本地工具边界**。
- **理论边界（不可忽略）**：若工具已产生外部副作用、但 Executor 在记录结果前崩溃，则无论本地库还是远程协调服务都**无法判断工具是否真的完成**。没有工具端幂等或事务协作，就不能对任意外部工具承诺 exactly-once。A1/A2 都跨不过这道坎。

**阶段倾向**：当前确定性本地工具实验用 A1 作为最小方案；将来多执行节点优先研究 A2；凡工具具不可逆外部副作用，必须进一步引入 A3。

## 4. 状态抗回滚（G2）方案比较

### 4.1 B1 — 远程单调计数器

- **原理**：每次状态推进递增外部计数，Executor 保存对应版本；本地版本小于远程则判定倒退。
- **优点**：实现简单；能检测本地版本变小。
- **局限**：计数器只能“发现版本低”，**不能恢复丢失的执行记录**，也不回答“哪些操作已被接受/执行/缺失”；无法区分“真回滚”与“消息延迟导致的短暂落后”；与 G1 无关。

### 4.2 B2 — 远程追加式执行日志（推荐研究）

- **原理**：将执行意图、完成结果、连续序号、前序摘要与签名检查点写入独立可信日志，形成可验证的连续检查点链。
- **优点**：不仅发现版本异常，还能回答 §4 引言的四个恢复问题——哪些操作被接受、哪些已执行、本地缺哪些记录、恢复后能否重新 dispatch；日志可作审计与恢复依据。
- **局限**：日志服务需可靠持久化与认证；日志本身若被回滚/丢失则失去锚点（§2.2、§8）。
- **必须区分三种状态（详见 §7.4）**：若 Journal 是全局共享日志，别的 Executor 正常追加就会使本地 `last_applied_seq` 小于全局 head——这是**状态落后**，不是回滚。B2 的判定必须基于“同一序号处的检查点摘要是否一致”（状态分歧），而非单纯序号大小；仅序号差异只能判“落后”或“回滚疑似”，不能证明发生了回滚。

### 4.3 B3 — TPM/HSM 单调锚点

- **原理**：用硬件保护的单调计数器或受保护状态，为本机状态回滚提供检测能力。
- **优点**：对本机文件层回滚提供强检测，不依赖网络服务在线。
- **局限**：硬件依赖与部署成本；状态迁移/设备更换复杂；**不覆盖跨实例 G1**，也不解决日志/服务端回滚；不适合当前 MVP 直接引入。

**阶段倾向**：B2。理由：目标是“可验证、可恢复、可审计”，B1 只有检测无恢复，B3 是部署增强而非当前 MVP 所需；B2 的信息完备度最高，且与 G1 的 Authority 可共置。

## 5. 推荐组合架构与关键数据结构

### 5.1 逻辑架构（待论证，非已冻结实现）

```
Agent / Runtime
    │  提交经 E1.5 四门禁验证的 PendingExecution
    ▼
Execution Authority ─────────────┐
    │  跨实例唯一性 · operation_id 唯一约束        │ 共享可信服务，
    │  执行权裁决 · fencing token 签发             │ 但两个不变量分别测试
    ▼                            │
Append-only Journal ◄────────────┘
    │  执行意图 · 执行结果 · 连续序号 · 前序摘要 · 签名检查点
    ▼
Trusted Executor
    │  执行前核验 · 工具 dispatch · Execution Receipt（格式不变）
```

两个独立不变量（**即使共置也必须分别测试**）：

1. `operation_id` 在权威执行状态中只能被**接受一次**（G1）。
2. 本地执行状态必须与外部可信日志中**其自身序号对应的历史检查点一致**；若仅落后于 head 但摘要一致，是正常落后需补齐，不是回滚；若相同序号处摘要不一致，是状态分歧（G2，见 §7.4）。

### 5.2 关键数据结构（逻辑视图，非冻结格式）

- **`ExecutionRight`（执行权）**：`operation_id`、`executor_id`、`fencing_token`、`granted_at`、`epoch`/租期到期、`authority_signature`。语义：在租期内，仅持此权且 token 为当前最大者可 dispatch 该操作。
- **`JournalEntry`（日志条目）**：`seq`、`prev_digest`、`operation_id`、`phase ∈ {INTENT, RESULT}`、`payload_digest`、`executor_id`、`fencing_token`、`entry_signature`，以及恢复所需的 `result_ref` / `receipt_ref`（见下）。语义：`seq` 连续无缺号；`prev_digest` 链接前序；INTENT 先于 RESULT。
  - **序列作用域**：本设计采用**全局单一序列**（所有 Executor 共用一条 `seq`），因此其他 Executor 的追加会推进 head 而不改变本地已应用条目——这是“状态落后”的来源，判定规则见 §7.4。若改为按 `executor_id`/分区维护独立序列，则跨实例的全局单调锚点消失，G2 需另设全局检查点，不在本方案范围内。
  - **`payload_digest` 的承诺对象（规范化 RESULT envelope）**：`payload_digest` 必须对**完整的规范化 RESULT envelope** 计算摘要，而不是仅对工具原始结果摘要，否则会出现“两个引用（`result_ref`/`receipt_ref`）+ 一个摘要”的解释歧义。规范化 envelope 定义为：

    ```
    RESULT envelope = {
        operation_id:      <原操作 ID>,
        binding_digest:    <E1.5 工具调用绑定摘要>,
        result:            <原始工具结果对象，含成功值或 error>,
        execution_receipt: <原始签发的 Execution Receipt 完整对象，含 signature_b64>
    }
    payload_digest = canonical_digest("e1-result-envelope-v1", RESULT envelope)
    ```

    `result_ref` 定位 envelope 中的 `result`，`receipt_ref` 定位 envelope 中的 `execution_receipt`（二者是同一 envelope 内的分段引用，不是各自独立的摘要根）。恢复时必须：按两引用取回原始对象 → 重组 RESULT envelope → **重算 `payload_digest` 并与日志条目比对**（保证 envelope 完整未被替换）→ 再独立验证原始回执签名与绑定（见下）。域标签 `e1-result-envelope-v1` 属本设计新增，若进入 E1.9 需另行冻结，不改变 E1.1–E1.6 已冻结的域前缀。
- **`Checkpoint`（检查点）**：`seq`、`journal_head_digest`、`checkpoint_signature`。语义：权威服务对序号 `seq` 处日志前缀的签名承诺。检查点是**带序号的历史快照**：本地应保存并比对“自身 `last_applied_seq` 对应的那个历史检查点摘要”，而不是无条件与最新 head 摘要比较（后者在正常落后时会误判）。
- **`LocalExecutionState`（本地状态）**：`operation_id → status`、`last_applied_seq`、`last_checkpoint_digest`（=本地已应用序号处的**历史**检查点摘要）。语义：本地已应用到哪个日志序号与检查点。

**恢复数据完整性（RESULT 与 Receipt 必须可恢复）。** 仅保存 `payload_digest` 无法从日志还原原始工具结果或 Execution Receipt，因此 §7.3–7.5 承诺的“从 RESULT 恢复回执、不重建新回执”必须有明确数据来源。建议二选一（本文档不选定实现，但要求明确其存在与绑定）：

1. **完整载荷入日志**：`RESULT` 条目直接携带原始工具 `result`、`error`、以及**原始签发的 Execution Receipt 完整对象**（含其 `signature_b64`），由 `entry_signature` 对整条背书。恢复时直接取用原始回执对象，不重新签发。
2. **内容寻址存储引用**：日志只存 `result_ref` / `receipt_ref`（如 `sha256:...` 内容寻址键），原始对象存放于权威可验证存储；恢复时按引用取回，并用日志中 `payload_digest` 校验一致性。

无论哪种方式，恢复时必须校验下列绑定，全部通过才接受（缺一不可）：

- 按 `result_ref`/`receipt_ref` 取回原始 `result` 与原始回执，连同 `operation_id`、`binding_digest` 重组 RESULT envelope，**重算 `canonical_digest("e1-result-envelope-v1", envelope)` == 对应 `JournalEntry.payload_digest`**（envelope 完整、未被替换）；
- 该 `JournalEntry` 的 `operation_id` == 原 `operation_id`；
- 原始回执的 `binding_digest` / `budget_receipt_digest` / `executor_authorization_digest` 与 E1.5 已验的 binding、Budget Receipt、授权一致（复用 E1.5 验签逻辑，不另造摘要）；
- 原始 Execution Receipt 的**签名仍可验证**，且验证公钥为该 `executor_id` 的可信公钥。

**“恢复而非重建”硬规则**：恢复路径只允许返回日志/权威存储中**原始签发的回执对象**（或其经摘要校验的内容寻址副本），**不得**用恢复出的字段重新调用 `make_receipt` 生成一份新回执。原因：重新签发会因时间/字段差异产生与原件不同的签名字节，破坏“返回与首次执行逐字节一致的回执”这一 E1.6/E1.7 已验证语义。若原始回执确实不可恢复（引用失效、存储丢失），则 fail-closed，不允许以“重建回执”代替。

### 5.3 与 dispatch 边界的关系（关键）

E1.5 的 `_DispatchCapability` 是**进程内一次性令牌**（防同进程绕过），E1.8 的执行权是**跨实例、外部可验证的授权**。二者正交：

- 四道凭据门禁仍是 dispatch 的**授权前置条件**，保持不变；
- E1.8 在“门禁通过之后、`registry.dispatch()` 之前”插入两个正交检查：①持有当前有效执行权（G1a）；②本地 `last_applied_seq` 处的历史检查点摘要与权威日志该序号处一致（G2，避免把正常落后误判为回滚）；
- 本文档不改变 `Execution Receipt` 的字段与签名字段。若将来希望把 fencing token / 日志序号写入回执以增强可审计性，那是**独立的协议扩展，需另行冻结**，不在本阶段假定。

**TOCTOU 窗口（必须显式承认，这是 G1a ≠ G1b 的根因）。** 仅在 Executor 本地“检查 token 有效 → 执行 dispatch”存在时间差：

```
Executor A: 检查 token=t 有效 ──A 在此暂停────────────────▶ dispatch (t 已过期仍执行)
Authority :               租期到期 → 发放 token=t+1 给 B
Executor B:                                检查 token=t+1 有效 ──▶ dispatch
结果：两次真实 dispatch，尽管 token 检查在各自时刻都"通过"
```

本地检查只约束**在检查时刻 token 是否为当前最大**，无法约束**检查之后到 dispatch 之前**租期是否已被别人接管。因此：

- **仅 A2（租期 + 本地 token 检查）只能保证 G1a（唯一有效执行权）**，不能保证 G1b（至多一次真实 dispatch）。
- 要保留 G1b，必须二选一：①**执行资源侧原子 fencing**——被保护资源在真正产生副作用的同一原子操作内校验并拒绝低于当前最大的 token（要求资源提供该校验能力并持久化“已见过的最大 token”）；或 ②**原子消费不可重放执行许可**——在 dispatch 前由权威组件原子地将该 `operation_id` 的许可标记为“已消费”，且该消费**不可因租期到期或崩溃回滚而重新发放**，使至多一次尝试成为可能。注意 ② 的代价：一旦许可被消费而进程在 dispatch 前崩溃，将**不会自动重试**（可能零次执行），这是“至多一次”换取“不重复”的必然结果，不能同时承诺自动恢复重试。

**A1 共享事务的边界（必须写清，不能声称 G1b）。** `registry.dispatch()` 不是 SQLite 操作，`BEGIN IMMEDIATE` 包住“查重 + dispatch + 落记录”并不意味着 dispatch 与 commit 是一个原子操作：

```
BEGIN IMMEDIATE; 查重通过
  ──▶ registry.dispatch()      # 工具已真实执行
  ──▶ 进程崩溃                  # SQLite 尚未 commit
  ──▶ 事务回滚，执行记录消失
  ──▶ 重试同一 operation_id
  ──▶ registry.dispatch()      # 第二次真实 dispatch
```

E1.7 T03 已实测“恢复旧 SQLite 快照后 dispatch 由 1 增至 2”，正是这一窗口的真实表现（恢复旧快照等价于让已消费的记录连同事务一起消失）；T01 的同库并发 dispatch=1 只证明**并发事务串行化**，不证明崩溃恢复下至多一次 dispatch。因此：

- **A1 只能保证并发查重与状态更新的串行化（G1a 的存储层形态），不能单独保证崩溃窗口下的 G1b**；当前确定性本地工具的 A1 受限实现也**不声称 G1b**（重复 dispatch 仅是多算一次无外部副作用的本地调用，见 §7.5）。
- 多主机下 A1 的共享库前提本身不成立，更不得把单机同库结论外推为分布式 G1b。
- 对有外部副作用的工具，即便权威裁决了执行权，工具侧仍未校验 token 时仍可能由旧持权者产生副作用；此处仍需 §7.5 的 A3 幂等键兜底。

## 6. 关键字段语义

- **`operation_id`**：工具调用的全局唯一身份。E0/E1.5 已把它绑定到 binding、Budget Receipt 与 Transition Receipt；E1.8 沿用同一标识作为权威执行状态的主键，不引入第二套操作身份，避免跨层映射歧义。
- **执行权（execution right）**：Authority 授予某一 executor 对某一 `operation_id` 的临时独占 dispatch 许可。同一 `operation_id` 在任一时刻至多一个有效执行权（G1a）；租期到期或更新 token 后旧权在**协议语义上**失效——但“语义失效”不等于“旧实例已停止”，旧持权者可能仍在运行（见 §5.3 TOCTOU）。
- **fencing token**：Authority 签发的严格单调递增整数，随每次新执行权递增。作用：判定“持权者是否为当前最新”。**有效性有严格边界（见 §5.3、§8）**：只有当被保护的资源在**产生副作用的同一原子操作内**校验并拒绝更低 token 时，fencing 才能阻止旧持权者产生真实副作用；仅在 Executor 本地检查，既挡不住检查后租期被接管的 TOCTOU 双 dispatch（G1b），也挡不住已失权但仍在运行、对 token 无关资源操作的旧实例。
- **日志序号（log seq）**：追加日志中连续无缺号的**全局单调序号**，是外部单调锚点。本地 `last_applied_seq` 小于 head **仅表明本地可能落后**（别的 Executor 追加也会造成），**不能直接判为回滚**；判定需结合同序号处摘要比对（§7.4）。
- **检查点（checkpoint）**：Authority 对某一 `seq` 处日志前缀的签名承诺，是**按序号索引的历史快照**。本地用 `last_applied_seq` 去取权威日志**该序号**的检查点摘要，与本地 `last_checkpoint_digest` 比对：一致则最多是正常落后（可补齐），不一致才是状态分歧（回滚疑似）。不得无条件与最新 head 摘要比较，否则正常落后会被误判为回滚。

## 7. 状态机

### 7.1 正常执行（无故障）

```
UNCLAIMED
  ──申请执行权(operation_id)──▶ CLAIMED(fencing_token=t, 本地 seq=k)
  ──门禁四验 + 执行权/检查点核验──▶ PREPARED
  ──写 INTENT(seq=k+1)──▶ INTENTED
  ──registry.dispatch()──▶ DISPATCHED
  ──生成并签名原始 Execution Receipt（E1.5 _dispatch_and_seal / make_receipt，tool 执行后）──▶ SEALED
  ──写 RESULT(seq=k+2)（envelope 含原始 result + 原始 Receipt）+ 新检查点──▶ COMMITTED
  ──本地落库 / 返回原始 Receipt 原件──▶ DONE
```

每一步的落库顺序遵循 E1.0 Saga：**日志/权威状态先推进，本地后推进**；预算扣减仍在 dispatch 之前，不退款语义不变。

**RESULT 与原始 Receipt 的生成顺序（不可颠倒）**：与 E1.5 实现对齐，`Execution Receipt` 由 `_dispatch_and_seal()` 在**工具 dispatch 之后**通过 `make_receipt()` 生成并签名；因此必须严格按 `dispatch → 生成签名 Receipt → 写 RESULT（envelope 含原始 result + 原始 Receipt）→ 本地落库/返回原件` 的顺序。**写 RESULT 时原始 Receipt 必须已经生成并签名**，否则 §7.3 中“RESULT 后、本地落库前”与“本地落库后、回执返回前”两行的“恢复留存回执”无法成立。恢复一律取回**原始回执对象**并校验 §5.2 的 envelope 摘要、签名与字段绑定，禁止用恢复字段重新 `make_receipt`。

### 7.2 并发竞争（两实例申请同一 operation_id）

```
Authority 收到 (op, ex_A) 与 (op, ex_B)（近似同时）
  ──原子主键裁决──▶ 仅一个获得执行权，token=t+1；另一个返回 ALREADY_CLAIMED
  ──败者：fail-closed，不 dispatch，按 get_operation 语义查询已有结果
```

与 T02 的差别：T02 中“谁执行”没有任何裁决者；此处由 Authority 唯一裁决。但注意：**原子裁决只闭合了“申请时的唯一执行权”（G1a），没有闭合 §5.3 的 TOCTOU 窗口（G1b）**——胜者若在检查 token 后暂停、租期被接管，仍可能双 dispatch。要声称 G1b，需在裁决/执行资源侧加入原子 fencing 或原子消费不可重放执行许可（见 §5.3）；**A1 的共享 SQLite 事务不是后者**，只给并发串行化。**仍需分别测试 G1a、G1b 与 G2**，即使由同一服务提供。

### 7.3 崩溃恢复（按崩溃位置）

| 崩溃位置 | 日志/权威可见状态 | 恢复动作 |
| --- | --- | --- |
| 获得执行权后、INTENT 前 | 有执行权，无 INTENT | 租期到期后释放；原权在**协议语义上**失效，允许重新申请（新 token）。**旧实例可能仍在运行**（§5.3），仅在旧实例遵守协议并重新校验 token 时才会退出；否则需执行资源侧 fencing 才能阻止其 dispatch（G1b） |
| INTENT 后、dispatch 前 | 有 INTENT，无 RESULT | 重放：持原执行权且 token 仍为当前最大者的实例继续 dispatch；否则重新裁决 |
| **dispatch 后、RESULT 前**（含 Receipt 生成前/后两个子窗口） | 有 INTENT，无 RESULT，**副作用状态未知**；Receipt 可能尚未生成 | 见 §7.5 崩溃窗口。若 Receipt 已生成但未写 RESULT，属“已签名未入日志”，按 §7.5 处理，不把未入日志的回执当恢复依据 |
| RESULT 后、本地落库前 | 有 RESULT 与新检查点，envelope 含原始 result + 原始 Receipt | 按日志补齐本地状态，按 `receipt_ref` 取回原始回执并重算 envelope 摘要 + 验签（§5.2），不重复 dispatch、不重建回执 |
| 本地落库后、回执返回前 | 全流程 COMMITTED | 查询恢复原始回执原件（同 E1.6 kill-after-commit），不重建 |

### 7.4 状态落后、状态分歧与回滚判定（G2）

**Journal 是全局单一序列**（§5.2），因此“本地序号小于 head”有三种成因，必须分开处理，不能一律叫回滚：

| 判定 | 条件 | 含义 | 处理 |
| --- | --- | --- | --- |
| **LOCAL_STATE_BEHIND** | `last_applied_seq < head.seq`，且本地在 `last_applied_seq` 处的 `checkpoint_digest` == 权威日志同序号历史检查点摘要 | 别的 Executor 正常追加导致本地落后；本地已应用前缀仍可信 | 按日志从 `last_applied_seq+1` 补齐，补齐期间不 dispatch；**不判回滚** |
| **LOCAL_STATE_DIVERGED** | 本地在 `last_applied_seq` 处的 `checkpoint_digest` != 权威日志同序号历史检查点摘要 | 相同序号内容被替换/分叉，状态不可信 | fail-closed，进入恢复流程；**这是可判定的异常** |
| **ROLLBACK_SUSPECTED** | 本地状态与某个更早历史检查点一致、且与当前应处状态不符，但缺少能直接证明“攻击者做了回滚”的外部证据 | 有回滚迹象，但仅凭版本差异**不能证明**发生了回滚 | 按状态分歧处理（fail-closed + 补齐），**表述为“疑似”而非“已确认回滚”** |

判定要点：

1. **比较对象**：本地 `last_applied_seq` 处的历史检查点摘要 vs 权威日志**同一序号**处的历史检查点摘要——不是 vs 最新 head 摘要。这样正常落后（前缀未变）与回滚/分叉（前缀被改）可区分。
2. **同步/补齐**：`LOCAL_STATE_BEHIND` 时，按顺序回放 `last_applied_seq+1 … head.seq` 的 INTENT/RESULT 条目到本地，逐条校验 `prev_digest` 链与检查点，补齐期间禁止 dispatch。
3. **证据门槛**：只有“同序号摘要不一致”（DIVERGED）才是可直接判定的状态异常；“序号变小”本身只支持 BEHIND 或 SUSPECTED，不足以声称攻击者执行了回滚（这也符合 E1.7 复核把 T03 表述为“回滚边界被具体验证到 ExecutionStore”而非形式化证明的口径）。
4. **远程日志自身回滚**时本地无更上层独立锚点，无法检测（§2.2、§8），该限制保留。

补齐边界：若被回滚/落后的本地记录对应日志中的 RESULT，补齐后应**恢复原始留存回执**（见 §7.5、§5.2 的 `receipt_ref`）而非重新 dispatch；若只到 INTENT，则按 §7.3 的窗口规则处理。

### 7.5 工具执行与执行记录之间的崩溃窗口（核心）

这是必须显式承认的难题：**工具已dispatch并可能产生副作用，但 RESULT 尚未持久化**。

- **确定性本地无副作用工具（当前 E1.7/E1.6 范围）**：重复 dispatch 不产生外部损害（同样输入得同样结果），因此“INTENT 先落 + 崩溃后按 INTENT 重放”即可；T01/T03 的重复 dispatch 在此范围内只是“多算一次本地调用”，不是外部 double-spend。但对本设计仍应通过权威状态裁决避免，以满足 G1 的可验证性；恢复时若日志已有 RESULT，按 §5.2 取回**原始回执**而非重新执行工具或重新签发回执。
- **有外部副作用的工具**：Executor 崩溃后无法仅凭本地库或日志判断工具是否完成。**必须由工具端幂等键（A3）兜底**：把 `operation_id`/派生幂等键随调用传入，使工具端对重复调用返回同一结果而不重复副作用。没有 A3 时，本设计**不承诺**此类工具的 exactly-once。

## 8. 故障矩阵与 fail-closed 规则

| 场景 | 状态迁移 / 处理策略 | 是否 fail-closed |
| --- | --- | --- |
| 两 Executor 同时申请同一操作 | Authority 原子裁决唯一胜者（新 token），败者 ALREADY_CLAIMED 不 dispatch | 是（败者） |
| 获得执行权后进程崩溃 | 租期到期释放；旧 token 在协议语义上失效，重新申请取新 token；旧实例可能仍在运行（G1a/G1b 区别见 §5.3） | 协议内是；G1b 需额外机制 |
| 工具执行后、回执落库前崩溃 | 若 RESULT 已写：按 `receipt_ref` 取回原始回执、重算 envelope 摘要 + 验签 + 字段绑定（§5.2），禁止重建；若尚未写 RESULT：本地工具按 INTENT 重放（无外部损害）；外部工具需 A3 幂等键，缺失则拒绝宣称 exactly-once | 部分（外部工具无法承诺） |
| 远程服务暂时不可用 | 无法申请执行权/核验检查点 → 拒绝 dispatch，等待恢复或走查询恢复路径 | 是（一律 fail-closed） |
| 本地数据库恢复旧快照 | 取本地 `last_applied_seq` 处历史检查点与权威同序号摘要比对：摘要不一致 → LOCAL_STATE_DIVERGED（fail-closed + 恢复）；仅序号小且摘要一致 → LOCAL_STATE_BEHIND（补齐）；证据不足时记 ROLLBACK_SUSPECTED，不声称已确认回滚（§7.4） | 分歧时是；落后时补齐 |
| 日志已推进、本地未推进（别的 Executor 追加） | LOCAL_STATE_BEHIND：按序回放 INTENT/RESULT 补齐，逐条校 `prev_digest`，补齐期间不 dispatch；补齐后恢复原回执 | 补齐，不 fail-closed |
| 远程日志本身丢失或回滚 | 本设计内无独立锚点 → **不能保证检测**，fail-closed 停止 dispatch 并报警；需复制/外部水印把信任下移一层 | 是（检测不了就停） |
| 旧 Executor 持有过期执行权 | 遵守协议的实例在 dispatch 前重校 token，过期即退出（G1a）；但检查后租期被接管的 TOCTOU 窗口本地校验挡不住（§5.3），需执行资源侧原子 fencing 或原子消费不可重放许可才能保 G1b（A1 共享事务不算） | 协议内是；G1b 需额外机制 |
| 工具端不检查 fencing token | 旧持权者仍可对该 token 无关资源产生副作用 → **fencing 无法阻止** | 否（见下） |

**fencing token 的实际有效边界（必须写清）**：token 只在“被保护方在**产生副作用的同一原子操作内**校验并拒绝更低 token”时有效。分三类情况：

1. **遵守协议、且在检查后到 dispatch 前租期未被接管**：本地重校 token 可阻止旧权继续使用（G1a 范围内有效）。
2. **检查后租期被接管的 TOCTOU 窗口（§5.3）**：本地检查时刻 token 有效，但 dispatch 时已过期 → 本地校验**挡不住**双 dispatch（G1b 不成立）；只有执行资源侧原子 fencing 或原子消费不可重放执行许可能覆盖（A1 共享事务不算，见 §5.3 崩溃时序）。

3. **已失权但仍在运行、对 token 无关资源操作的实例**：若下游工具不校验 token，fencing **不能**阻止其副作用。

因此 fencing 不是独立的“唯一实际 dispatch”机制，也不是外部副作用防重放机制；要得到 G1b 或对有副作用工具成立，必须与执行资源侧原子校验、原子消费不可重放执行许可或 A3（工具端幂等键）配合（§5.3）。

## 9. 与 E0 / E1.0–E1.7 的兼容性

- **E1.5 四道门禁**：不变。E1.8 机制位于门禁通过之后、dispatch 之前，作为正交的外部唯一性与状态一致性检查，不改任何验签逻辑或凭据字段。
- **E0 §2.4**：ExecutionStore 仅限确定性本地工具的边界不变；E1.8 不把它推广为任意网络 API 的 exactly-once。
- **E0 §7.1 / §7.2**：Saga、准入计费、不退款、失败关闭语义不变；预算扣减仍在 dispatch 前；本地工具失败仍产生 FAILED 回执且不退款。
- **E0 §8.2 / §8.3**：不推翻既有信任假设；但新增的 Authority/Journal 是**新的可信组件**，若实施必须按 E0 级流程显式扩充信任假设与 TCB 清单，不能默许引入。
- **D10 / D11 语义与凭据格式**：不改。沿用 `operation_id`、binding、`D_E`、Budget Receipt、Transition Receipt，不引入第二套身份或摘要域。
- **E1.6 / E1.7 冻结测试**：不改、不重跑（本阶段无生产改动）。
- **Execution Receipt**：格式与签名字段不变；fencing/seq 若要入回执属独立协议扩展，需另行冻结。

## 10. 安全保证、不能声称的性质与部署成本

### 10.1 若按推荐方案实施，可声称

- **G1a 唯一有效执行权**：`operation_id` 由 Authority 原子裁决，任一时刻至多一个当前有效执行权持有者（有 fencing token 与裁决证据）——**仅 A2 即可声称这一层**。
- **G1b 至多一次真实 dispatch**：**不能仅凭 A2 声称，也不能仅凭 A1 的 SQLite 共享事务声称**。只有在“执行资源侧原子校验并拒绝旧 token”或“原子消费不可重放执行许可（消费后不可因租期到期/崩溃回滚重新发放，代价是崩溃后可能零次执行、不自动重试）”成立时才可声称（§5.3）。A1 的 `BEGIN IMMEDIATE` 只串行化并发查重与状态更新，dispatch 与 commit 非同一原子操作，崩溃窗口下不保证至多一次 dispatch（T03 实测）；多主机更不成立。
- G2：本地状态被替换/分叉可由“自身序号处历史检查点摘要与权威同序号摘要不一致”（LOCAL_STATE_DIVERGED）检测，并给出确定的恢复或失败关闭行为；**正常落后（BEHIND）与回滚疑似（SUSPECTED）被明确区分**，不把单纯序号差说成已确认回滚。
- 可审计：日志提供“哪些被接受、哪些已执行、缺哪些记录”的可验证序列。
- 可恢复：崩溃/回滚后依据日志与检查点恢复到确定状态，而非猜测；**前提是 RESULT 条目的原始结果与原始回执可恢复**（完整入日志或内容寻址引用有效，§5.2），且恢复的是原始签发回执而非重建回执。

### 10.2 仍不能声称

- “至多一次真实 dispatch”（G1b）——除非上述执行资源侧原子 fencing 或原子消费不可重放执行许可前提成立（§5.3、§10.1）；仅 A2 的租期 + 本地 token 检查只给 G1a，仅 A1 的 SQLite 共享事务只给并发串行化——dispatch 与 commit 非原子，崩溃窗口下可二次 dispatch（T03 实测）。
- 任意外部工具副作用层面的 exactly-once（需 A3，且需工具端配合）；见 §7.5、§8。
- 工具已执行但记录前崩溃时，能凭本机制判断副作用是否发生。
- fencing token 在没有工具端校验时，能阻止旧持权者的外部副作用。
- 在原始 RESULT/回执不可恢复（引用失效或存储丢失）时，仍能返回与首次逐字节一致的回执——此时只能 fail-closed，禁止用字段重建一份新回执充当原件（§5.2）。
- 远程 Authority/Journal 自身被攻陷或回滚时仍有独立锚点（信任根只能移动，不能消除）。
- G1 与 G2 因共置而自动同时成立（必须分别测试）。
- 本设计是形式化安全证明或可直接部署的完整系统。

### 10.3 部署成本

- **A1**：最低（同机共享库），但不解决 G2、不跨主机。
- **A2 + B2（推荐研究组合）**：新增常驻可信服务、日志持久化与认证、fencing token 管理、客户端核验逻辑、服务故障恢复；网络依赖与运维复杂度上升；若要求服务高可用需复制与共识，成本进一步上升。
- **A3**：要求工具接口支持幂等键，属下游生态改动，成本取决于工具方。
- 所有方案均**不改变**现有 Ed25519/Halo2 证明链的计算成本。

## 11. 后续是否进入 E1.9 的决策条件

在冻结审查本设计后，按以下条件决定是否实施 E1.9：

1. **范围确认**：E1.9 是否只面向确定性本地工具（则可只做 A1 + B2 的最小形态，但**只声称 G1a/并发串行化、不声称 G1b**），还是纳入有外部副作用的工具（则必须含 A3 接口约定）。
2. **信任组件可得性**：能否接受新增 Authority/Journal 作为可信组件并按 E0 级流程冻结其信任假设；若否，则 G1/G2 只能停留在“单库 + 文档声明边界”。
3. **G1 保证层级与 fencing 有效性前提**：E1.9 目标是只声称 G1a（唯一有效执行权，仅 A2 即可；A1 只给存储层并发串行化），还是要求 G1b（至多一次真实 dispatch）；若要求 G1b，被保护资源是否愿意在**产生副作用的原子操作内**校验并拒绝低 token，或能否原子消费不可重放执行许可（崩溃后零次执行、不自动重试）。**A1 的 `BEGIN IMMEDIATE` 不是后者**（dispatch 与 commit 非原子，T03 已实测崩溃/回滚下二次 dispatch）。若这些都不可得，则必须把保证降为 G1a，不得写成“至多一次真实 dispatch”。
4. **可验证性验收**：能否为 G1、G2 分别设计独立测试（含进程级并发、真实文件回滚、远程日志回滚注入），并以数据库/日志状态双重确认，而非只看返回值。
5. **恢复语义闭合**：§7 各崩溃窗口是否有确定状态迁移；“dispatch 后、RESULT 前”是否有工具端幂等兜底或明确的不承诺声明；且 RESULT 条目的原始结果/原始回执是否有可验证的恢复来源（§5.2），恢复是否严格取回原始回执而非重建。
6. **不破坏冻结**：能否在完全不改 E1.5 门禁、凭据格式与 E0 Saga 语义的前提下实现。

任一关键条件（1、2、5、6）不满足时，建议不启动 E1.9 实现，而是把相应问题作为开放研究项记录。**本阶段结论仅为设计论证，不构成实施授权。**
