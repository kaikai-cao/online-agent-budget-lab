> **一句话核心结论**：D10 的 `OnlineLeaseGrant.quota_limit` 是 Lease 的**操作次数上限**（当前每次新操作加一单位），D11 的 `Q`/`c` 是 uint32 预算关系中的**加权消费量与配额**，D10 还有第三层**全局预算上限**。这是三种不同的计量维度，不能合并成一个 `Q`。E1 必须采用**双预算（实际是三层）模型**：D10 限操作次数与全局总量，D11 限加权消费量；两者都通过，Executor 才执行工具。

## §1 目标、范围与非目标

### 1.1 目标

冻结 D10 执行链与 D11.3 隐私预算状态机之间的跨层接口设计，使后续 E1 原型能够在这个冻结接口上实现，而不需要再次修改已验收的 D10.4–D10.7 默认行为、D11.3-A 协议、B.1 电路或 C/D 阶段实现。

本阶段要回答的**研究问题**（保持原样，不扩大）：

> 一个经过 D10 精确授权的 Agent 工具调用，能否在不暴露隐藏预算状态的前提下，使用可信 Executor 生成的计量凭据和真实 Halo2 证明，完成一次绑定、可审计、不可重复的预算状态转移？

### 1.2 范围

- 只产出本设计文档 `docs/D11.3_E0_D10_D11_INTEGRATION_DESIGN.md`。
- 明确冻结：身份与额度映射、`c` 的定义、Metering Quote 结构、联合执行顺序、跨层摘要、凭据链、幂等与故障恢复、威胁模型与信任边界、E1 实现边界。
- 所有尚未实现的功能一律标为 **E1** 或**后续工作**。

### 1.3 非目标（本阶段明确不做）

- 不写任何集成代码，不新增 crate、模块或测试。
- 不实现 Executor 真实计量、D10+D11 联合执行、注册知识证明、分布式 Coordinator / 共识 / 高可用。
- 不实现动态资源计量、执行后结算、退款，也不支持任意网络 API 或不可逆外部副作用。
- 不修改 `src/online_budget/`、D9、D10.4–D10.7、D11.3-A/B/C/D 任何现有文件。

### 1.4 关于「固定费用」的研究判断（必须先说清楚）

**固定工具费用不是实际资源计量。** 它不声称测得 CPU 时间、内存、Token 数或任何真实物理资源消耗。第一版把它作为研究原型，只为回答 §1.1 的可验证问题：在授权精确、凭据可验、证明真实、状态不可重复消费这些性质上，跨层绑定能否闭合。动态计量与执行后结算留到后续阶段，本设计不为其预留会削弱上述性质的捷径。

## §2 D10 / D11 现有接口与已验证执行顺序

本节只记录**核查代码后确认的事实**，作为 E1 的事实基线；不在此处提出改动。

### 2.1 D10 现有执行链

概念顺序与代码入口对应如下（`src/online_budget/agent_runtime.py::AgentToolRuntime.run_tool_call`）：

| 概念步骤 | 代码入口 | 作用 |
| --- | --- | --- |
| 1. 固定参数快照 | `snapshot_arguments(arguments)` | 先脱离 Planner 拥有的嵌套对象，得到唯一确定快照 |
| 2. 构造绑定 | `build_tool_call_binding(...)` | 固定工具名、Schema 哈希、参数摘要、操作身份、网关/Coordinator/Lease/Executor 身份 |
| 3. 验证执行授权 | `verify_executor_authorization(...)` | `authorization_required` 策略要求存在授权且为 v2 参数级绑定 |
| 4. 预检 | `executor.prepare_tool_call(...)` | 独立重验授权、Schema 未漂移、实际参数摘要等于绑定摘要 |
| 5. 预算准入 | `gateway_adapter.consume_for_grant(..., request_digest=admission_digest)` | D10 Coordinator 扣一个操作额度，签发签名 Budget Receipt |
| 6. 执行与留存 | `executor.execute(...)` → `ExecutionStore.execute_once(...)` | 重验准入回执，执行本地工具，保存结果与签名 Execution Receipt |

**关键事实**：D10 的预算准入发生在工具执行**之前**；执行失败仍会留下 `FAILED` 回执，预算准入**不自动撤销**。

### 2.2 D10 的计量与摘要字段

- `OnlineLeaseGrant.quota_limit`（`grants.py`）：**每个 Lease 的操作次数上限**，源码注释明确「not a reserved share of G」。
- `global_quota_limit` / `global_used_count`（`coordinator.py::budget_meta`）：**全局预算上限与已用次数**。
- `coordinator.consume(...)` 每次新操作执行 `used_count + 1` 与 `global_used_count + 1`，两个计数都是**次数**，不是加权单位。
- `request_digest` 现状（`agent_runtime.py`）：
  - 无授权时：`admission_digest = binding.binding_digest`；
  - 有授权时：`admission_digest = executor_admission_digest(binding.binding_digest, executor_authorization)`；
  - `executor_admission_digest = digest({"domain": "agent-executor-admission-v1", "binding_digest": ..., "executor_authorization_digest": ...})`，结果为 `sha256:` 前缀的 SHA-256 摘要。
- Executor 在 `execute()` 中用 `_verify_admission(...)` 重算同一个 `request_digest` 并与 Budget Receipt 比对，因此 Budget Receipt 已经间接承诺了工具调用绑定与授权。

### 2.3 D10.7 回执格式

- `ExecutionReceipt` v1 字段集 `RECEIPT_FIELDS_V1` 包含 `binding_digest`、`budget_receipt_digest`、`arguments_digest`、`status`、`result_digest`、`result`、`completed_at` 等；
- v2 字段集 `RECEIPT_FIELDS_V2 = RECEIPT_FIELDS_V1 | {"executor_authorization_digest"}`，承诺本次实际验证所用的授权。
- `ExecutionStore` 按 `operation_id` 去重，`execute_once()` 再把返回回执与本次授权摘要比对，防止异授权冒用旧回执。

### 2.4 ExecutionStore 的硬边界

`execution_store.py` 源码明确：`execute_once()` 把本地工具回调放在 SQLite `BEGIN IMMEDIATE` 事务里，**仅限无外部副作用的确定性本地函数**。不得把它当作任意网络 API 的 exactly-once 执行机制。E1 沿用此边界（见 §9 第 6 条）。

### 2.5 D11.3 现状

- **B.1 电路**：单个 instance 列，8 行公开输入 `[budget_id, period_id, Q, c, C_old, C_new, N, P]`；`u_old, u_new, s, r_old, r_new, nf_secret` 为私有见证；两条独立等式 \(u_{\mathrm{old}}+c-u_{\mathrm{new}}=0\)、\(u_{\mathrm{new}}+s-Q=0\)，五个数值均做 uint32 范围约束；`k=10` 实测确定。
- **C crate**：`Coordinator::new(issuer_vk, db_path)`、`register(&RegistrationAuthorization)`、`submit_transition(proof: &[u8], instance: &[Fp; INSTANCE_ROWS]) -> TransitionReceipt{budget_id, period_id, version, new_commitment, nullifier}`；`submit_transition` 内部为真实 `verify_proof`，无 `verified` 旁路；SQLite `BEGIN IMMEDIATE` 事务内重查 `C_old`/`N` 后原子更新。此 5 字段结构是 C 阶段**已验收且冻结**的接口，E1 不修改它；E1 在集成层另定义带签名的扩展回执 `E1TransitionReceipt`（含 `operation_id`、`metering_quote_digest` 等），其字段、摘要承诺与来源认证见 §6.2.3。
- **C 的注册授权**：域前缀 `D11.3-C-REGISTRATION-v1`，按 `budget_id, period_id, Q, P, C_0` 的 5×32 字节规范小端字段编码，Issuer Ed25519 签名；不证明 Prover 知道 `C_0` 开口（D11.3-A §4.1 方案 B）。
- **D crate**：Python 参考状态机，测试证明 token 绑定全部 8 行公开输入，**不是 Halo2 / ZKP**，不得在 E1 中充当真实证明验证。
- **字段编码**：Pallas `Fp`，规范 32 字节小端，`Fp::to_repr()` 为规范表示，`from_repr` 拒绝非规范编码。

### 2.6 缺失的连接点

E 阶段真正要新增的是连接 D10 与 D11 的桥梁，当前均不存在：

1. D11 的公开输入里没有任何 D10 操作身份。
2. C 的状态转移记录没有保存 D10 的 `operation_id`、`binding_digest` 或计量凭据摘要。
3. 没有可信 Executor 签发的、绑定精确工具调用与 `c` 的计量凭据。
4. D10 的 `request_digest` 只绑定工具调用与授权，不承诺计量凭据。
5. 没有跨实例唯一性约束，无法阻止同一 Lease 注册多个 D11 budget 实例分摊配额。

## §3 双预算模型与身份映射

### 3.1 三个计量维度（不得合并）

| 层 | 字段 | 单位 | 每次操作增量 | 约束位置 |
| --- | --- | --- | --- | --- |
| D10 Lease | `quota_limit` / `used_count` | 操作次数 | +1 | `coordinator.py::consume` |
| D10 全局 | `global_quota_limit` / `global_used_count` | 操作次数 | +1 | `coordinator.py::consume` |
| D11 实例 | `Q` / `u` / `c` | 加权消费单位 | `+c`（\(1\le c\le 2^{32}-1\)） | B.1 电路 + C Coordinator |

D10 与 D11 都通过是工具执行的**必要条件**，任一层拒绝即不执行。D10 的一个操作可以消耗 D11 的多个加权单位；D11 的一次合法转移也只对应 D10 的一次操作。两层不能互相替代，也不共享计数表。

### 3.2 身份映射原则

**不把 D10 的字符串 ID 直接哈希或取模转成 Pallas Fp。** 由 Issuer 签发独立的、带签名的跨层作用域绑定记录，显式建立映射。绑定记录至少包含：

```
version
issuer_id
global_budget_id
lease_id
online_lease_grant_digest

budget_id
period_id
Q
P

metering_policy_digest
registration_authorization_digest

signature
```

字段语义：

- `global_budget_id`、`lease_id`、`online_lease_grant_digest` 来自 D10，逐字节引用已签名对象，不重新编码字符串。
- `budget_id`、`period_id`、`Q`、`P` 是 D11 协议层字段元素（D11.3-A §2），由 Issuer **显式分配**。
- `period_id` **必须由 Issuer 显式分配**，不得从 `issued_at` 或 `expires_at` 推导。
- `registration_authorization_digest` 指向 D11.3-C 的注册授权原文，把跨层映射与 `C_0` 注册绑定。
- `metering_policy_digest` 指向 Issuer 签名的计量策略清单（§4.1）。
- `signature` 是 Issuer 对该记录规范编码的 Ed25519 签名；编码规则采用固定域分离 + 定长字段，具体字节布局在 E1 冻结。

### 3.3 唯一性约束

必须实施：**同一个 D10 Lease 在同一个周期内，不能通过注册多个 D11 budget 实例获得重复的加权额度。**

- 唯一键建议：`(global_budget_id, lease_id, period_id)` → 最多一个 `budget_id`。
- 该约束由 D11 Coordinator 在注册路径强制（E1 实现，对应 C crate 新增注册检查）；与 D11 现有的 `(budget_id, period_id)` 联合主键并存，不冲突。
- 若需为同一 Lease 追加额度，应走显式的重新注册/新周期流程，不得靠多开实例绕过。

### 3.4 `P` 与策略清单

`P` 是 Pallas `Fp` 字段元素，未必能承载任意长度的策略文件摘要。E.0 冻结：

- `P` 作为 **Issuer 分配的策略标识**（字段元素，例如一个小整数标识），其具体取值由 Issuer 分配并签名。
- 策略的**具体内容与摘要**由独立的、Issuer 签名的**计量策略清单**绑定：`P ↔ (metering_policy_digest, 策略内容)`。
- 由 Coordinator 在验证时检查 `proof.public_inputs.P == registered_policy[(budget_id, period_id)]`（沿用 D11.3-A 方案 B），并进一步检查该 `P` 在当前签名策略清单中的 `metering_policy_digest` 与 Metering Quote 中一致。
- **不自行发明未经冻结的 SHA-256 → Fp 映射**，不把策略文件摘要截断/取模塞进 `P`。

## §4 Metering Policy 与 Metering Quote 格式

### 4.1 计量策略清单（Metering Policy）

- 由 Issuer 签名，记录 `metering_policy_digest`、`policy_version`、以及「工具名 + Schema 哈希 → 固定整数费用」的映射表。
- 清单版本与 D11 注册时的 `P` 一一对应（§3.4）。费用表第一版按工具/Schema 固定，不依赖参数内容、执行结果或执行时长。
- `metering_policy_digest` 是链下 SHA-256 摘要，与 `P`（Fp）通过签名清单建立关系；两者不得混称。

### 4.2 `c` 的定义

E.0 第一版冻结：**`c` 是执行前确定的加权调用费用**（admission-time charge），是按计量策略计费的记账单位。

规则：

1. 使用 Issuer 签名的计量策略清单。
2. 可信 Executor 根据工具名称、Schema 与策略计算整数费用。
3. 费用必须在**执行前**确定，且满足 \(1 \le c \le 2^{32}-1\)。
4. 计量策略版本与 D11 注册时的 `P` 对应。
5. 费用绑定到当前 `ToolCallBinding`，包括精确参数摘要与操作身份。
6. 第一版不允许依赖执行结果或执行时长才能确定 `c`。

这样 `c` 在工具副作用发生前就已确定，D11 状态转移可以在执行前完成。

### 4.3 Metering Attestation（计量凭据）

引入**独立的 Metering Attestation**，签名由可信 Executor 用自己的 Ed25519 私钥完成，**不直接破坏 D10.7 已冻结的 Receipt v2 字段结构**。至少绑定：

```
version
executor_id
operation_id

binding_digest
executor_authorization_digest
arguments_digest
canonicalization_version

tool_name
tool_schema_hash

global_budget_id
lease_id
budget_id
period_id
Q
P

c
metering_policy_digest

issued_at
expires_at
```

编码要求：固定域分离前缀 + 定长字段 + 规范序列化；与 ExecutionReceipt 的签名域分离，避免跨协议重放。具体前缀与字节布局在 E1 冻结（本阶段不擅自确定未冻结的编码）。

### 4.4 D11 Coordinator 收到证明时的验证项

D11 Coordinator 在接收状态转移证明时，除现有的 B.1/C 验证外，还须同时验证：

1. **Executor 计量签名有效**（可信 Executor 公钥验签）。
2. **凭据绑定当前 D10 工具调用**（`operation_id`、`binding_digest`、`executor_authorization_digest`、`arguments_digest` 一致）。
3. **`c` 与 B.1 公开输入第 4 行（instance[3]）一致**。
4. **`budget_id` / `period_id` / `Q` / `P` 与已注册作用域一致**（并与 §3.2 跨层绑定记录一致）。
5. **计量策略摘要与 Issuer 签发的策略清单一致**（`metering_policy_digest` 对应该 `P`）。

### 4.5 凭据性质的诚实表述

**Metering Attestation 证明：可信 Executor 按指定计量策略为这次调用签发了费用 `c`。** 它**不证明**实际 CPU、内存或其他物理资源消耗一定等于 `c`。任何文档、注释或对外描述都不得把它写成「真实资源计量」或「实测消耗」。

## §5 D10 / D11 联合执行流程

### 5.1 七步顺序（E1 采用）

1. **请求预检**：固定参数快照，验证 D10 Grant、Executor Authorization v2、工具 Schema 与参数绑定。
2. **Executor 生成 Metering Quote**：根据 Issuer 签名策略计算 `c`，签发绑定操作身份的费用凭据（§4.3）。
3. **Prover 生成 D11 证明**：用当前私有预算状态与 `c`，生成 B.1 真实 Halo2 证明。
4. **D10 Coordinator 准入**：用扩展后的 admission digest（§6）绑定 D10 调用与 Metering Quote，提交操作次数额度，取得 Budget Receipt。
5. **D11 Coordinator 提交状态**：验证 Metering Quote（§4.4）与真实 Halo2 证明，在 SQLite 事务中原子更新承诺、Nullifier、版本与操作记录（§7.3）。
6. **Executor 执行工具（含执行前最终绑定检查）**：两套预算都成功提交后，Executor 在真正 dispatch 工具之前，必须验证 D10 准入与 D11 提交使用的是**同一份计量凭据**：

   1. D10 Budget Receipt 的 `request_digest` 等于根据**本次** Metering Attestation 重新计算的 \(D_{\mathrm{E}}\)（§6.1）。
   2. D11 Transition Receipt 的 `operation_id` 与当前 `ToolCallBinding` 一致。
   3. D11 Transition Receipt 中保存的 `metering_quote_digest` 等于**本次** Metering Attestation 的规范摘要。
   4. Transition Receipt 的 `budget_id`、`period_id`、`version`、`new_commitment`、`nullifier` 与本次已提交的 D11 状态转移一致。
   5. 只有 D10 准入与 D11 状态提交**均**验证成功，才允许进入工具执行；随后产生原有 D10 Execution Receipt。

   必须区分两个概念：**D11 Transition Receipt 证明 Coordinator 已接受并提交这次状态转移**；**Metering Attestation 证明可信 Executor 按指定策略为操作签发了费用**。两者不能互相替代。若 Executor 只验 D10 Budget Receipt 而不核对 D11 Transition Receipt，则「D10 准入用 Quote A、D11 转移关联 Quote B」（A/B 可有相同 `operation_id` 与 `c` 但其他字段或摘要不同）会被错误地关联为一次操作——本检查正是为阻断该错配。

7. **形成联合审计记录**：将 D10 Budget Receipt、D11 Transition Receipt、Metering Quote 与 Execution Receipt 通过同一个 `operation_id` 关联，并按 §6.2 的摘要逐项核对，不得仅凭 `operation_id` 相同就声称已密码学绑定。

### 5.2 关键时序说明

- 步骤 3 的证明使用步骤 2 的 `c`，因此证明的公开输入 `c` 与 Metering Quote 的 `c` 必须一致（§4.4 第 3 项）。
- 步骤 4 在步骤 5 之前：D10 操作额度先提交，D11 状态随后提交；这也是 §7.2 中「D10 成功、D11 失败」不退款情形的来源。
- **两份预算回执都是工具执行的前置条件，且顺序固定**：D10 Budget Receipt（步骤 4）与 D11 Transition Receipt（步骤 5）都必须先于工具执行（步骤 6）产生并可用。任一回执缺失、未生成或未通过验证，都不得 dispatch 工具。
- 步骤 6 的工具执行必须在两套预算都提交**之后**，不得提前；`ExecutionStore` 的确定性本地工具边界不变（§2.4）。步骤 6 的最终绑定检查（§5.1 第 6 步的 1–5 项）是 dispatch 的**硬前置门**，而不是执行后的审计动作。
- **同一份 Metering Attestation 必须贯穿步骤 2、4、5、6**：步骤 2 签发它，步骤 4 经 \(D_{\mathrm{E}}\) 承诺它，步骤 5 把它的摘要写入 D11 操作记录，步骤 6 重新核对两本账引用的正是它。任何一步引用了不同的凭据，检查即失败、工具不执行。
- 步骤 7 不新增签名凭据结构，只用 `operation_id` 与既有摘要把四条凭据链起来；Transition Receipt 的签名/摘要格式在 E1 冻结。联合审计记录的逐项摘要核对规则见 §6.2。

## §6 跨层摘要与凭据关联

### 6.1 跨层摘要 \(D_E\)

D10 当前的 `request_digest` 只绑定工具调用与授权。E1 增加独立的跨层摘要：

\[
D_{\mathrm{E}} = H\!\left(D_{\mathrm{binding}},\ D_{\mathrm{authorization}},\ D_{\mathrm{metering\ quote}}\right)
\]

其中：

- \(D_{\mathrm{binding}}\) = `ToolCallBinding.binding_digest`；
- \(D_{\mathrm{authorization}}\) = `ExecutorAuthorization.authorization_digest`；
- \(D_{\mathrm{metering\ quote}}\) = Metering Attestation 的规范摘要。

编码要求：

- 使用固定域分离前缀（建议 `agent-e0-cross-layer-admission-v1`，E1 冻结）与规范序列化；
- **不得直接拼接可变长度字符串**；
- 结果采用 D10 `digest()` 的 `sha256:` 前缀格式，以满足 `coordinator.consume()` 对 `request_digest` 的格式校验；
- 这是 SHA-256 摘要，**不是** Pallas `Fp`，**不是** Poseidon 输出，与 D11 的字段元素严格区分。

### 6.2 用法与闭环

- 把 \(D_{\mathrm{E}}\) 作为 D10 Coordinator 的 `request_digest`（步骤 4）。
- Executor 在实际执行时（步骤 6）重新计算 \(D_{\mathrm{E}}\) 并与 Budget Receipt 中的 `request_digest` 比对，形成闭环。
- 由此三条凭据链通过同一操作身份关联：

| 凭据 | 承诺对象 | 关联方式 |
| --- | --- | --- |
| D10 Budget Receipt | 间接承诺 Metering Quote（经 \(D_{\mathrm{E}}\)） | `request_digest = D_E` |
| D10 Execution Receipt v2 | 承诺 Budget Receipt 与实际授权 | `budget_receipt_digest` + `executor_authorization_digest` |
| D11 Transition Receipt | 关联 Metering Quote | `budget_operations` 中 `metering_quote_digest` 与 `transition_digest`（§7.3） |

不必直接破坏 D10.7 已冻结的 Receipt v2 字段结构即可完成绑定。

#### 6.2.1 跨层凭据关联的验证规则（最终绑定）

「三本凭据有相同的 `operation_id`」本身**不构成密码学绑定**。执行前（§5.1 第 6 步）与联合审计（步骤 7）必须逐项核对以下等价关系，任一项不成立即拒绝执行 / 标记审计失败：

1. `D10 Budget Receipt.request_digest == recompute_D_E(binding, authorization, metering_attestation)`。
2. `D11 Transition Receipt.operation_id == ToolCallBinding.operation_id`。
3. `D11 Transition Receipt.metering_quote_digest == canonical_digest(metering_attestation)`。
4. `D11 Transition Receipt.(budget_id, period_id, version, new_commitment, nullifier)` 与本次已提交的 D11 状态转移逐字段相等。
5. `D10 Execution Receipt.budget_receipt_digest == D10 Budget Receipt.receipt_digest`（D10.7 既有保证，沿用）。

这些规则确保 D10 批准的那一次操作、D11 扣除的那一次预算、Executor 执行的那一次工具调用使用的是**同一份 Metering Attestation**。

#### 6.2.2 联合审计记录的摘要与关联

保留 D10 Execution Receipt v2 字段结构不变；联合审计记录（步骤 7）额外保存以下字段，并明确其关联：

```
operation_id
budget_receipt_digest        # D10 Budget Receipt
transition_digest            # D11 Transition Receipt
metering_quote_digest        # Metering Attestation 规范摘要
execution_receipt_digest     # D10 Execution Receipt v2
```

关联验证规则：

- 四个摘要必须通过 §6.2.1 的等价关系指向同一 `operation_id` 与同一 Metering Attestation；
- `budget_receipt_digest` 出现在 Execution Receipt 的 `budget_receipt_digest` 字段中（规则 5）；
- `transition_digest` 与 `budget_operations.transition_digest` 一致（§7.3）；
- `metering_quote_digest` 同时被 `D_E`（规则 1）与 D11 操作记录（规则 3）承诺；
- **不得仅因四个字段共享 `operation_id` 就声称它们已密码学绑定**；必须按上述规则逐项校验摘要相等。

审计记录只保存摘要，不重复保存凭据原文；这些摘要本身是 SHA-256 格式（与 §6.1 一致），不是 Pallas `Fp`。

#### 6.2.3 E1 Transition Receipt：字段、摘要承诺与来源认证

本节明确 §5.1 第 6 步与 §6.2.1 所依赖的回执凭据依据，回答三个具体问题，不引入新安全机制。

**(a) E1 是否扩展 Transition Receipt——是，但以 additive 方式，不改 C 已冻结结构。**

C 阶段现有的 `TransitionReceipt{budget_id, period_id, version, new_commitment, nullifier}` 保持不动。E1 在集成层定义独立扩展回执 `E1TransitionReceipt`，字段集合冻结为：

```
operation_id                 # 来自当前 ToolCallBinding（满足 §5.1 第 6.2 项）
binding_digest               # 当前 ToolCallBinding 摘要
metering_quote_digest        # 本次 Metering Attestation 规范摘要（满足第 6.3 项）
budget_id
period_id
state_version                # 即 C 回执的 version
new_commitment               # 即 C 回执的 new_commitment
nullifier                    # 即 C 回执的 nullifier
coordinator_key_id           # 签发方密钥标识
transition_digest            # 完整回执的摘要，定义见 (b)
coordinator_signature        # D11 Coordinator 对 payload 的 Ed25519 签名，见 (c)
```

前五个状态字段直接取自 C 的 `TransitionReceipt`，不是重新计算；`operation_id`/`binding_digest`/`metering_quote_digest` 由上层在提交转移时传入、Coordinator 写回（与 §7.3 `budget_operations` 所存字段一致）。E1 不修改 C crate 结构体定义，只做包装与签发（沿用 §6.3 additive 边界）。

**(b) `transition_digest` 的承诺范围——对包含上述字段的完整规范化 payload 计算。**

区分两个摘要，避免混淆：

- `metering_quote_digest` = `canonical_digest(metering_attestation)`，承诺 Executor 签发的费用凭据（§6.2.1 规则 3）；
- `transition_digest` = `digest({"domain": "d11-e1-transition-receipt-v1", "payload": canonical(完整 E1TransitionReceipt payload)})`，其中 payload 至少包含 (a) 中除 `coordinator_signature` 外的全部字段，**特别是 `operation_id` 与 `metering_quote_digest`**。

因此 `transition_digest` 承诺的是完整回执，任何字段被替换（含 `operation_id`、`metering_quote_digest`、五个状态字段）都会使摘要不匹配。§7.3 `budget_operations.transition_digest` 保存的正是这个完整摘要，§6.2.2 联合审计记录引用同一个值。域分离前缀 `d11-e1-transition-receipt-v1` 与 `D_E` 的 `agent-e0-cross-layer-admission-v1` 不同，防止跨协议摘要复用。

**(c) Executor 如何确认字段来自 D11 Coordinator——验 D11 Coordinator 签名，而非读取本地数据库记录。**

来源认证不依赖「Executor 能读到 `budget_operations` 一行」——那只是本地存储事实，任何持有 DB 写权限者都能伪造。凭据依据是签名：

1. D11 Coordinator 在 `submit_transition` 成功提交后，用其 Ed25519 私钥对 (b) 的完整规范化 payload 签名，生成 `coordinator_signature`（与 D10 Budget Receipt 由 D10 Coordinator 签名、Execution Receipt 由 Executor 签名的既有模式一致，不新增签名机制或信任主体）。
2. Executor 在执行前（§5.1 第 6 步）用**可信运行时配置注入的 D11 Coordinator 公钥**验 `coordinator_signature`，再重算 `transition_digest` 与回执内值比对，并按 §6.2.1 规则 2–4 逐项核对 payload 字段。验签通过才认定回执字段确实来自该 Coordinator。
3. 信任假设不变：Coordinator 本就是可信方（§8.2），此处只是让它对已提交结果签发可验证凭据。若 Coordinator 私钥泄露或被攻陷，则该凭据与 D10 Budget Receipt 一样不再可信（沿用 §8.2 的既有边界，非新风险）。
4. `budget_operations` 的本地查询仅用于 §7.4 幂等恢复（防止二次消费），**不得**作为字段来源认证的替代；签名验签是执行前的硬前置门（§5.2）。

由此，§5.1 第 6 步与 §6.2.1 的全部检查都有明确凭据依据：D10 侧由 Budget Receipt 的 `request_digest = D_E` 承诺计量凭据，D11 侧由带 Coordinator 签名的 `E1TransitionReceipt` 承诺同一凭据，Executor 通过「验签 + 摘要重算 + 逐字段比对」确认两本账引用同一份 Metering Attestation。

### 6.3 additive 边界（保护既有测试）

- 新增 \(D_{\mathrm{E}}\) 与跨层入口是**增量**的：E1 新建独立摘要函数与集成入口，**不修改** D10.6 的 `executor_admission_digest` 行为，也不改 `run_tool_call` 的默认路径。
- D10.4–D10.7 现有默认行为与既有测试必须保持回归通过；跨层摘要只在 E1 集成路径启用。

## §7 并发、幂等与故障恢复

### 7.1 Saga，而非跨库原子提交

D10 与 D11 使用**不同的持久化数据库**，当前没有跨数据库原子事务。E1 必须采用**可恢复的 Saga 式流程**，**不得声称**实现了跨库原子提交。第一版采用**准入计费、不退款、失败关闭**的保守策略。

### 7.2 故障处理表

| 故障位置 | 处理规则 |
| --- | --- |
| 预检失败 | 不扣除任一预算，不执行工具 |
| D10 准入失败 | 不提交 D11，不执行工具 |
| D10 成功、D11 失败 | D10 操作额度**不退还**，不执行工具 |
| D11 成功、执行前崩溃 | 使用原 `operation_id` 与原凭据恢复 |
| 工具执行失败 | 产生 `FAILED` 回执，已提交的两类额度均不退款 |
| 完整成功 | 保留全部签名凭据与状态转移记录 |

**必须显式承认**：若 D10 已扣一个操作额度，但 D11 因并发状态冲突拒绝转移，D10 额度仍被消耗。这是两个独立账本之间的保守代价，不得隐藏或声称不存在。

### 7.3 `budget_operations` 幂等记录

C 阶段现有的 Nullifier 表单独不足以解决联合集成后的崩溃恢复。E1 增加独立操作记录表：

```
budget_operations
-----------------
operation_id                 PRIMARY KEY
budget_id
period_id
binding_digest
metering_quote_digest
transition_digest
nullifier
committed_version
```

- 该表的插入必须与 Nullifier 插入、状态指针更新放在**同一个 `BEGIN IMMEDIATE` 事务**里。
- `transition_digest` 为 D11 Transition Receipt 的规范摘要，使幂等重试能返回同一份可审计凭据。

规则：

1. 相同 `operation_id`、相同请求内容（完整凭据摘要一致）：返回之前保存的 Transition Receipt。
2. 相同 `operation_id`、不同 `binding_digest` 或不同 `metering_quote_digest`：拒绝。
3. 未提交成功的请求：**不能**留下操作记录。
4. 已经提交的请求：**不能**再次消耗同一份状态。

这样在 D11 已提交、但上层进程尚未收到返回值时，可以安全地用原请求恢复，而不会二次消费。

### 7.4 恢复流程

- 以 `operation_id` 为幂等键查询 `budget_operations`；**但恢复时绝不能仅凭 `operation_id` 存在就返回结果或认定操作已完成**——必须核对完整凭据摘要后才决定：
  - `binding_digest` 与当前 ToolCallBinding 一致；
  - `metering_quote_digest` 与本次 Metering Attestation 的规范摘要一致；
  - `transition_digest`、`nullifier`、`committed_version` 与留存记录逐字段一致，并满足 §6.2.1 的全部等价关系。
- 命中且上述全部一致 → 返回留存 Transition Receipt；命中但任一摘要不一致 → 拒绝（§7.3 规则 2），不得复用旧凭据；未命中 → 允许按 §5 正常走完整流程。
- 若只有 D10 侧已扣额度而 D11 侧无对应操作记录（§7.2「D10 成功、D11 失败」），不伪造 D11 Transition Receipt，按不退款策略如实上报；上层不得以恢复为名绕过 D11 提交。
- D10 侧 `consume` 本身已有 operation 幂等与 `INDETERMINATE` 健康状态机制，E1 沿用，不重复实现；同样，D10 的幂等命中也须核对 `request_digest == D_E`，不能只看 `operation_id`。

## §8 威胁模型、信任假设与安全边界

### 8.1 攻击者能力

假设攻击者控制 Agent 的 Planner/Prover，可任意构造见证、篡改公开输入、重放旧证明、并发提交多个转移、跨实例/跨周期重放、自选 Nullifier、替换计量凭据中的 `c` 或绑定字段、伪造策略摘要映射。

### 8.2 信任假设（不得夸大）

- **可信**：Issuer 的跨层绑定记录、策略清单、初始状态签发与 ID 分配；D10 Coordinator 的准入与账本；可信 Executor 的计量签名与工具执行；D11 Coordinator 的证明验证、状态存储与原子提交；Poseidon 参数与域分离规则正确。
- **不可信**：Planner / Prover，可恶意构造见证、公开输入与凭据内容。
- **密码学保证依赖**：承诺绑定性、ZKP 完备性/可靠性/零知识性、Poseidon 抗碰撞与单向性、Ed25519 签名可靠性、底层 SQLite 事务原子性与持久性。
- **明确不在范围内**：Coordinator 与 Executor 串通或被攻陷时，隐私与计量正确性都不再成立（沿用 D11.0 / D11.3-A §9.3 的信任边界）。

### 8.3 安全边界与不声称项

E1 完成后可以声称：授权精确的 D10 工具调用，通过可信 Executor 签发的计量凭据和真实 Halo2 证明，完成一次绑定、可审计、不可重复的隐私预算状态转移。

E1 完成后**仍不能声称**：

- `c` 反映真实 CPU / 内存 / Token / 物理资源消耗（§4.5）；
- D10 与 D11 之间存在跨库原子提交（§7.1）；
- 并发冲突导致 D10 额度被扣后一定会退款（§7.2）；
- D11-D 的 Python 测试验证器具备密码学可靠性；
- `ExecutionStore` 支持任意网络 API 的 exactly-once（§2.4）；
- 隐藏了 `c` 或累计消费量——按 D11.3-A §10，`c` 公开且累计消费 \(u_n=\sum c_i\) 可由公开信息推导，转移之间保持可关联；
- 协议已有形式化安全证明，或系统可直接部署到任意 Agent 工具调用场景。

## §9 E1 集成原型的实现范围（预留边界）

E1 只实现以下范围，逐条冻结：

1. 只使用 `authorization_required` 与 D10 Executor Authorization **v2**；严格模式，无授权不执行。
2. 第一版采用**每个工具/Schema 对应固定整数费用**的 Issuer 签名计量策略（§4.1），不做动态或执行后计费。
3. 真实 D11 Halo2 证明与 Coordinator 验证必须**沿用 B.1/C**（k=10、真实 `verify_proof`、无旁路），**不使用** D11-D 的 Python 测试验证器。
4. 增加 Rust Coordinator 的集成接口供上层调用；建议先比较**长驻 JSON Lines 服务**与其他桥接方式，再决定，**不得**把 Rust 证明验证改写成 Python。
5. 为 D11 增加操作 ID 幂等记录（`budget_operations`，§7.3）并生成可审计的 `E1TransitionReceipt`——字段、`transition_digest` 承诺范围与 Coordinator 签名来源认证按 §6.2.3 冻结实现，C 阶段 5 字段结构不改。
6. 只支持**确定性本地工具**，不支持任意网络 API 或不可逆外部副作用（沿用 §2.4）。
7. D10.4–D10.7 的现有默认行为及既有测试必须保持**回归通过**；跨层能力以 additive 方式接入（§6.3）。

E1 不得扩展为：生产部署、分布式/高可用、动态计量、退款、隐藏 `c`、形式化安全证明或论文创新性结论。
