**D10 Python 执行链**
- 入口 `AgentToolRuntime.run_tool_call`（`agent_runtime.py:32`）：预检授权 → `operation_id` 取自可信 `execution_grant["operation_id"]` → `snapshot_arguments` → 构造 `ToolCallBinding` → `verify_executor_authorization`（以当前 binding 的 `arguments_digest`/`canonicalization_version` 复核）→ `executor.prepare_tool_call` → `consume_for_grant(request_digest=admission_digest)` → 取回已验签 Budget Receipt → `executor.execute`。

- `tool_binding.py`：`CANONICALIZATION_VERSION = "python-canonical-json-v1"`；binding 摘要域 `agent-tool-call-binding-v1`；参数摘要域 `agent-tool-arguments-v1`；`snapshot_arguments` 拒绝 float、整数限 signed 64-bit，并在哈希前脱离 Planner 拥有的嵌套对象。
- `executor_authorization.py`：`authorization_digest` 域 `executor-authorization-v1`；`executor_admission_digest` 域 `agent-executor-admission-v1`。
- `receipts.py`：Budget Receipt 字段集固定（`receipt_version, coordinator_id, coordinator_key_id, global_budget_id, global_sequence, gateway_id, lease_id, global_lease_grant_digest, execution_grant_digest, operation_id, request_digest, lease_used_count, global_used_count, committed_at`），`receipt_digest = digest({"payload":…, "signature_b64":…})`。
- `execution_receipts.py`：`RECEIPT_FIELDS_V2 = RECEIPT_FIELDS_V1 | {"executor_authorization_digest"}`。

### A.2 不可信 Planner 不得决定的字段（硬边界）
Planner 输入**只是数据**。以下值必须由可信运行时配置或可信组件产生，任何来自 Planner 的同名字段一律忽略或拒绝：
- 计量费用 `c`（Executor 按签名策略计算）；
- Executor 身份与公私钥（`executor_id`/`executor_private_key`）、Issuer/D10 Coordinator/D11 Coordinator 公钥（可信配置注入）；
- D11 预算作用域（`budget_id/period_id/Q/P`、跨层绑定记录）由 Issuer 签名分配；
- `operation_id` 取自可信 `execution_grant`，不是 Planner 自报；
- `coordinator_key_id`→公钥映射来自可信配置，不来自回执自述。

### A.3 关于「Python 参考模型」的隔离
`experiments/d11_3_d_reference/` 的测试证明 token 与其验证器**仅作协议语义对照**，E1 真实执行路径**不得**导入、调用或以其结果替代 Halo2 `verify_proof`。集成 crate 依赖图里不得出现对 D 阶段模块的引用。

## B. Python ↔ Rust 交互接口（任务包 B）

### B.1 备选方案比较

| 维度 | 方案 1a：短生命周期 subprocess CLI | 方案 1b：长驻 JSON Lines 服务 | 方案 2：FFI / PyO3 |
| --- | --- | --- | --- |
| 构建复杂度 | 低，`cargo build` 出二进制 | 低，同 1a | 高：pyo3/maturin、ABI、wheel、Python 开发头 |
| 与现有代码契合 | 需新建 bin | 需新建 bin + 长驻循环 | 需把 crate 改 cdylib，触碰冻结 crate 的构建配置 |
| keygen 开销（`k=10`） | **每请求重新 keygen**，昂贵 | 进程级 `OnceLock` 只做一次 | 只做一次，但进程内 |
| VK/PK 稳定性 | 依赖各进程确定性重建，易分歧 | 进程内稳定，天然一致 | 进程内稳定 |
| 错误语义 | 退出码 + stderr，清晰 | 逐行 JSON 响应 + 退出码，清晰 | panic 跨 FFI 边界风险，错误语义难保证 |
| 进程崩溃可检测/可恢复 | 每请求天然隔离 | 可用 EOF/退出码检测并重启 | 段错误直接带崩 Python，无法用「进程退出」检测 |
| 测试便利性 | 可命令行喂数据 | 可用管道逐行喂 JSON，易做故障注入 | 需要 Python 测试环境绑定 |
| 与 E.0 §9.4「先比较长驻 JSON Lines 与其他桥接」的关系 | 是被比较对象 | 是被比较对象 | 是被比较对象 |

### B.2 选定：方案 1b — 长驻 JSON Lines 服务

**选择理由**（对应上表）：
1. `proof_verifier.rs` 的 Params/PK/VK 是进程级 `OnceLock`，`k=10` keygen 昂贵；短生命周期 CLI 每请求重做，且难保证跨进程 VK/PK 不分歧；长驻服务一次生成、进程内稳定。
2. 崩溃语义可工程化：Python 用 `subprocess.Popen` 管理单一子进程，管道 EOF / 非零退出即判为服务不可用 → 整笔操作失败关闭 → 重启服务（重新 keygen）后按原 `operation_id` 走幂等恢复（§D.6）。这正是任务包要求明确回答的「Rust 进程异常退出如何处理」。
3. 进程隔离：Rust panic 不会带崩 Python；不改 C crate 构建配置，保持 D11.3-B/C 已验收契约不变。
4. 测试友好：可直接用命令行逐行喂 JSON 做协议/故障注入测试，无需 Python ABI 环境。

**不选方案 2** 的决定性原因：panic/段错误跨 FFI 边界无法用「进程退出」检测，与 §B.6 的恢复语义直接冲突，且会触碰冻结 crate 的构建方式。**不选 1a** 的决定性原因：keygen 每请求重做 + VK/PK 跨进程一致性风险。

**进程模型**：一个 D11 Rust 进程 = 一个实验 Coordinator 实例；持有 issuer_vk、D11 Coordinator 签名私钥（实验原型从配置载入）、SQLite 路径、`experimental_proof_assets`。Prover 端 `prove_experimental` 复用同一进程内的 Params/PK（保证 verify 用同一 VK）——Prover 通过同一服务的另一方法调用，证明仍由 Rust 真实生成，Python 只提交见证数据且不接触 VK 以外的密钥材料。

> 说明：长驻容器内 VK/PK 由进程内 `OnceLock` 生成，属 E.0 允许的「实验原型参数管理」，不声称生产级密钥管理。跨请求重启后 keygen 重新生成 VK；因此本阶段约定**一次端到端业务流程内服务不得重启**，重启只用于崩溃恢复且必须走幂等路径（§D.6），不得用新 VK 验证旧 proof 后声称成功。

### B.3 传输数据结构与编码（两端共用一套，禁止各造一套）

所有跨层 JSON 字段遵循一张**编码对照表**（E1.1 落成代码 + golden vectors 交叉测试）：

| 逻辑类型 | JSON 表示 | 约束/校验入口 |
| --- | --- | --- |
| Pallas `Fp`（含 `budget_id/period_id/Q/c/C_old/C_new/N/P`） | 64 位**小写 hex 字符串** | Rust `fp_from_hex`（非规范拒绝）；Python 侧同规则小端 32 字节实现，两端对同一值产出相同 hex |
| `u32` 数值（`Q/c` 的语义值） | JSON number | Rust `fp_to_u64_checked` + `1..=MAX_UINT32`；Python 侧 `int` 且非 `bool`、边界检查；禁止负数/溢出/取模截断 |
| proof（`transcript.finalize()` 的字节） | base64 字符串 | 解码后交 `verify_proof`；空/非 base64 拒绝 |
| 各类摘要（`request_digest`、`transition_digest`、`metering_quote_digest` 等） | `sha256:` 前缀字符串 | Python `is_sha256`（长度 71）；Rust 侧等价校验 |
| Attestation / Receipt 对象 | JSON object（字段集合固定） | 见 §C；字段多一个/少一个即拒绝 |

**请求信封**（`method` 决定 payload 结构）：
```json
{"request_id": "<opaque id>", "method": "submit_transition_e1", "payload": { ... }}
```
**响应信封**：
```json
{"ok": true, "result": { ... }}   // 或
{"ok": false, "error": {"code": "<稳定错误码>", "message": "<可读详情>"}}
```
首版方法集（E1.3 实现）：`register_e1`、`prove`、`submit_transition_e1`、`get_operation`（幂等查询）、`health`。

**避免重复造轮子的规则**：E1.1 先写一份编码规范 + 一组 golden vectors（同一输入在 Python `e1_encoding` 与 Rust `e1_encoding` 产出字节级相同的摘要与 hex），两端测试都引用同一组向量；任何一端私自改编码即向量测试失败。E.0 已冻结的摘要公式只做「落到具体字节」，不改公式。

### B.4 `submit_transition_e1` 输入/输出
- 输入 payload：`proof`(base64)、`instance`（8 字段 hex/number 对象）、`metering_attestation`（对象全文 + 摘要）、`operation_id`、`binding_digest`。
- 输出 result：`E1TransitionReceipt` 全文（§C.3）。
- 约束：`instance.c` 必须等于 `metering_attestation.c`（E.0 §4.4 第 3 项）；`operation_id` 必须等于 attestation 与 binding 中的值；任一不等 → 错误码 `ATTESTATION_BINDING_MISMATCH`，不写库。

### B.5 错误码映射（稳定码，供 Python 判定失败语义）

| Rust 来源 | 稳定错误码 | Python 处置 |
| --- | --- | --- |
| `InvalidPublicInput` | `INVALID_PUBLIC_INPUT` | 整笔失败关闭，不重试原样数据 |
| `UnregisteredInstance` / `InvalidAuthorization` | `UNREGISTERED_INSTANCE` / `INVALID_REGISTRATION` | 先完成注册/绑定再重试 |
| `QuotaMismatch` / `PolicyMismatch` | `QUOTA_MISMATCH` / `POLICY_MISMATCH` | 不重试，审计告警 |
| `ProofVerification` | `PROOF_INVALID` | 不重试原 proof |
| `StateConflict` | `STATE_CONFLICT` | 用**同一 operation_id** 走幂等查询（§D.6），不重签状态 |
| `Store` | `STORE_ERROR` | 查询是否落库后决定；不确定则按失败关闭 |
| `DuplicateRegistration` | `DUPLICATE_REGISTRATION` | 视为已注册，核对后继续 |
| 新增：`ATTESTATION_INVALID` / `ATTESTATION_BINDING_MISMATCH` / `IDEMPOTENCY_CONFLICT` / `SCOPE_CONFLICT` | 同名 | 均失败关闭；`SCOPE_CONFLICT` 触发唯一性审计 |
| 进程 EOF / 超时 / 非零退出 | `SERVICE_UNAVAILABLE` | 重启服务 + 幂等恢复（§B.6） |

### B.6 Rust 进程异常退出处理
1. Python 侧对每次请求设超时；管道 EOF、进程退出或非零退出码 → 判 `SERVICE_UNAVAILABLE`。
2. **不得**把「服务不可用」当作证明验证通过，也不得据此 dispatch 工具（E.0 §5.2 两份回执前置）。
3. 重启服务 → 用原 `operation_id` 调 `get_operation`：
   - 命中且摘要一致且回执验签通过 → 返回留存回执，继续最终绑定门禁；
   - 命中但摘要不一致 → `IDEMPOTENCY_CONFLICT`，失败关闭；
   - 未命中 → 从 §E 中「D11 未提交」的故障点重新走流程（D10 已扣的额度按不退款处理）。
4. 记入联合审计：进程崩溃事件 + 恢复路径，不隐藏、不伪造 D11 回执。

## C. 四种凭据接口（任务包 C）

### C.0 统一约定
- 签名算法：Ed25519；签名输入：`canonical_json_bytes({"domain": <域>, "payload": <对象字段>})`（域分离进签名消息，防跨协议重放）；存 `signature_b64`。
- 摘要入口：Python `digest(...)`（`sha256:` 前缀）；Rust 侧 E1.1 提供字节等价实现；**E.0 已冻结的公式原样使用**。
- 摘要/签名字段一律由可信组件计算；调用方传入的摘要字段只用于「比对」，不用于「赋值」。
- 验证失败一律拒绝执行，不降级、不旁路。

### C.1 Metering Attestation
- **签发**：D10 Executor（可信）；**验证**：D11 Coordinator（提交时）+ Executor（执行前门禁复验同一份）。
- **字段**（E.0 §4.3 全量，字段集合固定，多/少即拒）：`version, executor_id, operation_id, binding_digest, executor_authorization_digest, arguments_digest, canonicalization_version, tool_name, tool_schema_hash, global_budget_id, lease_id, budget_id, period_id, Q, P, c, metering_policy_digest, issued_at, expires_at`。
- **签名域**：`d11-e1-metering-attestation-v1`（E1 冻结，落实 E.0 §4.3「前缀 E1 冻结」）；与 ExecutionReceipt 签名域分离。
- **摘要**：`metering_quote_digest = digest({"domain": "d11-e1-metering-attestation-v1", "payload": <attestation 字段>})`。
- **字段来源**：`c` 由 Executor 按 Issuer 签名策略清单计算（\(1\le c\le 2^{32}-1\)）；`operation_id/binding_digest/executor_authorization_digest/arguments_digest/canonicalization_version` 由可信 binding/授权派生；`budget_id/period_id/Q/P/metering_policy_digest` 来自 Issuer 跨层绑定与策略清单；`issued_at/expires_at` 来自可信时钟。**不接受调用方指定 `c`**。
- **性质**：只证明「可信 Executor 按策略为本操作签发了费用 `c`」，不证明真实物理资源消耗（E.0 §4.5）。
- **拒绝**：签名无效、字段集不符、过期、`c` 越界、与 binding/授权/实例不一致 → `ATTESTATION_INVALID` / `ATTESTATION_BINDING_MISMATCH`。

### C.2 D10 Budget Receipt
- **签发**：D10 Coordinator；**验证**：Executor（`_verify_admission`）。字段结构与签名/摘要逻辑**完全沿用 `receipts.py`，不改**（含 `coordinator_key_id`）。
- E1 唯一变化：在集成路径里把 `request_digest` 从 `executor_admission_digest` 换成 \(D_{\mathrm{E}}\)（§C.5），并让 Executor 门禁用同一份 Attestation 重算 \(D_{\mathrm{E}}\) 比对；D10.4–D10.7 默认路径（含 `run_tool_call`）保持 additive 不变。

### C.3 E1TransitionReceipt
- **签发**：D11 Coordinator；**验证**：Executor（执行前门禁）。E.0 §6.2.3 已冻结字段/摘要承诺/来源认证，原样实现：
  ```
  operation_id, binding_digest, metering_quote_digest,
  budget_id, period_id, state_version, new_commitment, nullifier,
  coordinator_key_id, transition_digest, coordinator_signature
  ```
  - `unsigned_payload` = 上列除 `transition_digest`/`coordinator_signature` 外的全部字段（9 个），不含任何摘要或签名字段；
  - `transition_digest = digest({"domain": "d11-e1-transition-receipt-v1", "payload": canonical(unsigned_payload)})`（无循环自引用，E.0 §6.2.3(b) 修订后口径）；
  - `coordinator_signature` = Coordinator 对 `{"domain": "d11-e1-transition-receipt-sign-v1", "transition_digest": <摘要>}` 的 Ed25519 签名。
- **字段来源**：五个状态字段取自 C 的 `TransitionReceipt` + CAS 提交的 `version`（Coordinator 生成）；三个跨层字段（`operation_id/binding_digest/metering_quote_digest`）由上层传入、Coordinator 写回；摘要与签名由 Coordinator 生成。C 的 5 字段结构不改。
- **来源认证**：Executor 用**可信配置注入的 D11 Coordinator 公钥**验签 + 重算摘要 + 逐字段比对；`budget_operations` 本地查询仅用于幂等恢复，**不得**作为来源认证（E.0 §6.2.3(c)）。

### C.4 D10 Execution Receipt v2
- **签发**：Executor；**验证**：审计方。字段结构沿用 `execution_receipts.py::RECEIPT_FIELDS_V2`，不改；`authorization_required` 下 `receipt_version=2` 且含 `executor_authorization_digest`。
- 联合审计记录复用既有摘要，**不新增**独立签名凭据（E.0 §5.2 修订后口径）。

### C.5 跨层摘要 \(D_{\mathrm{E}}\)（E.0 §6.1 冻结公式的具体编码）
\[
D_{\mathrm{E}} = \mathrm{digest}\big(\{\text{domain}: \text{"agent-e0-cross-layer-admission-v1"},\ D_{\mathrm{binding}},\ D_{\mathrm{authorization}},\ D_{\mathrm{metering\ quote}}\}\big)
\]
- 三个分量键名固定为 `binding_digest`、`executor_authorization_digest`、`metering_quote_digest`，分别对应 E.0 公式中的 \(D_{\mathrm{binding}}\)、\(D_{\mathrm{authorization}}\)、\(D_{\mathrm{metering\ quote}}\)（第三项即 Metering Attestation 的规范摘要）；
- 域前缀 `agent-e0-cross-layer-admission-v1`（E1 冻结）与 `d11-e1-transition-receipt-v1`/`-sign-v1`、`d11-e1-metering-attestation-v1`、既有 `agent-executor-admission-v1` 均不同，防跨用途复用；
- 结果为 `sha256:` 前缀字符串，满足 `coordinator.consume()` 对 `request_digest` 的格式校验；不是 `Fp`、不是 Poseidon 输出。

### C.6 `coordinator_key_id` 与可信公钥配置
- 两种 Receipt 都带 `coordinator_key_id`，但它是**标识不是信任根**。可信运行时配置维护 `key_id → public_key` 映射：收到回执先取 `key_id`，查映射得公钥，再验签；**未知 key_id、映射缺失或回执自述公钥 → 直接拒绝**。
- D10 Coordinator 公钥沿用现有注入路径；D11 Coordinator 公钥为 E1 新增的可信配置项。

### C.7 字段来源总表（调用方提供 vs 可信组件生成）

| 字段 | 来源 | 可否由调用方指定 |
| --- | --- | --- |
| `operation_id` | 可信 `execution_grant` | 否 |
| `binding_digest` / `arguments_digest` / `canonicalization_version` | Runtime/Executor 由 binding 派生 | 否 |
| `c` / Metering Attestation 全文 | 可信 Executor 按策略计算并签发 | 否 |
| `budget_id/period_id/Q/P`、跨层绑定记录、策略清单 | Issuer 签名分配 | 否 |
| `budget_id/period_id/version/new_commitment/nullifier`（回执内） | D11 Coordinator 从已验证 instance + CAS 生成 | 否 |
| `transition_digest` / `coordinator_signature` | D11 Coordinator | 否 |
| 所有摘要字段 | 各自可信签发方 | 仅用于比对 |

## D. D11 Coordinator 扩展与崩溃恢复闭环（任务包 D）

### D.1 additive 实现边界
在 C crate 内**新增模块**（建议 `src/e1.rs`）与**新增表**，不修改已冻结的 `TransitionReceipt` 五字段结构、`submit_transition` 签名与既有模块的对外行为；既有 C01–C16 测试保持回归通过。对外新增 `submit_transition_e1`（§B.4）。

### D.2 跨层字段进入提交路径
`submit_transition_e1(proof, instance, metering_attestation, operation_id, binding_digest)` 内部顺序：
1. 复用既有 public-input uint32 域检查、注册与留存授权复核、Q/P 比对（与 `submit_transition` 一致）；
2. **验 Metering Attestation**（§C.1）：验签、字段集、有效期、`c` 范围；
3. 逐项核对 E.0 §4.4 五项：签名有效、绑定当前调用（`operation_id/binding_digest/executor_authorization_digest/arguments_digest`）、`c == instance[3]`、`budget_id/period_id/Q/P` 与注册作用域一致、`metering_policy_digest` 对应注册 `P` 的策略清单；
4. 真实 `verify_proof`（无旁路）；
5. 进入 CAS 事务（§D.5），签发回执（§D.6）。

### D.3 `(global_budget_id, lease_id, period_id)` 唯一性
- 新增表 `cross_layer_scopes(global_budget_id, lease_id, period_id, budget_id, binding_record_digest, …)`，`UNIQUE(global_budget_id, lease_id, period_id)`。
- 在 `register_e1` 路径验证 Issuer 签名的跨层绑定记录（E.0 §3.2 字段集）后写入；同一 Lease 同周期第二个 `budget_id` 注册 → `SCOPE_CONFLICT`，事务回滚、无部分落库。
- 与既有 `(budget_id, period_id)` 主键并存，不冲突；追加额度走显式新周期/重新注册（E.0 §3.3）。

### D.4 `budget_operations` 幂等表（字段扩充）
按 E.0 §7.3 落表，并**为崩溃恢复扩充** `new_commitment` 与 `receipt_blob`：
```
budget_operations
  operation_id            PRIMARY KEY
  budget_id, period_id, binding_digest, metering_quote_digest
  transition_digest, nullifier, committed_version, new_commitment  -- 重建 unsigned_payload 所需
  receipt_blob            -- 完整 E1TransitionReceipt 序列化原文（含签名），用于原样恢复
```
### D.5 三件事同一事务
在**同一个** `BEGIN IMMEDIATE` 事务内完成：插入 Nullifier → 更新 `current_commitment`/`current_version`（带 `current_commitment` 条件的 CAS）→ 插入 `budget_operations` 全行（含 `receipt_blob`）。任一步失败整体回滚，杜绝「状态已扣、操作记录/回执未留」的半提交。

### D.6 崩溃恢复闭环（「已提交但未签发/返回回执」）—— 本阶段最关键的工程结论

**为什么签名只能在事务内完成**：`unsigned_payload` 含 `state_version`（CAS 的 `next_version`）与 `new_commitment/nullifier`——这些是 CAS 事务的**产物**，只有事务内才知道最终值。因此签名消息必须基于 CAS 后的最终值计算；把签名推迟到 `commit` 之后，会让「已提交但尚未签名」成为可崩溃的真实中间态。

**实现的原子化顺序**（`submit_transition_e1` 事务内）：
1. CAS：重查 `C_old`、查 `N` 未用、插 `N`、条件 UPDATE 得 `next_version`；
2. 用最终状态字段组装 `unsigned_payload` → 算 `transition_digest` → 用 Coordinator 私钥签 `coordinator_signature` → 得到完整 `E1TransitionReceipt`；
3. 把该回执序列化为 `receipt_blob`，连同全部业务字段写入 `budget_operations`；
4. `tx.commit()`；
5. 返回回执。

**崩溃点全覆盖**：
- **commit 前崩溃**（含 CAS 后、签名中、写 `budget_operations` 中）：事务整体回滚 → 无状态推进、无 Nullifier、无操作记录 → 上层重试走完整 §E 流程，不产生半提交。
- **commit 后、返回前崩溃**：状态、Nullifier、`budget_operations`（含 `receipt_blob`）已原子落库 → 重启后用原 `operation_id` 调 `get_operation`，从 `receipt_blob` **原样读出**返回，得到字节相同的回执与签名。

**重启后的验证（不把本地记录当来源认证）**：读出 `receipt_blob` → 重算 `transition_digest` 与回执内比对 → 用可信配置公钥验 `coordinator_signature` → 逐字段核对 `binding_digest/metering_quote_digest/状态字段` 与当前 DB 行一致 → 全通过才返回；任一失败 → `IDEMPOTENCY_CONFLICT`，失败关闭。

**深层防御**：签名用标准确定性 Ed25519（相同密钥+消息 → 相同签名），即便退化为「重建 `unsigned_payload` 后重签」也可得字节相同回执；但首版以「事务内存 `receipt_blob`」为主路径，不依赖签名确定性作为唯一保障。`coordinator_key_id` 必须指向稳定密钥；若密钥轮换，旧回执按留存原文返回而不是用新钥重签。

### D.7 幂等与拒绝规则
- 同 `operation_id` + 全摘要一致 → 返回留存回执（§D.6 验证后）；
- 同 `operation_id` + 不同 `binding_digest`/`metering_quote_digest`/`c` → `IDEMPOTENCY_CONFLICT`，拒绝且不复用旧凭据；
- 未提交成功的请求不留下 `budget_operations` 记录；
- 已提交请求不得二次消费同一份状态（Nullifier 唯一约束兜底）。

### D.8 对已知非阻断项的处理
E1.3 实现时把 `state_store.rs` 中 `u64→i64` 的 `unwrap_or(i64::MAX)` 改为显式 `try_from` 错误处理，使持久化版本与返回版本一致；属 E1.3 内 additive 改动，不在本轮执行。

## E. Saga 与故障恢复（任务包 E）

### E.1 严格沿用的顺序
```
预检 → Metering Attestation → Halo2 Proof → D10 Budget Admission
     → D11 State Transition → Executor Final Binding Check → Tool Dispatch → Execution Receipt
```

### E.2 逐步骤故障语义

| 步骤 | 成功状态 | 失败状态 | D10 操作额度 | D11 加权预算 | 允许重试 | 重试须核对摘要 | 允许工具执行 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 预检 | binding/授权/快照就绪 | 授权缺失/绑定冲突 | 未扣 | 未扣 | 是（修正数据后） | `binding_digest`、`executor_authorization_digest` | 否 |
| 2 Metering Attestation | 已签发含 `c` 的 Attestation | 策略不匹配/`c` 越界/验签失败 | 未扣 | 未扣 | 是（同 `operation_id` 重算须得同 `c`） | `metering_quote_digest` | 否 |
| 3 Halo2 Proof | 真实证明生成，公开输入含该 `c` | proof 生成失败/公开输入不一致 | 未扣 | 未扣 | 是 | `instance`（8 行）、`metering_quote_digest` 中的 `c` | 否 |
| 4 D10 Admission | 取得签名 Budget Receipt（`request_digest = D_E`） | 额度不足/冲突/服务异常 | **成功后 +1；失败不扣** | 未扣 | 是（D10 operation 幂等 + `INDETERMINATE`） | `request_digest == D_E`、`operation_id` | 否 |
| 5 D11 Transition | CAS 成功，回执随状态原子落库 | 证明无效/`C_old` 过期/`N` 重复/服务崩溃 | **D10 已扣不退款** | **成功后 +c；失败不扣** | 是但走幂等（§D.6/§B.6） | `operation_id` 全摘要 + 回执验签 | 否 |
| 6 Final Binding Check | 5 项等价关系全部成立 | 任一摘要不等/验签失败 | 已扣 | 已扣 | 否（失败关闭，不伪造回执） | E.0 §6.2.1 规则 1–5 | 否（硬前置门） |
| 7 Tool Dispatch | 执行确定性本地工具，得结果 | 工具异常 | 已扣 | 已扣 | 否（按 `FAILED` 回执留存，不重跑） | `binding_digest`、`operation_id` | **仅此步允许** |
| 8 Execution Receipt | 生成 v2 回执 + 联合审计记录 | 落库失败 | 已扣 | 已扣 | 幂等返回留存回执 | `budget_receipt_digest`、`transition_digest`、`metering_quote_digest`、`execution_receipt_digest` | 已完成 |

### E.3 不变量（不可协商）
- 工具 dispatch **只能**发生在步骤 6 通过之后；两份预算回执都验过是硬前置门（E.0 §5.2）。
- 不退款：D10 成功而 D11 冲突时 D10 操作额度仍被消耗，如实上报，不得隐藏或补偿退款。
- 无跨库原子：D10/D11 不同数据库，用可恢复 Saga，不声称分布式事务（E.0 §7.1）。
- 恢复不得绕过：只有 D10 已扣而 D11 无记录时，不伪造 D11 回执，按不退款上报（E.0 §7.4）。
- 联合审计记录不新增签名凭据，只复用四个摘要并按 E.0 §6.2.2 逐项核对；共享 `operation_id` 不构成密码学绑定。
