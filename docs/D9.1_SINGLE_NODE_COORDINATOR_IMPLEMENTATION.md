# D9.1 — Single-Node Online Budget Coordinator Reference Implementation

**Status:** Initial reference implementation; not frozen and not production-ready
**Repository:** `kaikai-cao/online-agent-budget-lab`
**Design baseline:** D9.0 Online Global Budget Coordination proposal
**Offline dependency baseline:** `kaikai-cao/offline-agent-budget-lab` at `10577ab5d53181aef522b7c8f920e4dc7251a124`

## 1. Scope

D9.1 implements the first network-facing Online reference model: one logical HTTP Coordinator process owns one authoritative SQLite WAL database. Multiple independent Gateway clients send authenticated requests to that process. The database file is not shared with, mounted by, or directly opened from any Gateway.

D9.1 does not modify the frozen Offline repository. The Online adapter implements the broker-facing methods expected by the D8.2 E4.8.3 Gateway (`binding_for_execution_grant` and `consume_for_grant`) and provides deterministic remote Coordinator identity labels for the frozen Gateway's Broker identity hasher. These labels are identifiers only; they are not local Coordinator storage paths.

## 2. Implemented protocol objects

### 2.1 Online Global Lease Grant v4

`OnlineLeaseGrant` is Issuer-signed and binds:

- `issuer_id`, `grant_id`, `lease_id`, `nonce`;
- `global_budget_id`, per-Lease `quota_limit`;
- `issued_at`, `expires_at`, `coordinator_audience`;
- sorted `allowed_gateway_ids`;
- `subject_id`, `context_digest`, and sorted `tool_name -> schema_hash` permissions.

The Coordinator independently verifies the Issuer signature and exact v4 schema. The v3 Offline Lease Grant is not reinterpreted or modified.

### 2.2 Execution Grant v2

The Coordinator verifies an E4.8.3-compatible Execution Grant v2. It checks the signature and requires the common authorization fields to match the registered Online Lease Grant. The Execution Grant audience must match the authenticated Gateway ID and its `operation_id` must equal the consume request's operation ID.

### 2.3 Gateway request authentication

Every POST request uses a canonical signed envelope containing:

```text
(envelope_version, gateway_id, HTTP method, exact API path, payload)
```

The Coordinator verifies the Ed25519 signature against its enrolled Gateway key registry before dispatching the request. The caller cannot submit a public key or select an alternative trust root in the envelope.

A timestamp/one-use nonce is not used in this version. Replaying an identical signed request is safe for the state-changing endpoints because registration/revocation are idempotent and consume is bound to a global operation ID plus the full immutable authorization/request tuple. TLS remains required for non-loopback deployment.

## 3. HTTP API

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/health` | Minimal Coordinator health/epoch information |
| POST | `/v1/leases/register` | Verify and register Online Lease Grant v4 |
| POST | `/v1/leases/revoke` | Verify and apply an Issuer-signed revocation |
| POST | `/v1/leases/lookup` | Return current Lease registration state to an authorized Gateway |
| POST | `/v1/budget/consume` | Atomically consume one global unit and return a signed receipt |
| POST | `/v1/budget/lookup` | Return the stored receipt for an operation owned by the calling Gateway |

All POST request bodies are bounded and authenticated. Error responses use stable machine-readable codes, including `GLOBAL_BUDGET_EXHAUSTED`, `LEASE_CAP_EXHAUSTED`, `LEASE_INACTIVE`, `OPERATION_BINDING_CONFLICT`, `GATEWAY_UNAUTHENTICATED`, and `COORDINATOR_INDETERMINATE`.

## 4. Coordinator transaction and linearization point

One `POST /v1/budget/consume` request follows this order:

1. Verify Gateway request signature and enrolled identity.
2. Verify Online Lease Grant v4 and Execution Grant v2 Issuer signatures.
3. Verify Coordinator audience, Gateway allowlist, Lease/Grant identity, subject, context, quota cap, validity, and tool/schema permissions.
4. Begin SQLite `BEGIN IMMEDIATE` transaction.
5. Look up `operation_id` first. Exact committed replay returns the exact stored signed receipt; a different Gateway, Lease, Grant digest, Execution Grant digest or request digest is rejected.
6. For a new operation, check the current Lease state and expiry, Execution Grant validity, `U_i < Q_i`, and `S < G`.
7. Increment `U_i` and `S`, allocate the next global sequence, store the operation, and store the exact signed Coordinator Budget Receipt in the same transaction.
8. Commit. **The successful transaction commit is the linearization point.**

A crash before commit leaves no partial budget usage. A crash after commit but before the HTTP response is handled by retrying the same operation ID and exact tuple. The Coordinator never relies on a Gateway-side counter or cached remaining balance.

## 5. Online v1 quota semantics

Online Lease registration does not reserve global quota. `quota_limit` is a per-Lease consumption ceiling. The sum of Lease caps may exceed the global ceiling:

```text
0 <= U_i <= Q_i
S = SUM(U_i)
0 <= S <= G
```

No fairness or minimum-share guarantee is provided. A Lease may be unable to consume its full cap if other Leases consume the global pool first. This deliberate semantic change improves utilization under online coordination; it does not alter the frozen Offline v1 pre-reservation rules.

## 6. Coordinator Budget Receipt

The Coordinator signs a receipt binding:

- Coordinator ID/key ID and budget epoch;
- global sequence;
- authenticated Gateway ID and Lease ID;
- Online Lease Grant digest and Execution Grant digest;
- operation ID and request digest;
- per-Lease used count, global used count and commit timestamp.

`OnlineBudgetClient.consume()` verifies this signature and its expected bindings before returning. The Gateway adapter persists the full verified Coordinator receipt in a Gateway-local SQLite receipt cache.

The frozen E4.8.3 Gateway receipt schema does not have a field for the Coordinator receipt digest. To avoid editing the frozen Offline code, the adapter exposes `build_receipt_chain()`: it creates an additional Gateway Ed25519 signature linking the exact Coordinator receipt digest to the E4.8.3 execution receipt digest. Consumers can verify the chain with `verify_online_receipt_chain()`. A standalone E4.8.3 receipt without this additional link does not itself contain the Coordinator receipt digest.

## 7. Timeout and Coordinator outage behavior

- A transport timeout or HTTP 5xx is treated as **unknown outcome**, not as a definite denial. The caller must retry the same operation ID and exact payload.
- Exact Coordinator receipt already persisted in the Gateway adapter's local cache may be replayed locally after Coordinator outage. The cache re-verifies the Coordinator signature and exact Gateway/Lease/Grant/operation/request binding.
- The adapter also persists the signed Grant pairing. After Gateway process restart, an exact cached committed operation can be reconstructed and resumed without a Coordinator round trip.
- A new operation without a cached Coordinator receipt cannot consume while the Coordinator is unreachable. The adapter fails closed; it has no offline fallback.

The local receipt cache is recovery evidence, not an independently spendable budget ledger. It cannot authorize a new operation.

## 8. Persistence model

Coordinator tables:

- `budget_meta`: immutable epoch, global cap, global used count, next sequence, Issuer key digest, Coordinator signing identity, health.
- `gateways`: enrolled Gateway ID, public key, key digest and enabled state.
- `leases`: signed grant, immutable per-Lease cap, usage, validity, Gateway allowlist and lifecycle state.
- `operations`: globally unique operation ID and exact binding tuple, sequence and accounting snapshot.
- `receipts`: canonical receipt payload, signature and receipt digest.
- `revocations`: signed revocation digest and timestamp.

Gateway-local adapter cache:

- `grant_bindings`: exact Execution Grant v2 / Online Lease Grant v4 pair for restart recovery.
- `coordinator_receipts`: full signed Coordinator receipts for exact replay and receipt-chain construction.

Both stores use SQLite WAL and `synchronous=FULL` in this software model. The Coordinator database must remain local to the Coordinator host.

## 9. D9.1 validation evidence

The local reference implementation was tested in the build environment with:

```text
python -m unittest discover -s tests -v
Ran 15 tests ... OK
```

The 15 tests cover:

1. overlapping per-Lease caps without pre-reservations;
2. two Gateway identities racing for the final global unit;
3. exact duplicate HTTP requests returning the same signed receipt;
4. global operation-ID collision across Leases/Gateways;
5. revocation/consume commit ordering and exact replay;
6. expiry and committed replay semantics;
7. Gateway allowlist enforcement;
8. tampered Gateway request signature rejection;
9. Coordinator receipt tampering rejection;
10. Coordinator restart and durable exact replay;
11. fail-closed transport unavailability;
12. Execution Grant signature/operation binding rejection;
13. Execution Grant expiry rejection for new work;
14. Online adapter receipt verification, durable local cache, receipt-chain verification and offline exact replay;
15. independent Gateway OS processes sharing one Coordinator and racing for the final budget unit.

These are implementation regression tests, not formal verification or production security certification.

## 11. Explicit limitations and D9.2 work

- One logical Coordinator and one database; no replicated Coordinator, leader election, consensus, HA or multi-region operation.
- The built-in server is plain HTTP for local tests only. A non-loopback deployment needs a TLS reverse proxy or a proper HTTPS server, firewalling and key management.
- Gateway public-key enrollment is static. Rotation/revocation workflows, rate limiting, authorization of administrative controls and audit export are not productionized.
- Coordinator and Gateway signing keys are software-held in this prototype; no KMS/HSM, TPM or TEE custody.
- SQLite WAL has a same-host database boundary. Remote Gateways access the HTTP API only, never the SQLite file.
- The Coordinator is trusted. A malicious Coordinator or administrator who can alter its code, signing key and database is outside this model.
- No fairness, reserved shares, variable-cost consume, refunds or quota reclamation.
- External tool exactly-once semantics still depend on the provider's enforceable idempotency or authoritative lookup contract.

D9.2 should add delayed/dropped/reordered response tests, kill/restart during transaction boundaries, cross-process duplicate operation-ID races, consume/revoke races, Coordinator key/configuration drift tests, and a more explicit HTTP security boundary. D9.1 remains an initial reference implementation, not an Online freeze.
