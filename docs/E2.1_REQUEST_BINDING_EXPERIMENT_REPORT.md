# E2.1 — Agent Exec Binding 请求绑定安全有效性实验报告

> **实验性质**：受控对照实验（security-effectiveness experiment），不是形式化安全证明，不是性能基准，也不是对所有 ACL / Capability 系统的普遍比较。
> **基线**：`467fa249c2c7f6971dd9f217ce0827e6f7bfc995`（E1.9 Final Acceptance 后 `main` HEAD）。
> **分支**：`exp/e2.1-request-binding`。
> **数据来源**：全部指标来自 `experiments/e2_1_request_binding/results/run-001/`（`trials.csv` / `summary.json` / `raw.json`），由 `run_experiment.py --trials 10` 实际执行生成；本报告不含任何预填期望值，不手工修改任何原始数据。
> **样本数**：`N = 10`（当前受控实验样本数）。`0/10` 不等于统计意义上的攻击成功概率为零。
> **生成时间**：见 `raw.json.meta.generated_at`。

## 0. 一句话结论

在「同一工具、同一 Schema、同一授权身份、仅替换参数值」这一具体且可复现的场景中，以**相同攻击时机、相同样本数（每组 10 次）**的主对照比较：

- **只绑定工具范围（Static ACL / v1 签名）**：10/10 攻击请求被接受，10 次未授权副作用。
- **完整 E1 的精确参数绑定（v2 + 四门禁，G3-C2）**：10/10 攻击请求在工具产生副作用前被拒，0 次 dispatch、0 次未授权副作用。
- **G3-C1（Admission 前篡改）**单独报告：10/10 在 Runtime 预检查被拒，0 次 dispatch，D10/D11 均未提交。

这组数据说明：在该替换场景下，精确参数绑定提供了工具范围级授权所没有的保护；但它只是一个受控机制实验，不构成形式化安全证明，也不代表普遍安全保证。

## 1. 研究问题与实验设计

### 1.1 问题
一份已签发的工具授权，能否阻止攻击者在授权后替换参数，使工具执行未被该授权精确绑定的操作？

### 1.2 受保护工具与攻击输入
复用生产工具 `invoice_review`；正常参数 `INV-E16-SYSTEM`，攻击参数 `INV-E16-ATTACK`。两者工具名相同、Schema 结构相同、都通过 `registry.validate()`，仅参数值不同——排除了「Schema 校验拦截攻击」的干扰。

### 1.3 副作用观察
`StatefulEffectRegistry` 继承生产 `LocalToolRegistry`，schema/validate 不变，仅在真实 dispatch 后记录 `{"operation":"invoice_review","invoice_id":<实际值>}`。观察对象是**攻击参数是否真的到达工具并造成状态变化**，不是异常类型或 DENY 返回值。

本报告在表述上严格区分三件事，不混为一个指标：
1. **请求被拒绝**（授权/门禁层判定）；
2. **未发生 dispatch**（工具从未被调用）；
3. **未发生外部副作用**（本实验工具为本地确定性工具，dispatch 即写入本地状态；真实外部 API 副作用不在本实验范围）。

### 1.4 三组对照（G1/G2 为实验参考基线，非完整竞争系统）

| 组 | 机制 | 实现 |
|---|---|---|
| G1 | Static ACL + Schema | 工具白名单 + `registry.validate()`，无参数值绑定 |
| G2 | Signed Tool-Scope (v1) | 真实 `issue_executor_authorization()` 不传 arguments 签 v1；`verify_executor_authorization()` 不启用 `require_argument_binding` |
| G3 | Full E1 (strict v2) | 真实 `TrustedToolExecutor(e1_required=True)` + `authorization_required` + `execute_e1()` 四门禁 + 真实 Rust `e1_service` |

## 2. 场景与样本

- **A 正常**：授权参数 = 执行参数 = `INV-E16-SYSTEM`，每组 10 次。
- **B 授权后参数替换**：授权 `INV-E16-SYSTEM`，执行 `INV-E16-ATTACK`，G1/G2 各 10 次。
- **C1 Admission 前篡改**（G3）：签 v2 授权后改 `ctx.arguments` 再 `h.run()`，10 次。
- **C2 Admission 后、最终门禁前篡改**（G3）：正常 `h.run()` 得 `PendingExecution`，再 `dataclasses.replace(pending, arguments=ATTACK)` 交 `execute_e1()`，10 次。
- **D exact replay**（G3）：正常操作重复提交，10 次。

每个样本使用唯一 `operation_id` 与独立 harness（独立 D10 lease / D11 DB / Rust 服务），不把同一 operation_id 的重复调用伪装为独立样本。确定性机制实验，`N = 10`，**不做统计显著性或置信区间推断**。

## 3. 指标定义

| 指标 | 定义 |
|---|---|
| Unauthorized Effect Rate | `Unauthorized Effects / Attack Attempts`（核心指标） |
| Attack Rejection Rate | `Denied Attack Attempts / Attack Attempts` |
| Benign Acceptance Rate | `Accepted Benign Requests / Benign Requests` |
| Dispatch Count | 真实进入工具 dispatch 的次数（与副作用事件分别记录） |
| Admission 状态 | D10 / D11 是否提交；C1 与 C2 必须区分 |

## 4. 实验结果（run-001，N=10）

### 4.1 主对照（相同攻击时机、相同样本数）

主对照只用**相同攻击时机、相同样本数**的组：G1、G2 各 10 次参数替换样本，分别与 **G3-C2 的 10 次 Admission 后篡改样本**比较。

| 组（主对照） | Benign Acceptance | Attack Accepted | Attack Rejection | **Unauthorized Effect Rate** | Dispatch（正常 / 攻击） |
|---|---|---|---|---|---|
| G1 Static ACL + Schema | 10/10 (1.00) | **10/10** | 0/10 (0.00) | **10/10 = 1.00** | 10 / 10 |
| G2 Signed v1 (tool-scope) | 10/10 (1.00) | **10/10** | 0/10 (0.00) | **10/10 = 1.00** | 10 / 10 |
| **G3-C2 Full E1 (strict v2)** | 10/10 (1.00) | **0/10** | 10/10 (1.00) | **0/10 = 0.00** | 10 / 0 |

> **口径说明**：G3-C1（Admission 前篡改，10 次）**不并入主对照**，单独在 §4.2 报告。禁止把 G3 的 C1+C2 共 20 次直接与 G1/G2 各 10 次放在同一主对照列中——两者攻击时机不同（C1 在 Admission 前、C2 在 Admission 后），合并会破坏对照的可比性。

解读：
- G1/G2 的攻击参数全部通过静态检查 / v1 签名验证，并**真实写入受保护工具状态**（`INV-E16-ATTACK` 出现在 effect 记录中）。
- G2 的 v1 授权 payload 版本为 `1` 且**不含 `arguments_digest`**（由测试用例 `test_04` 直接断言），因此无法区分 `INV-E16-SYSTEM` 与 `INV-E16-ATTACK`。
- G3-C2 的攻击请求 10/10 被拒、工具 dispatch=0、未授权副作用=0。

### 4.2 G3 两个篡改时机（C1 / C2）——C1 单独报告

| 场景 | 尝试 | 拒绝 | 拒绝阶段与原因 | D10 Admission | D11 Transition | 工具 dispatch | Receipt |
|---|---|---|---|---|---|---|---|
| **C1 Admission 前** | 10 | 10 | Runtime 预检查：`ExecutorAuthorizationError: arguments digest in Executor Authorization differs from the current request` | **未发生**（`global_used=0, operations=0, lease_used=0`） | **未发生** | 0 | 无 |
| **C2 Admission 后** | 10 | 10 | Executor 最终门禁：`ToolExecutionDenied: E1 grant/authorization gate failed: actual dispatch arguments differ from ToolCallBinding` | **已提交** | **已提交**（`version=1` 保持） | 0 | 无（`NO_RECEIPT`） |

C1 与 C2 的区别本身就是证据：**篡改发生在 Admission 前还是后，决定了 D10/D11 是否已提交**，但两者都在工具 dispatch 之前被拒，均未产生未授权副作用。

**关键诚实边界（C2）**：
- D10/D11 的 Admission **在最终门禁拒绝后不自动回滚**，状态保持已提交（`version=1`）。**Admission 成功不等于工具执行完成**。
- 当前实现**不提供预算退款/返还机制**（生产代码与 Rust 服务中不存在 refund 逻辑，只有 SQLite 事务 rollback）。因此最终工具执行被拒后，已消耗的 D10 预算单位**不会自动退款**。这是明确的 Saga 窗口，不能写成「所有资源消耗均未发生」。
- C2 中「请求被拒」「未发生 dispatch」「未发生外部副作用」三件事同时成立，但它们是不同层面的判定，不能互相替代作为单一指标。

### 4.3 Exact replay

10/10 样本重复提交返回**完全相同**的原始 Receipt（`IDENTICAL=True`），首次 dispatch=1、replay 后仍为 1（未增加）。这只说明**在本次受控测试的本地确定性工具路径下**，幂等分支返回原件且不产生第二次分发；**不扩展为任意外部系统的 exactly-once 保证**。

---

## 5. 拒绝原因真实性核验

G3 两类攻击的拒绝并非来自无关失败，而是精确命中参数绑定校验：

- C1：`arguments digest in Executor Authorization differs from the current request`——Runtime 重算被篡改参数的摘要，与 v2 授权签名摘要不符，在 D10 Admission 之前 fail-closed。
- C2：`actual dispatch arguments differ from ToolCallBinding`——D10/D11 已提交，但 Executor 最终门禁用原始 binding 校验被替换的 `pending.arguments`，在 dispatch 之前拒绝。

两类差异共同说明：精确绑定同时覆盖「Admission 前的授权预检查」与「Admission 后的最终执行门禁」两道关口。

## 8. 边界与不外推事项

- **样本数 `N = 10`** 是当前受控实验样本数；`0/10` 不等于统计意义上的攻击成功概率为零。
- 本实验是**具体场景的受控机制实验，不是形式化安全证明**，也**不是对所有 ACL 或 Capability 系统的普遍比较**。
- 本实验只验证「工具参数值替换」这**一个具体场景**下的执行绑定效果。
- G1/G2 是隔离比较授权绑定性质的实验参考实现，不是完整竞争系统，不做四组端到端性能优劣结论。
- 不开展性能基准；不引入真实 LLM / AgentDojo；不做多实例唯一执行；不实现抗回滚；不改 Halo2/D11 电路；不改 Journal Service。
- 不声称 exactly-once（exact replay 只说明本地测试中未增 dispatch）；不声称全面抵御 Prompt Injection；不新增生产代码功能。
- C2 的 D10/D11 Admission 在最终门禁拒绝后**不自动回滚、不自动退款**，是有明确记录的 Saga 窗口；Admission 成功不等于工具执行完成。
- 区分「请求被拒」「未发生 dispatch」「未发生外部副作用」；本实验工具为本地确定性工具，真实外部 API 副作用不在观察范围内。
