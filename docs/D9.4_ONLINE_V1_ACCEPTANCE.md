
# D9.4 — Online v1 Integration Acceptance

**Status:** Accepted as a single-node research reference implementation
**Validated baseline:** `69dac31`
**Scope:** Full test suite, strict ResourceWarning run, isolated HTTP smoke test, and existing Adapter integration coverage

## 1. Acceptance objective

D9.4 evaluates whether the Online v1 implementation is sufficiently integrated and regression-tested to be frozen as a bounded single-node reference implementation.

This acceptance does not claim production readiness, formal verification, or completion of a full Agent-to-external-tool execution system.

### 2.3 Existing Adapter integration coverage

The existing test `test_online_adapter_exposes_verified_global_budget_receipt` exercises the Online adapter path, including:

- Binding an Execution Grant to an Online Lease Grant.
- Registering the Lease through the authenticated Client.
- Consuming budget through `consume_for_grant()`.
- Verifying the returned Coordinator receipt.
- Reading the locally cached verified receipt.
- Building and verifying a Gateway–Coordinator receipt chain.
- Replaying a previously committed operation after Adapter reconstruction while the Coordinator is unavailable.
- Rejecting a new operation when the Coordinator is unavailable and no committed receipt exists for that operation.

The Gateway execution receipt used in this test is constructed by the test. This test validates receipt binding and adapter integration; it is not evidence that a real external tool was executed.

## 3. Security and accounting properties covered by the implementation and tests

The implementation and regression tests cover the following areas:

- Atomic global and per-Lease budget admission under the single-Coordinator SQLite transaction model.
- Idempotent operation handling and rejection of operation-ID rebinding.
- Cross-thread and cross-process contention for limited budget.
- Recovery after a lost HTTP response and exact retry of a committed operation.
- Selected process-termination and transaction rollback behavior.
- Consume/Revoke ordering and Lease expiry boundaries.
- Gateway authentication and authorization checks.
- Coordinator receipt signature and binding verification.
- Gateway disable persistence and serialization with admitted operations.
- Startup rejection when logical ledger invariants are corrupted.
- Coordinator identity and budget-epoch binding on operation lookup.
- HTTP request framing, body-size, content-type, and loopback binding restrictions.

These are implementation and test results under the declared model. They do not establish security against every possible fault, malicious host, or adversarial administrator.

## 4. Explicit trust assumptions and limitations

### 4.1 Trusted Gateway/Tool Adapter semantics

The Coordinator receives an opaque request digest. It does not independently reconstruct or verify the tool name, schema hash, and canonical arguments that produced that digest.

The trusted Gateway/Tool Adapter is responsible for validating the tool invocation and computing the correct request digest.

Consequently, a Coordinator Budget Receipt proves the Coordinator's recorded budget admission and request-digest binding. It does not independently prove which external tool was invoked or what result that tool produced.

### 4.2 Database rollback

The logical invariant checker can detect many internally inconsistent database states. It cannot detect restoration of an older, internally consistent database snapshot without an external monotonic anchor or witness.

### 4.3 Deployment and availability

The validated implementation is a single-node Coordinator using a local SQLite WAL database. It does not provide replication, consensus, high availability, or multi-region operation.

The built-in HTTP server is for loopback development. A remote deployment requires separately designed TLS termination and network hardening.

### 4.4 External tool effects

The current acceptance does not establish exactly-once execution of arbitrary external tools. Such guarantees require tool-side idempotency or an authoritative mechanism for determining whether an external effect has already occurred.

## 5. Acceptance decision

The D9.4 evidence supports the following bounded conclusion:

**Online v1 is accepted as a single-node research reference implementation for transactional global budget coordination, authenticated Gateway admission, signed budget receipts, and the tested retry/recovery behaviors.**

The following claims are not made:

- The system is production-ready.
- The Coordinator is replicated or highly available.
- The Coordinator independently proves the semantic correctness of a tool invocation.
- The receipt proves successful execution of an external tool.
- The system detects all forms of database rollback.
- The system provides arbitrary external-tool exactly-once effects.
- The implementation has been formally verified or comprehensively penetration-tested.

## 6. Freeze boundary

The D9.4 acceptance closes the current Online v1 implementation scope.

Further work should be treated as a separately scoped stage, rather than appended to this acceptance retroactively. Potential future work includes:

- A real Agent/Gateway/Tool Adapter execution demonstration.
- A versioned ToolCallBinding protocol if independent tool-call semantic binding is required.
- An authenticated Coordinator administration and key-lifecycle design.
- External anti-rollback anchoring.
- A separately evaluated remote deployment architecture.

No such extension is implied to be implemented by this acceptance.
