## 1. Scope and Design Decision

### 1.1 本设计要回答的唯一核心问题

> 当 Executor 不再可信时，它是否仍然无法单方面修改、伪造或重写 Journal 的可信历史？

E1.9-A 已经在**组件层**实现了 Journal 的追加、签名链、Checkpoint、恢复与完整性校验，但 E1_9_A §1.2 / §7 已诚实记录：
"独立文件 + 独立密钥"只提供组件隔离与就地篡改检测，Journal 文件与 Executor 数据库处于同一文件系统、同一 OS 主体、同一备份域，
能恢复 Executor 库的攻击者同样能整体换回 Journal 旧文件（连同当时有效的旧签名一起通过本组件的全部验证）。
本设计要补的正是这道**部署层信任边界**：用 OS 账户与文件权限，把"能回滚 Executor 库的主体"与"能改写 Journal 存储/密钥的主体"分开。

### 1.2 采用的架构决策

**独立 Journal 服务 + 独立操作系统账户 + 独立数据目录与密钥权限。**

四条核心原则（贯穿全文，所有接口与权限设计都不得违反）：

1. Executor **不能直接读写** Journal SQLite 文件（无论读、写、删、替换、快照恢复）。
2. Executor **不能读取** Journal Ed25519 私钥（无论读、复制、导出）。
3. 所有 Journal 写入必须经 Journal 服务完成；Executor 只能通过受限 IPC 接口提交请求。
4. Journal 服务**独立验证**签名、seq 连续性、哈希链与 Checkpoint，**不信任 Executor 提供的任何历史状态**
   （seq / prev_digest / 链头 / 既有 Checkpoint 一律由服务端权威状态决定）。

### 1.3 为什么不采用其他方案（本阶段明确不选）

| 方案 | 本阶段结论 | 理由 |
|---|---|---|
| **localhost HTTP 服务** | 不选做第一版 | 监听 localhost **不等于身份认证**；其他本机进程同样可连接。若用 HTTP，必须额外做调用方认证；HTTP 栈的认证/ACL 能力不如 OS 原生 IPC 直接。本设计保留未来在 HTTP 上做 mTLS/Windows 认证的可能，但第一版优先 OS 级访问控制。 |
| **配置文件共享 Token** | 明确禁止单独使用 | 共享 Token 可被任何能读配置文件的进程窃取，无法区分"哪个 OS 主体在调用"，且 Token 与 Executor 账户同信任域时，账户失陷即 Token 失陷。见 §5.3 调用身份要求。 |
| **区块链** | 不选 | 引入共识、外部依赖与不可逆部署成本，超出"单机工程+明确权限边界"的目标；且并不能消除信任根（E1.8 §2.2）。 |
| **TEE（SGX/TrustZone）** | 不选 | 部署与硬件依赖重，密钥不可导出性虽有吸引力，但第一阶段不追求硬件级保证；文件 ACL 已足够表达"Executor 账户读不到私钥"这一边界（代价见 §6.5）。 |
| **远程服务器 / 独立主机** | 本阶段不部署，但保留迁移路径 | 用户明确"不急着部署远程服务器"；本设计给出从单机 ACL 迁移到独立主机的路径（§9.3），但不作为本阶段实现。 |

### 1.4 与 E1.8 / E1.9 冻结口径的关系

- 本设计不改 E1.8 / E1.9-A 的任何冻结内容；Journal Entry、Checkpoint、INTENT、RESULT 的字段与语义保持不变。
- 本文档是 E1.9 §2.2 "Journal 存储/服务形态待勘察" 的勘察结论与部署设计：把"独立文件 + 独立签名"升级为"独立服务 + 独立账户 + 独立目录/密钥权限"，
  使 E1.9 §1.4 "Journal 不可被攻击者回滚或篡改"的信任假设在**Executor 账户失陷**这一层面具备真实的部署依据。
- 该信任组件按 E1.8 §2.2 / E1.9 §1.4 要求，属**新增可信组件**，进入实现时须按 E0 级流程显式冻结其信任假设并扩充 TCB；本文档不构成实施授权。

## 2. Threat Model

### 2.1 攻击者谱系与能力假设

按权限从低到高分为六类。前五类是本阶段要处理或明确边界的对象，第六类是明确排除项。

| 编号 | 攻击者 | 能力 | 本阶段定位 |
|---|---|---|---|
| T-A | 不可信 LLM / Planner（E0 §8.2） | 构造任意请求参数、重放旧凭据/旧请求；无 OS 账户权限 | 通过 Executor 间接到达服务接口，由 §5 服务端校验约束 |
| T-B | Executor **进程**被攻破 | 以 Executor 账户身份运行任意代码，可调用 IPC、读写 Executor 自身文件 | **本阶段主要防御目标** |
| T-C | Executor **运行账户**被攻破 | 拥有 Executor 账户的全部权限，可访问该账户可读写的任何文件 | **本阶段主要防御目标** |
| T-D | 其他本机非特权进程 | 以某个普通用户身份运行，无 Executor、无 Journal 账户权限 | IPC ACL 与目录 ACL 共同拒绝 |
| T-E | Journal 服务进程/服务账户被攻破 | 以 `JRNL_SVC_ACCT` 身份运行任意代码 ⇒ 同时具备 DB 读写权 + 私钥读取权 + 以合法私钥重签能力 | **TCB 整体失陷**：本设计**不保证**（见 §2.2、§8.1、§10）；不得靠"签名密钥独立保护"或叠加本地校验来宣称历史仍可信 |
| T-F | 整台机器**管理员** | 可控制所有账户、替换服务二进制、恢复任意文件与密钥、改 ACL | **明确排除**：本阶段不抵抗，不得声称（见 §2.3） |

> T-E 的定位说明（B2-R1）：服务进程能执行攻击者代码，与该进程**合法拥有**的权限是同一件事——
> `JRNL_SVC_ACCT` 本就对 DB 有读写权、对私钥有读取权（§4.2）。因此"服务进程被控"并非只多了"签几条看似有效条目"的能力，
> 而是把 Journal 这一 TCB 组件的**全部权威能力**交给了攻击者：改写/删除/重排历史条目与 Checkpoint、用合法私钥对伪造历史重签、使本机所有自洽性校验通过。
> 这属于 Journal TCB 失陷，不属于本阶段可防御范围，详见 §2.2 场景表与 §8.1 保证矩阵。

### 2.2 逐场景分析（能否成功 / 检测 / 阻止 / fail-closed）

下表的判定基于权限矩阵（§4）与接口校验（§5）。"能否成功"指攻击者目标是否达成。

| 场景 | 攻击者 | 能否成功 | 如何检测 | 是否阻止 | 失败时 fail-closed |
|---|---|---|---|---|---|
| 直接修改 Journal DB 文件 | T-C（Executor 账户） | **否** | 目录/文件 ACL 使 Executor 账户无写权限；即使尝试，服务 `verify_integrity` 也会在读取时发现签名/链断裂 | 是（ACL 拒绝写入） | 是（服务读到异常即拒绝对外返回） |
| 读取 Journal DB 文件 | T-C | **否**（读权限同样拒绝） | ACL 审计 | 是 | 是 |
| 读取/复制/导出私钥 | T-C | **否** | 私钥目录 ACL 仅 Journal 服务账户可读 | 是 | 是 |
| 替换私钥为攻击者密钥 | T-C | **否** | 私钥目录 ACL 不可写；服务公钥注册表固定（§6.4） | 是 | 是 |
| 经 IPC 追加伪造条目（伪造 seq/prev_digest/签名） | T-B/T-C | **否** | 服务端忽略客户端提供的 seq/prev_digest/签名，自行从权威状态计算并签名（§5.4） | 是 | 是（校验失败返回错误） |
| 经 IPC 重放旧 append 请求 | T-B/T-C | **否**（不产生第二条） | 接口层按 `operation_id`+`phase` 幂等去重（§5.5），重放返回原条目而非新追加 | 是（幂等） | 是 |
| 经 IPC 回滚 Journal 数据库 | T-C | **否** | Executor 账户无 DB 写/替换权限，无法通过 IPC 触发回滚（接口无此能力） | 是 | 是 |
| 替换服务二进制/配置 | T-C | **否**（若配置/二进制目录 ACL 仅管理员+服务账户可控） | 文件完整性监控（本阶段仅记录建议） | 是（ACL） | 是 |
| 冒充 Executor 身份调用 IPC | T-D | **否** | IPC 端点 ACL 仅授权 Executor 账户 + 服务端调用身份校验（§5.3） | 是 | 是 |
| 服务进程自身被攻破（任意代码执行） | T-E | **成功**：攻击者以 `JRNL_SVC_ACCT` 身份同时取得 DB 读写 + 私钥读取，可改写/删除/重写历史并用合法私钥重签 | **无可靠检测**：重签后的伪造历史通过本机全部自洽性校验（签名/链/Checkpoint/辅助列）；无外部可信锚点则无法区分（B2-R1） | **否** | **否**——TCB 失陷，不保证 |
| 服务账户被攻破且私钥可读 | T-E | **成功**：与上同，私钥对该账户可读即等效于签名权失陷 | 同上，无独立锚点不可检测 | **否** | **否** |
| 服务私钥泄露（被读取/导出） | T-E | **成功**：任何持有该私钥者可签出自洽条目/历史 | 公钥验签仍通过，本机无法分辨签名者是否为真服务 | **否** | **否** |
| DB 与私钥均受攻击者控制 | T-E | **成功**：可构造完全自洽的伪造链 | 本机验证只查自洽不查新鲜度/真实性 | **否** | **否** |
| **恢复到旧 DB + 旧密钥（联合回滚）** | **T-F（管理员）** | **成功，且无法检测** | **无检测能力**：旧 DB + 旧密钥 + 旧签名三者自洽，本机所有验证只检查自洽性与连续性，不检查新鲜度 | **否** | **否**——必须诚实记录（§7.5、§8、§10） |

> 不得再从"服务密钥与 DB 分离且密钥未泄露"推出"服务进程失陷时仍能 fail-closed"——
> 服务进程**本身就是**被授权读取该密钥与读写该 DB 的主体；一旦它执行攻击者代码，这两个前提同时失效（B2-R1）。
> 正确的 fail-closed 边界只适用于 T-B/T-C（Executor 账户失陷，碰不到服务账户的 DB/私钥），不适用于 T-E。

### 2.3 关键区分：Executor 账户失陷 ≠ 管理员失陷

这是本设计最重要的边界，必须在任何汇报与评审中保持：

- **Executor 账户失陷（T-B/T-C）**：本设计建立了真实边界。Executor 进程/账户即使完全被控，也只能调用受限 IPC 追加合法结构的条目，
  **无法**直接读写 DB、**无法**读取私钥、**无法**伪造他人签名、**无法**回滚历史、**无法**伪造权威 seq/链头。这是本阶段可验证、可声称的安全目标。
- **管理员失陷（T-F）**：本设计**不建立**边界。管理员能控制 Journal 服务账户、替换服务、恢复 DB 与密钥到任意历史点。
  此时"账户隔离"这一前提本身被攻击者掌控，所有基于 OS 权限的保证同时失效。要抵抗管理员级攻击，需要**独立于本机的信任锚**
  （远程权威服务、独立 OS 主体 + 外部 ACL、WORM 存储、TPM/HSM 单调锚点），这些均不在本阶段范围（§10）。
- 任何"本机管理员无法回滚 Journal"的表述都是**错误的**；E1.8 §10.2、E1.9 §10、E1_9_A §1.2 均已明确"信任根只能移动不能消除"，本文档延续该口径。

### 2.4 明确排除项（本阶段不做，也不得声称）

- 不抵抗管理员级攻击、不抵抗 DB + 密钥联合回滚（T-F）。
- 不抵抗 Journal TCB 自身失陷（B2-R1）：服务进程被攻破、服务账户被攻破且私钥可读、私钥泄露、DB 与私钥均受攻击者控制——
  这四种情形攻击者都同时取得 DB 读写与私钥读取/重签能力，可重写历史并使本机校验全部通过；没有外部可信锚点时不保证可检测。
  服务账户与本阶段"独立账户"是同一信任边界的两端，若它整体失陷，需更上层锚点（§10）。
  不得通过"签名密钥独立保护"或增加更多本地完整性检查来规避这一结论——本地检查用的密钥与数据与受攻击的对象同源。
- 不解决 G1b（至多一次真实 dispatch）与任何外部副作用的 exactly-once（E1.8 §10.2）；本设计只涉及 Journal 可信历史，不裁决执行权。
- 不引入新密码学算法、不改 Entry/Checkpoint 编码、不引入区块链/TEE/远程服务器实现。

## 3. Trust Boundary and Architecture

### 3.1 架构图

```
                 Untrusted LLM / Planner  (T-A)
                            │  构造请求 / 重放凭据
                            v
              +-------------------------------+
              |   Python Executor             |
              |   account: EXEC_ACCT          |   ← 失陷目标 T-B / T-C
              |   - E1.5 四门禁               |
              |   - 仅持有 Journal IPC 客户端  |
              +-------------------------------+
                            │
                            │ Authenticated IPC（仅 EXEC_ACCT 可连，服务端校验调用身份）
                            │ append_intent / append_result / get_* / verify_integrity
                            v
   ========================= TRUST BOUNDARY =========================
              +-------------------------------+
              |  Independent Journal Service  |
              |  account: JRNL_SVC_ACCT       |   ← 唯一可写 DB、唯一可读私钥
              |  - 权威 seq / prev_digest      |
              |  - entry/checkpoint 签名       |
              |  - 全前缀 verify_integrity     |
              |  - 幂等去重 / 调用身份校验      |
              |  +---------------------------+ |
              |  | Ed25519 Private Key       | |   ← 密钥目录：仅 JRNL_SVC_ACCT 可读
              |  +---------------------------+ |
              +---------------+---------------+
                              │ 仅此服务可写
                              v
              +-------------------------------+
              | Journal SQLite DB             |   ← 数据目录：仅 JRNL_SVC_ACCT 可写
              |  journal_entries              |
              |  journal_checkpoints          |
              +-------------------------------+
   ==================================================================

   管理员 (T-F)：横跨并控制以上全部主体 —— 本设计不设防（见 §2.3 / §10）
```

### 3.2 各组件职责与信任属性

| 组件 | 职责 | 信任属性 |
|---|---|---|
| Executor（`EXEC_ACCT`） | 经 E1.5 四门禁后，用 IPC 客户端请求追加/查询；本地保留 `executions` 与 `last_applied_seq` | **不可信**（T-B/T-C 失陷目标）。其提供的一切历史状态均不被 Journal 服务采信 |
| Journal 服务（`JRNL_SVC_ACCT`） | 权威分配 seq、计算 prev_digest、签名 Entry/Checkpoint、幂等去重、调用身份校验、完整性校验 | **新增可信组件**（须 E0 级冻结、扩充 TCB，E1.8 §2.2）；本阶段设计其边界，不实现 |
| Journal SQLite DB | 持久化 `journal_entries` / `journal_checkpoints` | 存储层；**仅 JRNL_SVC_ACCT 可写**，不信任其内容 —— 读取时由服务做 `verify_integrity` |
| Ed25519 私钥 | 签发 `entry_signature` / `checkpoint_signature` | **仅 JRNL_SVC_ACCT 可读**，不可导出（文件 ACL 保护，非硬件级，§6.5） |
| OS 账户 + ACL | 实现 Executor 与服务、DB、密钥之间的强制隔离 | 单机边界的根基；管理员可控 → 对 T-F 无效 |
| IPC 通道 | Executor ↔ 服务的唯一受控通路 | 具备 OS 级访问控制；服务端校验调用身份（§5.3），不靠端口或共享 Token |

### 3.3 数据流（正常追加，对照 E1.8 §7.1）

```
Executor 完成四门禁 + G2 核验
  │
  ├─ IPC append_intent(operation_id, envelope) ──▶ 服务：鉴权 → 权威 seq=k+1 → 签名 → 写 DB
  │                                          ◀── 返回 (seq, entry_digest, entry_signature, checkpoint)
  ├─ registry.dispatch() → 原始 result（本地，不经服务）
  ├─ make_receipt() → 原始 ExecutionReceipt（本地，不经服务）
  ├─ IPC append_result(operation_id, envelope{...,result,execution_receipt})
  │                                          ──▶ 服务：鉴权 → 权威 seq=k+2 → RESULT + 新 Checkpoint → 写 DB
  │                                          ◀── 返回 (seq, entry_digest, checkpoint)
  └─ 更新本地 executions（last_applied_seq / last_checkpoint_digest）→ 返回原始 Receipt 原件
```

与服务端的调用严格遵循 E1.8 §7.1 / E1.9 §2.4 的**权威先推进、本地后推进**顺序；
A1 共享库写锁的生命周期（E1.9 §2.4）在本设计中保持不变——Journal 服务的 IPC 调用仍是"锁内的外部独立服务调用"，
不与其本地 SQLite 事务声称跨存储原子性（本设计不改变这一点）。

## 4. Account and Permission Matrix

### 4.1 账户定义（Windows 11 单机）

| 账户 | 符号 | 用途 | 类型建议 |
|---|---|---|---|
| Executor 账户 | `EXEC_ACCT` | 运行 Python Executor 进程 | 标准用户（非管理员），专用本地账户 |
| Journal 服务账户 | `JRNL_SVC_ACCT` | 运行独立 Journal 服务 | 专用本地账户或虚拟账户（如 `NT SERVICE\<name>`），最小权限、非管理员 |
| 管理员 | `ADMIN` | 安装、升级、备份、恢复、审计 | 本地管理员组；**本设计不对其设防** |

三个账户必须互不相同；尤其 `EXEC_ACCT` **不得**是 `JRNL_SVC_ACCT` 的成员，也**不得**对 Journal 资源所在目录具有任何 ACE 授权。

### 4.2 权限矩阵（核心交付物）

图例：**R**=读，**W**=写/改，**X**=执行，**D**=删除/替换，**—**=无任何权限。
"管理员"列标注为 `*` 表示管理员可绕过 ACL（取得所有权/改 ACL），这正是 §2.3 的不设防点。

| 资源 | `EXEC_ACCT` | `JRNL_SVC_ACCT` | `ADMIN` | 说明 |
|---|---|---|---|---|
| Journal DB 文件 `journal.sqlite3` | — | R/W/D | `*` | Executor 完全不可访问；仅服务可写 |
| Journal 数据目录（含 WAL/SHM） | —（无遍历权） | R/W/X/D | `*` | 目录级拒绝 Executor 遍历，防止按名访问文件 |
| 私钥文件 | — | R | `*` | 私钥**只读**即可，服务不需要写私钥；不可导出（§6） |
| 私钥目录 | —（无遍历权） | R/X | `*` | 仅服务账户可进入并读取 |
| 公钥文件（固定注册表） | R | R/W | `*` | Executor 可读公钥用于验签；写仅服务/管理员 |
| 服务可执行程序 | X | X | `*` | Executor 可执行客户端，不得改服务二进制 |
| 服务配置 | R（仅客户端连接参数，不含密钥/Token 秘密） | R/W | `*` | 配置不得包含可冒充身份的共享秘密 |
| IPC 端点（Named Pipe） | 连接（按 ACL 授权） | 创建/监听 | `*` | 仅 `EXEC_ACCT` 可连接；服务端仍校验调用身份（§5.3） |
| 本地 `executions` 库（Executor 自有） | R/W/D | — | `*` | 与 Journal 存储物理分离；服务不访问执行库 |

### 4.3 权限设计要点

1. **拒绝优先**：Journal 数据目录与私钥目录采用"默认拒绝 + 仅显式授权 `JRNL_SVC_ACCT`"的 ACL，不依赖"Executor 恰好不在某组"。
2. **目录级隔离**：不仅文件 ACL，目录本身也不给 `EXEC_ACCT` 遍历权，阻断按已知文件名直接访问。
3. **公钥与私钥分离**：公钥可公开（供 Executor 验签），私钥严格只读于服务账户。
4. **服务不访问执行库**：`JRNL_SVC_ACCT` 对 `executions` 无任何权限，保证两个信任域单向依赖（Executor → 服务），服务不回读 Executor 状态。
5. **备份/恢复路径**：备份由 `ADMIN` 或专用备份账户执行（§4.4），**备份产物本身是 T-F 联合回滚的入口**（§7.5、§10）。

### 4.4 服务升级、备份与恢复的责任主体

| 操作 | 执行主体 | 约束 |
|---|---|---|
| 服务安装/升级 | `ADMIN` | 升级不得改变 IPC 端点 ACL 与账户隔离；升级后须重新验证权限矩阵 |
| DB 备份 | `ADMIN` 或专用备份账户 | 备份含 DB 与私钥；**备份产物必须与本机信任域隔离保存**，否则成为 T-F 回滚入口 |
| 密钥备份/恢复 | `ADMIN`，按 §6 流程 | 恢复密钥须走固定公钥注册表核对，避免被换成攻击者公钥 |
| 故障恢复 | `ADMIN` + 服务重启 | 服务重启后执行全前缀 `verify_integrity`（§7.1），不信任残留缓存 |
| 权限审计 | `ADMIN` | 定期核对 ACL 未被放宽（本阶段仅列为运维要求，不实现自动检测） |

## 5. Journal Service API

### 5.1 通用约定

- 传输：Windows Named Pipe（跨平台设计保留 Unix Domain Socket 路径）。
- 每条请求携带：接口名、参数对象、调用者身份由 OS 层提供（非请求自带）。
- 服务端对**所有**请求执行：①调用身份校验（§5.3）；②参数结构校验；③权威状态计算；④错误统一返回结构化错误码。
- 服务端**绝不**接受客户端指定的 `seq`、`prev_digest`、`entry_signature`、`checkpoint_signature` 或任何"历史链状态"。客户端如提供这些字段，服务端一律忽略或在严格模式下拒绝。

### 5.2 接口清单

| 接口 | 作用 | 是否写操作 |
|---|---|---|
| `append_intent` | 追加一条 INTENT | 是 |
| `append_result` | 追加一条 RESULT + 新 Checkpoint | 是 |
| `get_entry` | 查询指定 `operation_id`/`phase` 的 Journal Entry | 否 |
| `get_checkpoint` | 获取指定 `seq` 的历史 Checkpoint | 否 |
| `get_head` | 获取当前可信链头 | 否 |
| `verify_integrity` | 执行全前缀完整性检查 | 否 |

### 5.3 调用身份要求（关键：不靠端口，也不靠共享 Token）

1. **OS 级端点 ACL**：Named Pipe 创建时用安全描述符限定仅 `EXEC_ACCT`（及服务自身）可连接；其他本机进程（T-D）连接被 OS 拒绝。
2. **服务端主动校验调用者**：服务在每次连接/每次请求时通过 Named Pipe 的模拟机制获取客户端进程/线程身份，
   确认其为授权的 `EXEC_ACCT`，而不是仅凭"连上了管道"就信任。这样即便管道 ACL 被临时放宽，服务端仍有一层身份校验。
3. **禁止共享 Token 作为唯一凭证**：配置文件中不得存放可冒充身份的静态 Token；若将来增加请求级认证，采用基于 OS 身份的 challenge-response 或每会话凭据，
   而非所有进程共用的明文秘密（共享 Token 与 Executor 同信任域，账户失陷即凭证失陷）。
4. **身份与 operation_id 绑定校验**：`operation_id` 应包含或关联发起方身份语义；服务端按 E1.9-A.1 已冻结的"外层 operation_id == envelope.operation_id"规则校验，
   防止身份歧义（该规则在 E1_9_A 中已对 `AuthorityJournal.append` 生效，服务接口沿用）。

### 5.4 服务端权威状态（关键：客户端不能控制 seq 与链头）

- `append_intent` / `append_result` **输入**只有：`operation_id`、`envelope`（INTENT 三字段 / RESULT 四字段，编码冻结见 E1_9_A §3）。
- **seq 分配**：服务端在事务内按 E1.9-A.3 的 `_tail_entry` 逻辑，从**已签名**的尾条目取最大签名 seq，`seq = tail.seq + 1`；
  不读取客户端提供的任何 seq，不使用未签名 SQL 辅助 `seq` 排序（延续 A.3 修复）。
- **prev_digest**：服务端取尾条目的 `entry_digest`；创世条目用 `GENESIS_PREV_DIGEST`。客户端不可指定。
- **签名**：`entry_signature` / `checkpoint_signature` 由服务用 `JRNL_SVC_ACCT` 独占的私钥生成；客户端不可提供签名结果。
- **INTENT 先于 RESULT**：服务端在 `append_result` 时检查同 `operation_id` 已有 INTENT，否则拒绝（E1.8 §7.1、E1_9_A 已实现）。
- **与 Executor 提供状态的关系**：Executor 的 `last_applied_seq`/`last_checkpoint_digest` 仅用于**查询比对**（G2，§5.6），绝不作为服务写入依据。

#### 5.4.1 Journal 签名能证明什么 / 不能证明什么（B2-R2，定义性条款）

这是 RESULT 处理的设计前提，必须在追加 RESULT 前明确：

- **Journal 签名能证明**：服务在给定的权威 seq 处**接收并记录了**特定 envelope 内容；该条目自签发后未被就地改写（哈希链 + 签名自洽）。
- **Journal 签名不能证明**：对应工具**实际被执行过**、`result` 字段反映真实执行输出、`execution_receipt` 对应真实授权/真实资源消耗。
  Journal 不执行工具、不接触被保护资源、不持有物理计量；它只是记录者。
- 因此 **"Journal 可信历史" ≠ "可信执行历史"**。不得因为条目带 Journal 签名就称其证明了执行真实性。
- 执行真实性由 E1.5 的最终门禁体系（D10 授权签名、BudgetReceipt、Metering Attestation、D11 TransitionReceipt 的组合校验）在 **Executor 侧**承担；
  Journal 服务不重复这层证明，也不得把它当作自己的保证（§5.6 `append_result`、§8.1）。

#### 5.4.2 RESULT 验证边界（方案 B 的验证设计，不重签、不改编码、不新增算法）

采用"服务端独立验证原始回执"的设计方向（B2-R2 方案 B），但严格限定其能力边界：

- **信任根**：RESULT 的 `execution_receipt` 是 E1.5 生成的 **D10 `ExecutionReceipt` v2**，由 **Executor 私钥**签名（不是 Coordinator 签名）。
  服务端用**固定注册的 Executor 公钥注册表**（由 `ADMIN` 初始化并固定指纹，运行期不可被客户端推送替换，语义同 §6.4 公钥注册）验证其签名。
  该公钥注册表是此项验证的**唯一信任根**；客户端自带的公钥一律不接受。
- **服务端在追加 RESULT 前必须验证**：
  1. envelope 字段集精确（E1.8 §5.2 四字段）、`operation_id` 绑定。
  2. **RESULT 的 `binding_digest` 必须等于已签名 INTENT 的 `binding_digest`**（从服务权威状态按 `operation_id` 取回该 INTENT，比对后才可以追加）。
  3. `execution_receipt` 的 `operation_id`、`binding_digest` 与 envelope 对应字段一致；`result_digest` 按冻结规则重算一致（`digest({"domain":"agent-tool-result-v1","result":result})`）。
  4. `execution_receipt` 签名用固定 Executor 公钥验证通过。
  5. 以上任一失败 → **拒绝追加 RESULT**（结构化错误 + fail-closed），不产生 Entry/Checkpoint。
- **不重签、不改编码、不新增算法**：服务端**不重新签发或修改**原始 `execution_receipt`（它是被承诺的既有对象），只验证；沿用 E1.5 冻结的 `ExecutionReceipt` v2 结构与现有 Ed25519/sha256 原语；E1.9-A 的 RESULT envelope 编码不变。
- **诚实的能力上限（必须同时声明）**：由于 `execution_receipt` 由 **Executor**（本阶段不可信主体 T-B/T-C）自签，服务端验签只能证明"该回执由登记的 Executor 密钥签发且字段自洽、与 INTENT 绑定一致"，
  **不能证明工具真的执行过或结果真实**——持 Executor 密钥的攻击者可签出满足全部上述检查的伪造回执。
  因此即便完成方案 B 验证，Journal 的保证仍定位为"**可信记录 + 绑定一致性校验**"，在"执行真实性"维度上明确降级为方案 A 的口径（记录服务，非真实性证明）。
  若将来引入由可信第三方（如 Coordinator 对含 result 的回执）签发的可验证凭据，可在不改 E1.9-A 编码的前提下加固，但这属于 E0 级冻结变更，不在本阶段。

### 5.5 幂等性与重试（B2-R3：内容敏感的幂等语义）

幂等键仍为 `(operation_id, phase)`，但**不得仅凭键就无条件返回旧条目**——必须同时比较完整请求内容。
比较对象为**规范化后的完整业务请求**，取冻结的 `payload_digest` 等价物：对 INTENT 用其规范的 INTENT payload，对 RESULT 用 E1.8 §5.2 的 RESULT envelope（`e1-result-envelope-v1` 摘要对象）。
不得只比较 `operation_id`（相同键、不同 payload 是冲突，不是重试）。

| 情况 | 服务端行为 |
|---|---|
| 相同 `operation_id` + `phase` + 相同规范化 payload（含相同 `payload_digest`） | **返回原 Entry**（同一 seq / digest / signature），不新增条目 |
| 相同 `operation_id` + `phase` + **不同**规范化 payload | **拒绝**，返回 `IdempotencyConflict`（fail-closed），不新增条目、不改写原条目 |
| 同一 `operation_id` 对应不同 `executor_id` 身份 | **拒绝**（身份冲突），不新增 |
| RESULT 与对应 INTENT 的 `binding_digest` 不一致 | **拒绝**（§5.4.2），不新增 |
| RESULT 无对应 INTENT | **拒绝**，不新增 |

要点：

- **重试不得产生第二条 Entry 或 Checkpoint**；内容一致返回原件、内容冲突拒绝，二者都不写日志。
- **比较覆盖完整业务请求内容**（envelope 全字段 / 冻结 `payload_digest`），不是仅 `operation_id`。
- 目的：使"重放旧请求"（T-B/T-C，§2.2）与崩溃后重试（§7）不会产生第二条日志或分叉 seq；同时阻止攻击者用同一键夹带不同 payload 来"借幂等掩盖内容篡改"。
- 该幂等语义**强化**了 E1.9-A `AuthorityJournal.append` 当前的"每次调用必追加"行为；属接口层新增能力，**不改动 `AuthorityJournal.append` 既有行为**：本阶段只设计，实现时作为**服务层新增逻辑**（幂等索引 + 内容比对），见 §11 兼容记录。

### 5.6 各接口规格

**`append_intent`**
- 输入：`operation_id`(str)，`envelope = {operation_id, binding_digest, executor_id}`。
- 身份：调用者须为授权 `EXEC_ACCT`（§5.3）。
- 服务端校验：身份；外层与 envelope 的 `operation_id` 相等；envelope 字段集精确；binding_digest 为 sha256；**内容敏感幂等**（§5.5）；权威 seq/prev_digest；签名。
- 返回：`{seq, prev_digest, entry_digest, entry_signature, checkpoint{seq, journal_head_digest, checkpoint_digest, checkpoint_signature}}`。
- 错误：身份不符 / 字段不符 → 结构化错误码；**相同键+不同 payload → `IdempotencyConflict`**（不返回旧条目、不新增）；内部异常 fail-closed。
- 重试：可重试（相同 payload 幂等返回原条目）。

**`append_result`**
- 输入：`operation_id`(str)，`envelope = {operation_id, binding_digest, result, execution_receipt}`（E1.8 §5.2 四字段）。
- 身份：同上。
- 服务端校验（按序，任一失败即拒绝且不写日志）：
  1. 身份；`operation_id` 绑定；字段集精确。
  2. **同 op 已有 INTENT**（E1.8 §7.1）。
  3. **RESULT 的 `binding_digest` == 已签名 INTENT 的 `binding_digest`**（§5.4.2）。
  4. `execution_receipt` 字段对应一致 + `result_digest` 重算一致 + 用固定 Executor 公钥验签通过（§5.4.2；信任根为固定公钥注册表，非客户端提供）。
  5. **内容敏感幂等**（相同键相同 payload 返回原件；相同键不同 payload → `IdempotencyConflict`，§5.5）。
  6. 权威 seq/prev_digest；RESULT 与 Checkpoint 签名。
  服务端**不重签也不修改** `execution_receipt`（E1.5 已签的原始回执，作为 envelope 字段被承诺），只签 Journal 自身的 Entry/Checkpoint。
- 返回：同 `append_intent` 结构（RESULT 条目 + 新 Checkpoint）。
- 错误：无前置 INTENT / binding_digest 不一致 / receipt 验签或字段不符 / 身份不符 → 拒绝；相同键不同 payload → `IdempotencyConflict`；内部异常 fail-closed。
  **注意：Journal 签名的含义仅限§5.4.1——证明"记录并校验了内容一致性"，不证明执行真实性；receipt 即使是 Executor 自签伪造也可能通过上述结构校验，真实性边界见 §5.4.2/§8.1。**
- 重试：可重试（相同 payload 幂等返回原 RESULT，不重复 dispatch——dispatch 在 Executor 本地，服务从不触发工具）。

**`get_entry`**
- 输入：`operation_id`，`phase`（可选）。
- 身份：授权 `EXEC_ACCT`。
- 校验：身份；返回条目须通过 `_verify_entry` 验签后才返回（读取即校验，延续 E1_9_A 读路径）。
- 返回：原始 Entry 对象（含 envelope 全文，供恢复取回原始 result / execution_receipt）。
- 错误：不存在 → NotFound；验签失败 → fail-closed。

**`get_checkpoint`**
- 输入：`seq`。
- 身份：授权 `EXEC_ACCT`。
- 校验：身份；核对 DB 辅助 `seq` == 已签名 Checkpoint 的 seq（E1.9-A.2 修复口径）；验签后返回。
- 返回：该 seq 的历史 Checkpoint（历史快照，非 head）。
- 错误：不存在 / 验签失败 / 辅助 seq 分歧 → 拒绝。

**`get_head`**
- 输入：无。
- 身份：授权 `EXEC_ACCT`。
- 校验：身份；按**已签名 seq** 取最大 Checkpoint（E1.9-A.2 口径），读取时逐条验签 + 核辅助 seq。
- 返回：`{seq, journal_head_digest, checkpoint_digest, checkpoint_signature}`。
- 错误：空日志 / 验签失败 → 拒绝。

**`verify_integrity`**
- 输入：无（可选 `from_seq`）。
- 身份：授权 `EXEC_ACCT`（也可供审计主体，按 ACL 扩展）。
- 校验：全前缀 seq 连续、prev_digest 链、逐条 Entry/Checkpoint 验签、operation_id 绑定、INTENT-before-RESULT、Checkpoint 绑定、辅助列一致（完整继承 E1_9_A 的 `verify_integrity`）。
- 返回：`{ok: bool, entries: int, head_seq: int, error?: code}`（不抛异常给客户端，用结构化结果）。
- 错误：任一校验失败返回 `ok=false` + 错误码；服务端同时可记录告警。
- 重试：可随时调用（只读）。

### 5.7 与 E1.8 状态机的一致性

- 追加顺序、RESULT 原始回执的"恢复而非重建"、G2 三态（BEHIND/DIVERGED/SUSPECTED，E1.8 §7.4）的判定口径全部沿用，本设计不改。
- 服务的 `get_checkpoint(seq)`/`get_entry` 正是 Executor 做 G2 "本地序号处历史检查点 vs 权威同序号"比对的数据来源；
  服务不替 Executor 判定三态，只提供已验签的历史事实（判定在 Executor 侧，按 E1.8 §7.4）。
- 本设计**不改变** A1 写锁与 Journal 操作的生命周期（E1.9 §2.4）；IPC 调用是锁内外部调用，无跨存储原子性。

## 6. Key Management

### 6.1 私钥生成

- 在服务首次安装/初始化阶段，由 `ADMIN` 在受控环境用 Ed25519 生成 Journal 签名密钥对；
  生成过程不经过 Executor，私钥不落入 `EXEC_ACCT` 可读路径。
- 私钥写入私钥目录时，文件 ACL 立即设为仅 `JRNL_SVC_ACCT` 可读（§4.2），`ADMIN` 保留恢复所需访问权。
- 该密钥是 Journal 服务专用密钥，与 D10 授权、D11 预算、E1 计量、Execution Receipt 的密钥体系均不共用（延续 E1_9_A 的独立密钥原则）。

### 6.2 是否允许导出

- **正常运行时不允许导出**：私钥目录无导出接口，服务只用它签名，不提供任何"读取私钥字节"的 API。
- 文件 ACL 保护是**软件级**的：理论上 `ADMIN` 仍能读取私钥文件。因此这里声明的是"Executor 账户不可导出"，**不是**"物理不可导出"。
- 硬件级不可导出（HSM/TPM）不在第一阶段（§1.3、§6.5）。

### 6.3 服务重启后恢复密钥

- 服务启动时从私钥目录读取私钥；读取成功才进入服务态，否则 fail-closed（不启动、不签名）。
- 重启后不信任任何内存缓存的链头：重新执行全前缀 `verify_integrity`（§7.1），从已签名数据重建权威状态。
- 私钥文件损坏或缺失 → 服务拒绝启动并告警，不自动"重新生成一把新密钥继续签名"（否则历史条目无法用新密钥验证，且与回滚难以区分）。

### 6.4 公钥注册与分发

- 公钥写入"固定公钥注册表"（公钥文件），供 Executor 验签 `entry_signature`/`checkpoint_signature`。
- 注册表初始化由 `ADMIN` 完成并校验指纹；Executor 只读该注册表。
- 分发：公钥可随 Executor 部署分发（公开信息，无保密要求）；但 Executor 必须固定其信任的公钥指纹，不能在运行期接受"服务推送的新公钥"（否则 T-B/T-C 可诱导切换到攻击者公钥）。

### 6.5 密钥轮换

- 第一阶段**不实现自动轮换**；轮换作为受控运维操作设计：
  1. 生成新密钥对；2. 公钥注册表进入"双信任窗口"（旧+新都信任）；3. 服务用新密钥签新条目、旧条目仍用旧公钥验证；
  4. 确认所有旧条目已被验证/归档后，撤除旧公钥信任。
- 旧 Journal Entry 的验证：**始终使用签发时的公钥**（按条目所属 epoch 或嵌入的 key id 选择），不用当前密钥重验历史。
- 轮换事件本身是否记入日志、如何防止"借轮换掩盖回滚"，需与 E0 级冻结一并决定；本阶段仅记录为未决问题（§10）。

### 6.6 普通文件 ACL 的安全局限（必须明确）

- 私钥保护依赖 Windows ACL，属于**OS 软件级访问控制**：`ADMIN` 或取得服务账户权限的攻击者可读走私钥。
- 因此本设计只能声称"Executor 账户（T-B/T-C）读不到私钥"，**不能**声称"私钥不可导出"或"管理员拿不到私钥"。
- 一旦私钥被 T-F 或完全失陷的 T-E 读取，攻击者可签署自洽的假历史，配合 DB 回滚形成难以检测的伪造链（§10）。
- 硬件级保护（HSM/TPM 内生成与使用、私钥不出硬件）是未来的增强方向，不在第一阶段。

## 7. Crash Recovery and Failure Handling

### 7.1 Journal 服务异常退出 / 重启

- 服务重启后**不信任内存状态**：从 DB 读取全部条目与 Checkpoint，执行全前缀 `verify_integrity`
  （seq 连续、prev_digest 链、逐条验签、Checkpoint 绑定、辅助列一致）；任一项失败 → fail-closed，拒绝进入服务态并告警。
- 链头确认按 E1.9-A.2 口径：按**已签名 seq** 取最大 Checkpoint，而非 SQL 辅助 `seq` 排序。
- WAL/SHM 文件由 SQLite 在正常恢复中处理；服务仅接受能通过完整校验的 DB 状态。

### 7.2 Executor 异常退出

- Executor 重启后以其本地 `last_applied_seq` 调用 `get_checkpoint` / `get_entry` 查询权威历史，
  按 E1.8 §7.4 三态处理（BEHIND 补齐、DIVERGED/SUSPECTED fail-closed）。
- "dispatch 后、RESULT 前"等崩溃窗口的行为完全沿用 E1.8 §7.3 / §7.5 与 E1.9 §2.4：
  按 Journal 中是否已有 RESULT 决定是否恢复原始回执，禁止 `make_receipt` 重建。
- 本设计不改变这些语义，只是把"查 Journal"从读本地文件改为经 IPC 查询服务（服务返回已验签事实）。

### 7.3 Journal 数据库被修改

- 服务每次读取/启动时执行 `verify_integrity`；任何就地篡改（改条目、改 Checkpoint、删中间记录、seq 断裂、辅助列与签名不符）
  均抛 `JournalIntegrityError` 等价于失败 → 服务 fail-closed，拒绝对外返回被篡改的历史。
- T-C（Executor 账户）本就无 DB 写权限（§4），此路径主要覆盖磁盘故障、恶意软件以其他身份写入、或 T-F 的部分篡改。

### 7.4 Executor 账户尝试回滚 Journal

- **无权限做到**：`EXEC_ACCT` 对 Journal DB/目录无写、删、替换权限（§4.2），且无 IPC 接口触发回滚（§5）。
- 即使 Executor 回滚其**自己的**本地 `executions` 库，也只是触发 E1.8 §7.4 的 G2 判定：
  服务侧历史完整，Executor 侧因落后/分歧被识别并补齐或 fail-closed。
- 这正是"Executor 账户失陷可防"的核心体现（§2.3）。

### 7.5 管理员恢复旧数据库 / 数据库与密钥联合回滚

这是本文档必须给出**不含糊答案**的问题：

> 如果 Journal 的数据库和密钥一起被恢复到旧版本，系统还有没有办法知道发生过回滚？

**答案：在本设计范围内，没有办法知道。**

- 原因：本组件的验证只检查**自洽性**（签名是否有效、链是否连续、Checkpoint 是否绑定、辅助列是否一致），
  **不检查新鲜度**（"这是否是当前最新状态"）。当 DB 与私钥被同时换回旧版本时，
  旧 DB 里的每条签名都能用旧密钥验证通过，链仍然连续，Checkpoint 仍然绑定——所有本机验证都会通过。
- 管理员（T-F）能控制所有账户、恢复任意文件、替换服务，因此"账户隔离""目录 ACL""IPC 认证"这些前提对它全部失效。
- 单机上不存在"比管理员更可信的外部观察者"能保存一份独立的最新 head 摘要用于比对；
  要检测此类回滚必须引入**独立于本机的单调锚点**（远程权威服务保存 head、WORM 存储、TPM/HSM 单调计数器，
  对应 E1.8 §4 的 B1/B3 与 §10.2），这些均超出本阶段（§10）。
- 因此：**只能检测"Executor 账户级的篡改/回滚"（因为该账户碰不到 DB 与密钥）；不能检测"管理员级的 DB+密钥联合回滚"。**
  不得把前者包装成后者（§8、§10）。

### 7.6 Journal 服务密钥丢失

- 服务启动读不到私钥 → fail-closed，拒绝启动/签名（§6.3）。
- 若密钥**永久丢失**（不可恢复）：历史条目无法再追加新 Checkpoint（新条目无法签名），
  但已存条目仍可用其历史公钥验证读取。这种情况下**不允许"重建历史信任"**——即不得生成新密钥对后宣称旧历史仍由新密钥背书。
- 正确行为：密钥丢失视为严重故障，进入人工恢复流程（按备份恢复原密钥并核对固定公钥注册表指纹，§6.4）；
  无法恢复原密钥则 fail-closed，不自动继续。

### 7.7 故障处理汇总

| 场景 | 行为 | fail-closed |
|---|---|---|
| 服务重启 | 全前缀 `verify_integrity`，按签名 seq 重建链头 | 是（校验失败不启动） |
| Executor 重启 | 查权威历史，按 E1.8 §7.4 三态恢复 | 分歧/疑似时是 |
| DB 被修改 | 完整性校验失败，拒绝返回 | 是 |
| Executor 账户尝试回滚 DB | 无权限；本地回滚按 G2 判定 | 是 |
| 管理员联合回滚 DB+密钥 | **无法检测**，全部本机验证通过 | **否**（诚实记录） |
| 密钥丢失 | 拒绝启动/签名，走人工恢复，禁止重建信任 | 是 |

## 8. Security Guarantees

### 8.1 保证矩阵（严格区分不同安全目标）

| 安全目标 | 第一阶段能否保证 | 依据 / 边界 |
|---|---|---|
| Executor 无法直接修改 Journal DB | **能（需权限隔离验证）** | 目录/文件 ACL 使 `EXEC_ACCT` 无写/删权限（§4.2）；本阶段为设计，需实现后实测验证 |
| Executor 无法读取/复制/导出私钥 | **能（需权限隔离验证）** | 私钥目录仅 `JRNL_SVC_ACCT` 可读（§4.2/§6）；软件级 ACL，非硬件不可导出 |
| Executor 无法伪造 Journal 签名 | **能（需私钥隔离验证）** | 签名服务独占私钥，客户端不提供签名结果（§5.4/§6） |
| Journal 内部篡改检测（就地改条目/Checkpoint/删记录/seq 断裂） | **能（继承 E1.9-A）** | `verify_integrity` 已实现并测试（J06–J08 及 A.1/A.2/A.3 负向用例） |
| Executor 重放旧 append 请求（相同 payload） | **能（需接口层防重放设计，本阶段设计、实现时加入）** | 按 `(operation_id, phase)` + 完整规范化 payload 幂等去重（§5.5）；相同内容重放返回原条目而不新增 |
| 相同幂等键夹带不同 payload | **能阻止** | 内容敏感幂等：规范化 payload/`payload_digest` 不一致 → `IdempotencyConflict` 拒绝（B2-R3，§5.5） |
| 客户端控制 seq / 链头 / prev_digest | **能阻止** | 服务端从权威状态计算，忽略客户端提供的历史字段（§5.4） |
| RESULT 与 INTENT 的 `binding_digest` 绑定一致 | **能（需服务端校验，实现时加入）** | 追加 RESULT 前从服务权威 INTENT 取回并比对（§5.4.2/§5.6） |
| RESULT 回执签名/字段一致性校验 | **能（需固定公钥注册表，实现时加入）** | 用固定 Executor 公钥验 `ExecutionReceipt` v2 + 重算 `result_digest`（§5.4.2）；信任根为预置注册表 |
| **Journal 签名证明工具已真实执行 / result 真实** | **不保证（明确降级为可信记录服务）** | 回执由 Executor 自签，验签只证字段自洽与绑定一致，不证执行真实性；持 Executor 密钥者可伪造（B2-R2，§5.4.1/§5.4.2） |
| Executor 账户无法回滚 Journal | **能（需权限隔离验证）** | 无 DB 写权限、无回滚接口（§7.4） |
| IPC 调用方身份认证 | **能（需 OS 身份校验，非共享 Token/端口）** | 管道 ACL + 服务端主动校验调用身份（§5.3） |
| 本机管理员无法回滚 Journal | **不保证** | T-F 控制所有账户与文件，前提失效（§2.3/§7.5/§10） |
| DB + 密钥联合回滚可检测 | **不保证** | 旧 DB + 旧密钥 + 旧签名自洽，本机验证只查自洽不查新鲜度（§7.5） |
| 服务进程失陷后历史仍可信 | **不保证** | TCB 整体失陷：攻击者取得 DB 读写+私钥读取，可重写并重签历史；无外部锚点不可检测（B2-R1，§2.2/§2.4/§10） |
| 服务账户失陷且私钥可读 / 私钥泄露后仍可信 | **不保证** | 私钥对该账户可读即等效签名权失陷；本机验签无法分辨签名者（B2-R1） |
| DB 与私钥均受控时可检测伪造历史 | **不保证** | 可构造完全自洽的伪造链，本机验证只查自洽不查真实性（B2-R1） |

> R1 说明：以上四行与"Executor 账户失陷可防"**不是同一前提**。后者成立的唯一原因是 `EXEC_ACCT` 碰不到 DB 与私钥；
> 一旦失陷主体换成拥有这些权限的 Journal 服务自身（T-E），本设计的全部门禁失效。切勿把"签名密钥被独立保护"误读为"服务失陷后历史仍可信"。

### 8.2 六个安全目标必须分开陈述，不得混用

| 目标 | 含义 | 本设计状态 |
|---|---|---|
| **Integrity（完整性）** | 条目/Checkpoint 未被就地篡改 | **具备**（E1.9-A 哈希链 + 签名） |
| **Authentication（认证）** | 请求来自授权 Executor 身份 | **具备（设计层）**（§5.3 OS 身份校验） |
| **Authorization（授权）** | 仅授权主体能追加/访问 | **具备（设计层）**（§4 ACL + §5.3） |
| **Replay resistance（防重放）** | 旧请求不能产生新日志 | **具备（设计层）**（§5.5 幂等；实现时加入） |
| **Rollback detection（回滚检测）** | 能发现历史被换回旧版本 | **仅对 Executor 账户级回滚具备**；管理员级、TCB（T-E）失陷级**不具备** |
| **Rollback prevention（回滚阻止）** | 能阻止历史被换回旧版本 | **对 Executor 账户级具备（ACL 阻断）**；管理员级、T-E 级**不具备** |

上述各"具备"均以 **Journal TCB（服务进程/服务账户/私钥）未被攻破**为前提。T-E 失陷时，完整性、认证、授权、防重放、回滚检测全部失效——
攻击者拥有与服务相同的权威能力，本机校验无法区分（B2-R1，§2.2）。这些"具备"只描述 Executor 账户失陷（T-B/T-C）这一威胁下的设计目标。

另需单独强调：**上表六个目标中没有任何一个涵盖"执行真实性"**。Journal 提供的是"内容被可信记录且自洽"，不是"被记录的内容为真"：
- `Integrity`/`Authentication`/`Authorization` 只保证条目来自授权 Executor 且未被改写；
- RESULT 里的 `result`/`execution_receipt` 是 Executor 提交的内容，服务端能校验其签名与绑定一致性（§5.4.2），
  但因签名者是 Executor 自身，**不能**据此断言工具已执行或结果真实（B2-R2，§5.4.1/§8.1）。
不要把"防重放/完整性"误读为对执行声明真实性的背书。

### 8.3 严禁的表述

- 不得把"哈希链完整性 / 签名自洽"描述为"抗回滚能力"——完整性只保证"未被就地改写"，不保证"没有被整体换回旧快照"（§7.5）。
- 不得把"Executor 账户隔离"描述为"管理员级防回滚"。
- 不得把"软件 ACL 保护私钥"描述为"硬件级不可导出密钥"。
- **不得把"签名密钥被独立保护 / 服务账户与 Executor 分离"描述为"服务进程失陷后 Journal 历史仍可信"**——服务进程本就有权读写 DB 与读取私钥，其失陷即 TCB 失陷（B2-R1）。
- **不得用"增加更多本地完整性检查"来回应 T-E 失陷**——本地检查使用的私钥与 DB 与受攻击对象同源，自洽性检查无法发现权威主体自身的伪造（B2-R1）。
- **不得把"Journal 签名"或"RESULT 回执通过服务端验签"描述为"证明工具已执行 / 结果真实"**——Journal 只证明记录了自洽且绑定一致的内容；
  `execution_receipt` 由 Executor 自签，持密钥者可伪造（B2-R2，§5.4.1/§5.4.2/§8.1）。执行真实性归 E1.5 门禁体系，不归 Journal。
- **不得因幂等键相同就无条件返回旧条目**——相同键不同 payload 是 `IdempotencyConflict`，不是重试（B2-R3，§5.5）。
- 不得把本设计描述为形式化安全证明或可直接部署的完整系统（E1.8 §10.2 口径）。

## 9. Deployment Profile

### 9.1 Windows 11 单机开发环境可实现部署方案

| 项目 | 配置 |
|---|---|
| OS | Windows 11（本机 NTFS，支持 ACL） |
| Executor | 标准用户账户 `EXEC_ACCT` 下运行的 Python 进程（项目现有 `.venv`） |
| Journal 服务 | 专用本地账户 `JRNL_SVC_ACCT`（或 `NT SERVICE\JournalService` 虚拟账户），最小权限、非管理员 |
| Journal 数据目录 | 如 `C:\ProgramData\Journal\data\`，ACL：仅 `JRNL_SVC_ACCT` 完全控制，`EXEC_ACCT` 与 Users 拒绝全部 |
| 私钥目录 | 如 `C:\ProgramData\Journal\keys\`，ACL：仅 `JRNL_SVC_ACCT` 读取，`ADMIN` 保留恢复权 |
| 公钥注册表 | 如 `C:\ProgramData\Journal\public\journal_pub.der`，`EXEC_ACCT` 可读、不可写 |
| IPC | Named Pipe，名称如 `\\.\pipe\e1-journal-<instance>`；创建时安全描述符仅授权 `EXEC_ACCT` 与服务自身 |
| 服务生命周期 | 手动/注册为 Windows 服务；启动即执行全前缀 `verify_integrity`，失败则拒绝启动 |
| 备份 | `ADMIN` 定期备份 DB + 私钥，产物保存到与本机信任域隔离的位置（否则成为 T-F 回滚入口） |
| 审计 | 记录 IPC 调用身份与时间、完整性校验失败告警（本阶段仅列为运维要求） |

说明：以上为**部署设计**，本阶段不创建账户、不改 ACL、不实现服务；实际落地与权限验证属后续实现阶段。

### 9.2 部署后必须实测验证的隔离性质（进入实现阶段的验收项）

1. 以 `EXEC_ACCT` 身份尝试读写/删除 Journal DB → OS 拒绝。
2. 以 `EXEC_ACCT` 身份尝试读取私钥 → OS 拒绝。
3. 以非授权账户连接 IPC → 被 ACL 拒绝；以 `EXEC_ACCT` 连接但伪造身份字段 → 服务端身份校验拒绝。
4. 经 IPC 提交带伪造 seq/prev_digest/签名的请求 → 服务端忽略/拒绝，权威状态不受影响。
5. 重放旧 `append` 请求 → 返回原条目，条目总数不变（需 §5.5 幂等实现）。
6. 回滚 `EXEC_ACCT` 本地 `executions` → 服务历史完整，Executor 侧按 G2 判定补齐/fail-closed。
7. 模拟管理员联合回滚 DB + 密钥 → **预期：检测不到**（作为诚实边界的验证，不是缺陷修复）。

### 9.3 未来迁移路径（不在本阶段实现）

| 目标 | 迁移方式 | 解决什么 |
|---|---|---|
| 独立主机运行 Journal 服务 | 服务移到独立主机，Executor 经网络 IPC（带 mTLS/Windows 认证）访问 | 把回滚信任域移出 Executor 所在主机；抵抗"仅攻破 Executor 主机"的攻击者 |
| 外部单调锚点 | 远程水印服务/单调计数或 WORM 存储保存 head 摘要 | 提供检测"整库回滚"的独立新鲜度证据（E1.8 §4 B1/B3） |
| 硬件密钥保护 | HSM/TPM 内生成与使用签名密钥 | 抵抗私钥导出，逼近"不可导出" |

迁移到独立主机后，本设计的账户/权限/接口分层仍适用，只是 IPC 从本机 Named Pipe 变为带认证的网络通道；
但"服务自身被攻破/回滚"仍需更上层锚点——信任根只能移动不能消除（E1.8 §2.2）。

## 10. Residual Risks and Future Work

### 10.1 第一阶段无法消除的风险（不得包装）

1. **管理员级联合回滚（最重要）**：T-F 同时恢复 DB + 私钥 + 服务时，本机全部验证通过，无法检测（§7.5）。
2. **管理员读取私钥**：软件 ACL 对管理员无效，私钥可被导出（§6.6）。
3. **Journal TCB 失陷（B2-R1，最重要之一）**：服务进程被攻破、服务账户被攻破且私钥可读、私钥泄露、DB 与私钥均受控——
   四者均使攻击者以服务身份取得 DB 读写+私钥读取，可改写/删除/重写历史并用合法私钥重签，本机自洽性校验全部通过；
   无外部可信锚点时**不保证**可检测。这不是"签名密钥没保护好"的问题，而是该 TCB 组件本身持有全部权威能力（§2.2、§8.1、§8.3）。
4. **备份产物成为回滚入口**：备份含 DB 与私钥，若备份存储与本机同信任域，管理员可用其回滚（§4.4、§7.5）。
5. **未实现的服务层幂等与回执校验**：§5.5 的内容敏感幂等去重与 §5.4.2 的 RESULT 回执校验都是本阶段设计、实现时需加入的新逻辑；
   在加入前，E1.9-A `AuthorityJournal.append` 每次调用必追加、且不校验回执真实性，重放旧请求会产生第二条 ——
   这是现有接口与新设计的一处**不兼容点**，按用户要求"只记录、不改代码"（§11）。
6. **执行真实性不由 Journal 证明（B2-R2）**：即便实现方案 B 回执校验，回执仍是 Executor 自签，只能证明字段自洽与绑定一致，不证明工具已执行/结果真实；
   Journal 的定位是"可信记录服务"，真实性由 E1.5 门禁体系承担（§5.4.1/§5.4.2/§8.1）。
7. **fencing/G1b 与外部副作用**：本设计不涉及 G1b 与 A3，相关开放问题维持 E1.8 §10.2 / E1.9 §10 原状。

### 10.2 为什么需要独立单调锚点（未来必要性）

- 本机范围内不存在"比管理员更可信"的观察者，因此"整库回滚"在本机无解——这是信任根问题，不是实现缺陷（E1.8 §2.2）。
- 要检测管理员级回滚，必须把一份不可被同一攻击者篡改的"最新 head 证据"放到本机信任域之外：
  远程权威服务（保存最新 head 摘要/序号）、外部水印/单调计数器（B1）、WORM 存储、或 TPM/HSM 单调锚点（B3）。
- 这些方案能把信任根移到外部，但不会"消除"它；外部服务/设备自身的安全成为新的前提。

### 10.3 进入 E1.9-B 的必要前置条件与本设计的关系

- 本设计给出的是 B2 信任域的**部署前提**：独立服务 + 独立账户 + 独立目录/密钥权限，
  使 E1.9 §1.4 "Journal 追加写不可被攻击者回滚或篡改"在 Executor 账户失陷层面有真实依据。
- 进入 E1.9-B（Executor 状态接入）前仍需：①按 E0 级流程冻结该可信组件并扩充 TCB（E1.8 §2.2）；
  ②明确 §5.5 内容敏感幂等与 §5.4.2 RESULT 回执校验相对 E1.9-A `append` 行为的衔接（§10.1 第 5 点）；
  ③接受"管理员级回滚仍不保证""T-E/TCB 失陷不保证"（B2-R1，§8.1）与"Journal 不证明执行真实性"（B2-R2，§5.4.1）三项阶段边界；
  ④明确固定 Executor 公钥注册表的初始化/固定指纹流程为新增可信配置（§5.4.2）。
- **本设计不授权实现，也不声称 B2 已完成**；它只是把部署假设和权限边界明确下来，供架构决策。
