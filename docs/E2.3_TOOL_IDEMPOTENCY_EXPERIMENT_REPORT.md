# E2.3 工具端幂等与崩溃恢复实验报告

## 1. 摘要

E2.2 已证明：真实 Worker 进程在「外部副作用已提交、Journal RESULT 未写入」的 F2 窗口被强制终止后，重试会再次 dispatch 并产生第二次副作用（E2.2 中 eff 1→2，10/10）。本实验回答后续问题：**当 Executor 无法确定首次调用是否已产生副作用时，让工具端（真正产生副作用的资源）接收一个稳定的幂等标识并做原子去重，能否在允许重试的前提下压住重复副作用？**

结论（run-001，N=10/组，全部为真实进程终止）：

- **V0（无工具端幂等）**：eff 1→2、dispatch 1→2，`EFFECT_REPEATED` 10/10 —— 复现 E2.2 F2 窗口。
- **V1（有工具端幂等）**：eff **1→1**、dispatch **1→2**，DEDUP_HIT 10/10 —— **工具被再次调用，但第二次副作用被压住**；重试 Receipt 签名有效、绑定正确、result 与 Sink 原始结果一致，10/10。
- **V2（同 key 不同参数）**：eff 保持 1，`IDEMPOTENCY_KEY_CONFLICT` 10/10 —— 参数替换被工具端检出并拒绝，不产生新副作用。
- 专项：8 个并发同 key 同参请求仅 1 个副作用提交；Sink 事务中途回滚使 key 与副作用一起回滚、随后重试成功。

这把 E1.8 §3.3 A3「工具端幂等键」从设计论证推进到受控实验验证：A3 能把「Effect at-most-once」放在真正产生副作用的资源处，但**不改变 Dispatch 可能重复、也不恢复崩溃前的 Receipt 原件**。

## 2. 与 E1.8 / E2.2 的关系

- E1.8 §3.3 A3 原文：工具端幂等是「唯一能覆盖有外部副作用工具的方案」，把 exactly-once 放在副作用资源处；代价是要求下游工具配合、超出确定性本地工具边界；理论边界是「工具已产生副作用、Executor 记录前崩溃时，本地库与远程协调服务都无法判断工具是否真的完成」。
- E1.9 Final Acceptance 明确把「外部工具 / 外部 API 的 exactly-once」列为范围外（需 A3）。
- E2.2 用真实跨进程 kill 证明了 F2 不确定窗口（intent=1/result=0/effect=1 → 重试 effect=2）。
- E2.3 是独立实验分支，从 `main = 467fa24` 创建，不含 E2.1/E2.2 内容，不修改任何生产代码或冻结文档。

## 3. 必须区分的四种性质

| 性质 | 含义 | V0 | V1 | V2 |
|---|---|---|---|---|
| Dispatch at-most-once | 工具最多调用一次 | 否（1→2） | **否（1→2，允许重复 dispatch）** | 否（1→2） |
| Effect at-most-once | 同一操作最多一次已提交副作用 | 否（1→2） | **是（1→1）** | 是（1→1，冲突不产生副作用） |
| Retry result consistency | 重试返回首次操作对应的结果 | 否（重新执行） | **是（返回 Sink 原始结果 10/10）** | 否（冲突返回错误，符合预期） |
| Receipt continuity | 恢复崩溃前原始 Executor Receipt | 否 | **否（新签名 Receipt，不声称恢复原件）** | 否 |

**不把这四种性质合并为任何形式的 exactly-once 声称。**

## 4. 实验架构（三域隔离 + 真实进程终止）

- **A Journal Service**：独立 OS 进程，`python -m online_budget.journal_service_main`，真实 Named Pipe IPC，独立 journal/idem SQLite，真 Ed25519 签名；就绪探测 `verify_integrity()`。
- **B Executor Worker**：独立子进程，真实 `JournalBackedExecutor` + `ExecutionStore` + `E1CLocalState`（同库满足 A1）。
- **C External Tool Sink**：独立 SQLite，同时保存幂等记录 + 副作用 + 原始结果；与 A、B 数据库分离。幂等记录不放在 Executor 的 `ExecutionStore`——否则没有真正模拟外部副作用边界。

崩溃机制：Worker 在唯一崩溃点 `F2_AFTER_DISPATCH_BEFORE_RESULT` 写 marker `{point,pid,ts}`；父进程 20 ms 轮询确认后 `proc.kill()`（Windows TerminateProcess），记录 PID 与退出码，从不写 release 文件。无 Python 异常注入。工具只模拟持久化副作用，不调用真实第三方 API。

run-001 元数据：30 轮真进程终止，distinct PID，退出码均为 1，崩溃点确认 10/10/组。

## 5. 幂等键与原子去重

```
idempotency_key = digest({domain:"e2-3-sink-idempotency-v1", executor_id, operation_id})
request_digest  = digest({domain:"e2-3-sink-request-v1", executor_id, operation_id,
                          tool_name, tool_schema_hash, arguments})
```

- 幂等键**不含 arguments / binding_digest**：换参数不产生新键，避免绕过去重。
- `request_digest` 由 Sink 按**自身收到的实际参数**用仓库现有 `canonical_json_bytes()` 重算，不盲信调用者摘要。
- 键由可信 Executor 侧从 binding 派生，经工具适配器内部元数据传入，不改工具公开参数、不改 D10/D11 Binding、不改 Receipt 格式。

Sink 原子事务（`BEGIN IMMEDIATE`）：

| DB 行状态 | Sink 行为 | 新副作用 | outcome |
|---|---|---|---|
| key 不存在 | 插入 key+摘要+副作用+原始结果，一起 COMMIT | 是 | EXECUTED |
| key 存在、摘要相同 | 不写新副作用，返回原始结果 | 否 | DEDUP_HIT |
| key 存在、摘要不同 | 不写新副作用，拒绝 | 否 | IDEMPOTENCY_KEY_CONFLICT |

幂等记录、副作用、结果在**同一事务提交**——不先提交 key 再调用副作用（否则在工具端重造 F2 窗口）。

## 6. 正式结果（run-001，N=10/组）

崩溃前三方状态（各组 10/10 一致）：Journal 1 INTENT / 0 RESULT；ExecutionStore 无记录；Sink 副作用 = 1（F2：副作用已发生、RESULT 未写、本地未提交）。

| 场景 | 副作用 before→after（10 轮合计） | dispatch before→after | sink outcome | 恢复分类 |
|---|---|---|---|---|
| V0 无幂等 | 10 → **20** | 10 → 20 | EXECUTED | `EFFECT_REPEATED` 10/10 |
| V1 有幂等 | 10 → **10** | 10 → **20** | DEDUP_HIT | `SINK_DEDUP_NO_REPEAT` 10/10 |
| V2 同 key 异参 | 10 → **10** | 10 → 20 | IDEMPOTENCY_KEY_CONFLICT | `IDEMPOTENCY_CONFLICT_REJECTED` 10/10 |

Receipt 验证（各组，10/10 有效轮）：

| 检查 | V0 | V1 | V2 |
|---|---|---|---|
| 重试返回 Receipt | 10/10 | 10/10 | 10/10 |
| 签名有效 | 10/10 | 10/10 | 10/10 |
| 绑定正确 operation_id + binding_digest | 10/10 | 10/10 | 10/10 |
| result 与 Sink 原始结果一致 | 0/10（重新执行） | **10/10** | 0/10（冲突返回错误，符合预期） |

V1 是核心证据：**dispatch 次数照旧增长到 2，但副作用计数停在 1**——工具端去重允许再次 dispatch、同时阻止第二次外部效果。

## 7. 专项结果

- **并发重复请求**（8 个并发、同 key 同参）：EXECUTED=1、DEDUP_HIT=7、已提交副作用=1、dispatch 计数=8 —— 仅一个副作用提交，通过。
- **Sink 事务中途回滚**：注入回滚后 key 不存在、副作用=0；随后正常重试 EXECUTED、副作用=1 —— 幂等记录与副作用同事务回滚、之后可正常完成，通过。

## 8. Receipt 连续性边界（必须保留）

F2 崩溃时 Receipt 只在 Worker 内存、尚未写 Journal RESULT 或 ExecutionStore，强杀后该临时对象丢失。因此即使 V1 压住了重复副作用，重试 Executor 仍会为「Sink 返回的原始结果」**重新签发一份新 Receipt**。

- 本实验验证：新 Receipt 签名有效、绑定正确 `operation_id` / `binding_digest`、result 与 Sink 保存的原始结果一致（V1 10/10）。
- **不声称**：首次 Receipt 被恢复、Receipt 字节级连续、`receipt_identical_to_original` 为真。原始数据中该字段统一记为 `N/A_NO_ORIGINAL_AT_CRASH`（含义：没有可持久化恢复的原件，不代表 Receipt 从未生成）。
- V2 冲突请求返回 FAILED Receipt（result = `{error: IdempotencyKeyConflict}`），签名仍有效、绑定仍正确，但不返回 Sink 原始结果——这是冲突被拒的正常表现。

## 11. 局限与不可声称项

- N=10 是受控机制重复验证，**非形式化或统计性安全证明**；0/10 不等于统计意义上的概率为零。
- 受控 Sink（SQLite 副作用计数）≠ 真实第三方 API；未接入任何真实外部服务、未使用第三方 API Key。
- 幂等键作用域 = 本实验域标签 `e2-3-sink-idempotency-v1`；真实部署须逐服务核对供应商幂等范围与保留期限（如 AWS EC2 区分 Regional 与 Zonal）。
- 不声称：所有崩溃窗口自动恢复、G1b、外部 exactly-once、Journal 单独证明执行真实性、已解决跨存储原子性、Receipt 连续性。
- 哪些保证依赖谁：**「重试携带同一操作身份」依赖 Agent/Executor 侧稳定派生 operation_id（密码学 Binding 提供身份连续性）；「重复请求不产生第二次副作用」必须由外部工具服务（Sink）提供**——E2.3 证明后者在受控实现下成立，但不假定所有外部工具都实现幂等。
