# E1.9-B — Independent Journal Service 实施报告

## 0. 结论摘要

E1.9-B 将 E1.9-A 已在进程内实现的 `AuthorityJournal` 升级为**独立运行的 Journal Service**：独立进程、独占 DB 与签名私钥、Windows Named Pipe + OS 调用身份校验、服务端 Receipt v2 完整验证、内容敏感且持久化的幂等。`AuthorityJournal`（`journal.py`）作为冻结核心保持未改，所有新安全判断发生在服务端。

诚实边界（与 E1.9-B2 设计一致，未被本阶段突破）：

- Journal 是**可信记录者**，不是执行真实性证明者。Receipt 由 Executor 自签，验签只证明签名来源与字段绑定一致；持 Executor 私钥者可签出满足全部检查的伪造回执。
- 服务抵抗 Executor 进程/账户失陷（T-B/T-C）；**不抵抗**管理员级 DB+密钥联合回滚，也**不抵抗** Journal TCB（服务进程/服务账户/私钥）整体失陷（T-E, B2-R1）。
- 本阶段只验证 Journal 服务自身，不实现 Executor 完整恢复状态机；不声称 G1b（至多一次真实 dispatch）；无远程 Journal / HSM / TPM。
- 本机 Named Pipe + OS 身份测试验证的是"当前账户（含跨进程）"路径；**真实多账户 ACL 拒绝**需管理员配置第二个 Windows 账户后实测，本报告给出完整命令并列为环境依赖，未用模拟结果冒充。

## 3. 关键实现决策

1. **OS 身份获取（B-F4 收尾后）生产主路径用真正的 Named Pipe 客户端令牌**：`ImpersonateNamedPipeClient` + `OpenThreadToken` 读取连接方的 Named Pipe 安全上下文，绑定"实际调用安全身份"而非进程主令牌；客户端 `CreateFileW` 显式声明 `SECURITY_SQOS_PRESENT | SECURITY_IMPERSONATION`，否则令牌为匿名导致 error 1368——这是原实现的根因，补上 SQOS 后同进程自测亦可通过。进程主令牌路径（`GetNamedPipeClientProcessId`）降级为 `identity_mode="pid_test_only"` 的**显式测试路径**，生产入口恒用 impersonation；即便同进程测试也不再默认走 PID 路径。
2. **Receipt v2 强制在通用验证器之前**：现有 `verify_execution_receipt()` 同时接受 v1/v2；服务层先显式拒绝 `receipt_version != 2`，再复用冻结验证器并叠加 expected-map 做纵深防御。
3. **崩溃安全的两层幂等**：快索引表（`BEGIN IMMEDIATE` 权威串行）负责并发与性能；签名 Journal 条目（`payload_digest` 在签名对象内）作为真相源，在"追加成功但索引写丢失"时回退，避免重复 Entry。修复了实现期发现的一处真实缺陷：`authoritative_write()` 原成功路径未 commit，导致索引写入被回滚（已修）。
4. **Named Pipe 消息模式整帧读写**：用单次 `ReadFile` 读取整条消息（而非逐字节读长度前缀），避免消息模式下首读吞掉整帧导致位移错乱。
5. **端口/共享 Token 均不作为认证机制**：认证完全依赖 Named Pipe ACL + OS 调用身份；配置中无静态 Token 字段。

### 关键实测证据
- **真实 Named Pipe 通信**：服务端以 ctypes 创建带 DACL 的 Named Pipe，客户端 `CreateFileW` 连接；`GetNamedPipeClientProcessId` → 进程令牌 SID 取得 OS 身份，服务端映射校验通过，`verify_integrity`/`append_intent` 均返回正确结果。
- **独立进程**：`python -m online_budget.journal_service_main --config ...` 以 subprocess 启动为独立 OS 进程，跨进程经 Named Pipe 完成 append；终止后重启同配置，历史完整恢复（verified_entries=1）。
- **Receipt v2 服务端拒绝**：v1 被拒、错误签名被拒、`executor_id`/`operation_id`/`binding_digest` 不一致被拒、`result_digest` 重算不符被拒；失败不产生 Entry/Checkpoint。
- **并发幂等**：12 线程同 `(operation_id, phase)` 并发 append，服务端 `BEGIN IMMEDIATE` 串行化后恰好 1 条 Entry，其余返回原条目。
- **崩溃安全回退**：删除幂等快索引行后重试，从签名 Journal 回退判定为幂等，不产生重复 Entry。
- **启动完整性门禁**：篡改签名 Entry 后，新服务启动即 refuse（fail-closed）。

## 6. 真实 Windows ACL 管理员命令（环境依赖，未代为执行）

在目标 Windows 主机以管理员 PowerShell 执行（将 `EXEC_ACCT` 替换为实际 Executor 账户）：

```powershell
# 1) 创建独立的 Executor 运行账户（若尚未存在）
$acct = "EXEC_ACCT"; $pwd = Read-Host -AsSecureString "password for $acct"
New-LocalUser -Name $acct -Password $pwd -PasswordNeverExpires
# 2) 取该账户 SID，写入配置的 allowed_client_sids
$execSid = (Get-LocalUser -Name $acct).SID.Value
# 3) 生成 Journal 签名密钥与配置（在隔离目录）
python -m online_budget.journal_service_main --print-sid   # 另取服务自身 SID
python scripts/create_journal_service_config.py --out C:\ProgramData\Journal\service.json `
    --executor-id exec-A --executor-pubkey <base64-pub> `
    --os-identity "HOSTNAME\EXEC_ACCT" --allowed-sid $execSid
# 4)  ACL：AllowedClient SID 在 journal_ipc._build_dacl 中以 DACL ACE 写入，
#     其他本机账户（含未授权用户）连接将被 OS 拒绝（CreateFileW last_error=5）。
# 5)  以独立账户启动服务（推荐用服务宿主/scheduled task 以 EXEC_ACCT 之外的独立账户运行）
python -m online_budget.journal_service_main --config C:\ProgramData\Journal\service.json
# 6)  验证未授权账户拒绝：以普通用户身份运行客户端，预期 PIPE_ACCESS_DENIED。
```

上述第 6 步（真实跨账户 ACL 拒绝）需管理员建账户后实测；本报告未声称其已通过。

## 9. B-F 收尾修复（对 `e689f7d` 审查的四项阻断）

### B-F1 — Receipt `result` 与 RESULT envelope 绑定（阻断，已修）
- `journal_receipt_validator.py`：在原有"Receipt 自身 `result_digest` 自洽"之外，新增两条强制检查——① `Receipt.result == envelope.result`（否则 `RESULT_ENVELOPE_MISMATCH`）；② 用 envelope 的 result 重算 `digest({"domain":"agent-tool-result-v1","result":...})` 必须等于 Receipt 的 `result_digest`（否则 `ENVELOPE_RESULT_DIGEST_MISMATCH`）。堵住"Receipt 签名 result X、envelope 记录 result Y、两者各自自洽却被接受"的缺口。
- 负向测试：`test_e1_9_b_receipt.py` 的 V11（合法 Receipt + 被替换的 envelope result → 拒绝）、V12（双方 result 一致含嵌套结构 → 通过）；`test_e1_9_b_service.py` 的 S11（服务层拒绝且不产生 Entry/Checkpoint）。

### B-F3 — Named Pipe 阻塞等待的优雅停止（阻断，已修）
- `journal_ipc.py`：`CreateNamedPipeW` 改用 `FILE_FLAG_OVERLAPPED`；`ConnectNamedPipe` 以 `_OVERLAPPED` 异步发起，`WaitForMultipleObjects(connect_event, stop_event, timeout_ms)` 等待；`stop()` 除置位线程 Event 外还 `SetEvent(stop_event)` 直接解除阻塞的 accept。`timeout_ms` 现真正生效；无客户端连接时 `stop()` 可让 `serve_forever` 在超时窗口内干净退出，无需 `terminate()`。读写改为带超时的 overlapped 读/写（`_overlapped_read`/`_overlapped_write`），连接但静默的客户端不再挂死服务。
- 测试 `test_e1_9_b_ipc.py` P09：无客户端连接时 `stop()` 后服务线程在 3 秒内退出（旧实现必然失败）。

### B-F4 — 生产 OS 身份认证明确并落实（已修）
- `NamedPipeServer` 新增 `identity_mode`：`"impersonation"`（生产，默认）经 `HandleIdentityProvider` 读 Named Pipe 客户端安全上下文；`"pid_test_only"`（显式测试）才用进程主令牌。非法值构造即 `ValueError`（fail-closed）。
- `NamedPipeClient._open` 在 `CreateFileW` 显式加 `SECURITY_SQOS_PRESENT | SECURITY_IMPERSONATION`，使服务端模拟拿到可用客户端令牌——修复 error 1368 根因，生产路径名实一致。生产与同进程测试现均走真实模拟身份；独立进程入口恒用生产模式。

### B-F2 部署-验证一致性回修（a17ff10 之后的限定修复）
用户整体验收发现：管理员部署脚本 `setup_journal_service_acl.ps1` 用 `icacls /deny *EXEC:(OI)(CI)(RX,D,W)` 主动为 Executor 添加 DENY ACE，而首版 `journal_fileacl.py` 把每个非 allow ACE 记为不透明的 `<deny-ace-N>`，`dacl_problems` 又对所有此类标记无条件判违规。后果是**按项目自己的部署脚本配置 ACL 后，服务启动门禁反而拒绝启动**——部署流程内部逻辑矛盾。本次仅修这一处，不重开 B2 设计、未改冻结协议/E1.9-A/E1.8/Receipt v2。
- `read_dacl` 现在解析 ACCESS_ALLOWED_ACE 与 ACCESS_DENIED_ACE 的 **SID + 权限掩码**，返回结构化 `DaclView(allow, deny, unparsed)`；无法归属的 ACE 类型（object/audit/未知）记入 `unparsed`，一律 fail-closed。NULL DACL 仍显式表示为 Everyone/GENERIC_ALL。
- `dacl_problems` 增加：① **主体白名单** `principal_allowlist`（默认 = allowed_sids + SYSTEM `S-1-5-18` + Administrators `S-1-5-32-544`），任何 allow ACE 的主体不在白名单即拒绝——覆盖 Everyone `S-1-1-0`、Authenticated Users `S-1-5-11`、Users、CREATOR OWNER 及未知 SID 的意外授权，不再只检查 Executor；② **预期 DENY 主体** `expected_deny_sids`（来自 Executor SIDs）：仅此类主体的 DENY ACE 被接受，且掩码须分别命中 `_DENY_READ_BITS`/`_DENY_WRITE_BITS`（不重叠的 FILE_READ_DATA/FILE_WRITE_DATA + generic 位，避免把 READ-only DENY 误当成覆盖 WRITE）；③ 服务/受信任 SID 被 DENY、未知主体被 DENY、掩码过弱、未解析 ACE 类型全部 fail-closed。兼容旧 `{sid: mask}` 注入（`<...>` 标记视作未解析 ACE）。
- `restrict_to_sids` 可附带 `deny_sids`/`deny_mask`（默认 `FILE_GENERIC_READ|WRITE|EXECUTE|DELETE`，对齐脚本 `(RX,D,W)`），显式 DENY ACE 置于 ALLOW 之前（Windows 规范顺序），使 Python 部署路径与 PowerShell 脚本产生同形 DACL。`verify_private_file` 把 forbidden 列表中的 Executor SIDs 作为预期 DENY 主体传入。
- 测试 `test_e1_9_b_fileacl.py` 由 8 扩至 16：D01 部署脚本 ACL 形态通过验证；D02 旧不透明 deny 标记仍拒绝；D03 GENERIC_ALL DENY 可接受；F02 Executor 获得 READ 授权失败；F05 未知主体 DENY 失败；F06 服务账户被 DENY 失败；F07 READ-only 弱 DENY 失败；F08 Everyone/Authenticated Users/Users/CREATOR OWNER 意外授权全部失败；F09 未解析 ACE 失败；R01 真实 Win32 上 apply（含真实 DENY ACE）→read_dacl（解析 SID+mask）→verify_private_file 通过闭环（env 门控 `E1B_REAL_ACL=1`）。真实第二账户拒绝仍为管理员环境依赖，未冒充通过。
- 验证：`test_e1_9_b_fileacl.py` 16/16（含 `E1B_REAL_ACL=1` 真实 Win32 DENY ACE 闭环），E1 Python 全量 **283/283 OK，EXIT=0**（526.57s），Rust 回归 0 failed，`git diff --check` 干净。
- 诚实边界不变：主体白名单是 OS ACL 策略检查，不是不可绕过的安全边界——可取回所有权或控制服务账户的管理员仍可绕过；本修复只消除"脚本部署后服务无法启动"的矛盾并收紧意外授权检查，不把 ACL 检查升级为 HSM/TPM 或管理员级防护。
