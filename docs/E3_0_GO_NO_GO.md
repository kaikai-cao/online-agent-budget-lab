# E3-0 GO / NO-GO 决策：是否进入 E3 实际集成

> **阶段性质**：决策文档，暂不开发、不接入、不提交。
> **输入**：`E3_0_SCENARIO_SURVEY.md`、`E3_0_THREAT_MODEL.md`、`E3_0_RESEARCH_GAP.md` 及一手来源。标签 `[FACT]` / `[INFER]` / `[ASSUMPTION]`。
> **决策纪律**：不为了使用框架而拼凑场景；不把「接入某 Agent」本身当创新；如果条件不具备，明确给出 NO-GO 与先决条件。

---

## 1. 决策结论（摘要）

**条件性 GO，但有严格前置门槛。** `[INFER]`

- **GO 的部分**：进入 E3 的**最小可行实验设计阶段**（仍是研究/实验设计，先不接真实生产 Agent），聚焦唯一有确证规范空白支撑的差异点——`arguments_digest` 把授权绑定到具体 tool + 参数（GAP-1）。
- **NO-GO 的部分**：暂不把「接入 GitHub Copilot 做一层 Gateway」或「给 LangChain 套 Binding」当作 E3 目标——这两者重复现有机制、构成不了创新 `[FACT]`。
- **前置门槛**：必须先验证「用户授权意图 → 可签名结构化对象 → 执行出口校验」闭环可行且授权方/执行方分离（§4 的 H1）。若 H1 不成立，转为 NO-GO，不应投入数月做接入工程。

场景选择：**MCP 工具调用 Agent 为首选**（GAP-1 有一手规范原文空白、实验切入点最干净），数据访问 Agent 为次选（GAP-1 同样存在但 SQL 语义绑定存疑），GitHub Agent 暂列观察（重复度最高，除非发现真实独立授权方）。`[INFER]`

## 2. 回答三个验收问题

### 问题 1：真实 Agent 工作流中，究竟存在什么具体安全问题？

`[FACT]` 由一手来源证实的具体问题（非泛泛综述）：

1. **间接注入 → 数据外泄**：PR 描述 / DB 记录 / 工具 description 中的恶意文本被回灌 Planner，产生外泄型工具调用。证据：CamoLeak（GitHub Copilot Chat）、P2SQL RI.1/RI.2（arXiv:2308.01990, ICSE 2025）、Invariant `add(sidenote)`（MCP）。
2. **越权 / confused deputy**：过宽 scope、token passthrough 导致以错误 authority 调用下游。证据：OWASP MCP02、MCP 规范 token passthrough 禁令（原文已核实）、CVE-2025-62453。
3. **授权粒度不足**：现有授权绑定的是工具名/命令/DB 角色/Server scope，**不绑定具体 tool + 具体参数**；MCP 规范原文已核实 `resource` 指向整个 Server canonical URI。这是结构性空白。
4. **审计可验证性弱**：MCP08（beta）明确缺乏审计与遥测、要求 immutable audit trails；日志多为 agent 自产可篡改。
5. **重试重复副作用**（真实场景待证 `[ASSUMPTION]`）：at-least-once runtime 下写操作重试可产生第二副作用；MCP 规范无幂等强制机制。

**诚实边界** `[FACT]`：这些问题中，**注入根因本框架不解决**；真正对应本框架能力的是第 3、4 项，第 5 项依赖工具端幂等。

### 问题 2：我们现有框架能解决哪一部分，不能解决哪一部分？

| 能解决（有条件） | 不能解决 / 不声称 |
|---|---|
| `[FACT]` 参数级授权的密码学绑定（GAP-1）：前提是绑定用户授权意图、存在独立授权方 | `[FACT]` Prompt Injection 根因（LLM 不能区分指令与数据；prompt 防御可绕过） |
| `[FACT/INFER]` 签名可验证的单次执行审计链（GAP-2）：前提是独立验证方 | `[FACT]` 合法权限内的恶意查询（如 Text-to-SQL 泄露性 SQL；需 RLS/SQL rewriting） |
| `[INFER]` 跨调用状态机与幂等恢复（GAP-3）：依赖真实工具幂等 | `[FACT]` 外部工具/API 的 exactly-once；全局 dispatch at-most-once；跨存储原子性 |
| `[INFER]` 请求级确定性预算准入（GAP-4）：须证明相对现有 quota 的增量 | `[FACT]` Journal 单独证明外部副作用真实性；同信任域内签名的额外保证 |

**关键风险** `[ASSUMPTION]`：若绑定的是「模型输出参数」而非「用户授权意图」，则在注入场景下恶意参数会被合法签名——**这是「能解决」与「不能解决」的分界线**，也是 H1 要验证的核心。

### 问题 3：如果开展 E3，最小可行实验应该是什么，能得到什么研究价值？

**最小可行实验（MVP）**：在 MCP 场景做一个**受控的「授权意图 → 参数级绑定 → 执行出口」对照实验**，不接真实生产 Agent，用本地 MCP Server 与测试工具。

- **实验组**：用户通过结构化授权请求批准 `send_email(to=A, body=...)` → 生成绑定意图的签名授权（含参数摘要）→ Gateway 在执行出口校验 digest。
- **对照组 A（无 Binding）**：同一批准流程但执行出口不校验 digest。
- **对照组 B（绑模型输出而非意图）**：注入场景下对模型输出的恶意参数签名——预期**失效**，作为负面证据。
- **攻击注入**：①在途把 `to=A` 改为 `to=B`（构造 C2 能力）；②经工具 description 注入诱导模型产生 `to=attacker`（复现 tool poisoning/shadowing）。
- **指标**：未授权参数执行率、注入检出率、**误拒率（可用性代价）**。
- **归因**：检出必须来自出口 digest 校验，而非注入偶然失败。

**能得到的研究价值** `[INFER]：
- 正向（若实验组拦下在途篡改、对照组未拦）：首次在真实 MCP 工具调用链上证明「授权意图↔tool+参数」绑定有独立防护价值，且规范空白确证——这是有来源支撑的真实增量，不是「接入了 MCP」。
- 负面（若对照组 B 也拦下注入，或实验组误拒率高）：证伪「绑定模型输出参数可防注入」，明确框架边界——这同样是有价值的结论，避免错误创新声张。
- 诚实结论：即使正向，也只能说「受控 MCP 环境下、绑定用户意图时，参数级授权绑定拦下在途篡改」，**不能**说「解决了 Prompt Injection」或「实现了 Agent exactly-once」。

## 3. 场景选择理由

| 场景 | 决策 | 理由 |
|---|---|---|
| MCP 工具调用 Agent | **首选** | GAP-1 有一手规范原文空白（`resource`=Server、无 tool+参数绑定）；`tools/list`/`tools/call` 提供明确实验切入点；OWASP MCP08 审计空白对应 Receipt/Journal；实验 B 可干净归因 |
| 数据访问 Agent | 次选 | GAP-1 同样存在（token↔SQL 文本绑定空白），但「SQL 文本能否提取授权语义」存疑，Binding 对象模糊；DB 层 RLS/RBAC 已强 |
| GitHub Agent | 观察 | 执行前权限/sandbox/hooks/审计已完整，重复度最高；除非发现真实「授权方≠执行方」场景（如第三方 Agent HQ agent 委派），否则不优先 |

## 4. 前置假设与门槛（H1–H4）

进入 E3 集成前必须验证；任一失败则调整或 NO-GO：

- **H1 意图绑定可行性** `[ASSUMPTION 核心]`：能否把用户授权意图转成可签名的结构化对象（tool + 参数 + 预算），且存在独立授权方与执行方？→ 决定 GAP-1 能否落地。
- **H2 在途篡改真实性** `[ASSUMPTION]`：Planner→Executor 参数篡改在真实 Agent 中是否为现实威胁？若只能人为构造，须标注为实验假设，价值降为机制验证。
- **H3 差异可归因** `[INFER]`：能否用无框架基线 + 误拒率证明拦截来自 Binding 而非注入偶然失败？
- **H4 与现有机制共存** `[FACT]`：Gateway 能否与 OAuth audience / HITL consent 共存而不破坏语义（MCP 插入 Gateway 会改 audience，需重新设计信任锚）？

## 6. 最终建议

`[INFER]` **有条件 GO**：以 H1 为核心门槛，先做「授权意图绑定的可行性验证 + 上述 MCP MVP 实验设计」，不做接入工程。若 H1 通过且 MVP 实验能干净归因，再决定是否进入 E3 实际集成；若 H1 失败，诚实 NO-GO，把 E1/E2 框架定位为「本地/受控执行链的可信化」而非「通用 Agent 安全方案」，避免把数月投入到一个最后只能证明「成功接入了某 Agent」的项目。

本阶段所有结论均为 `[INFER]` / `[ASSUMPTION]` 级别的决策建议，唯一 `[FACT]` 级别的技术事实是 GAP-1 的规范空白与现有机制覆盖情况——它们来自一手来源，已二次核实。
