# E3-0.1 GO / NO-GO 决策：是否进入 E3 实际集成

> **阶段性质**：决策文档，暂不开发、不接入、不提交。
> **输入**：`E3_0_SCENARIO_SURVEY.md`、`E3_0_THREAT_MODEL.md`、`E3_0_RESEARCH_GAP.md` 及一手来源。标签 `[FACT]` / `[INFER]` / `[ASSUMPTION]`。
> **决策纪律**：不为了使用框架而拼凑场景；不把「接入某 Agent」本身当创新；如果条件不具备，明确给出 NO-GO 与先决条件。
> **★E3-0.3 修订（重要）**：E3-0.2 的 B/C 对照**同时改变了凭证机制与信任架构两个变量**，无法把结果归因于密码学凭证。本版重构 §4.1 为 **A / B1（共享信任域基线） / B2（跨信任域非密码学基线） / C（跨信任域密码学凭证）**，明确**只有 B2 vs C 才有密码学归因价值**，B1 vs C 仅展示不同部署假设下的能力上限；补足 C 组一次性消费状态的维护主体与信任假设；同步重写 H3、停止门槛与全文归因口径；并修正 §3 数据访问场景「同样缺 token↔SQL 绑定」旧口径。本轮不重新调研、不重新核实来源、不改生产代码、不接入 Agent。
> **★E3-0.1 修订（重要）**：E3-0 原稿把「`arguments_digest` 是 MCP 唯一确证规范空白」当作创新点，审查指出该论据过强——参数级审批（OWASP 两份 Cheat Sheet）、消息签名与防重放（MCPS）均已有相关工作。本版把研究问题收敛为「**Agent 生成工具调用 / 用户批准工具调用 / 可信执行器执行工具调用三者之间，能否建立独立且可验证的授权关系**」，并把 H1 从「自然语言意图自动转结构化授权对象」改为「可信授权界面展示具体动作 + 用户确认 + 独立授权服务签发凭证」，避免引入自然语言理解这一独立难题。

## 1. 决策结论（摘要）

**条件性 GO，但有严格前置门槛，且暂不进入实际集成。** `[INFER]`

- **GO 的部分**：进入 E3 的**最小可行实验设计阶段**（仍是研究/实验设计，先不接真实生产 Agent），聚焦「独立授权方对特定动作的批准 → 跨信任边界可验证、不可替换/重放的一次性凭证」这一研究问题（GAP-1 重写版）。
- **NO-GO 的部分**：暂不把「接入 GitHub Copilot 做一层 Gateway」或「给 LangChain 套 Binding」当作 E3 目标——这两者重复现有机制、构成不了创新 `[FACT]`；也**不把「给 MCP 加 arguments_digest」本身当创新**（参数审批与消息签名已有相关工作）。
- **前置门槛**：①H1 验证「可信授权界面展示具体动作 → 用户确认 → 独立授权服务签发凭证 → 执行方跨信任域验证并原子消费」闭环可行且授权方/执行方分离；②强对照中 **B2（跨信任域非密码学基线）被完整实现，且 C 相对 B2 必须有可测量、可归因的独立增量**（B1 与 C 的差异不作为密码学归因证据，见 §4.1）。任一不成立则 NO-GO，不投入数月做接入工程。

场景选择：**MCP 工具调用 Agent 为首选**（规范无 token↔tool+参数绑定是事实、`tools/list`/`tools/call` 实验切入点干净、且有 MCPS 可作品质对照），数据访问 Agent 为次选，GitHub Agent 暂列观察。`[INFER]` 首选理由**不是**「别人没发现的参数空白」，而是该场景最适合检验独立授权凭证跨信任域的可验证性。

## 2. 回答三个验收问题

### 问题 1：真实 Agent 工作流中，究竟存在什么具体安全问题？

`[FACT]` 由一手来源证实的具体问题（非泛泛综述）：

1. **间接注入 → 数据外泄**：PR 描述 / DB 记录 / 工具 description 中的恶意文本被回灌 Planner，产生外泄型工具调用。证据：CamoLeak（GitHub Copilot Chat）、P2SQL RI.1/RI.2（arXiv:2308.01990, ICSE 2025）、Invariant `add(sidenote)`（MCP）。
2. **越权 / confused deputy**：过宽 scope、token passthrough 导致以错误 authority 调用下游。证据：OWASP MCP02、MCP 规范 token 发送/接受/转发禁令（2026-07-28 原文已核实）、CVE-2025-62453。
3. **授权粒度不足**：现有授权绑定的是工具名/命令/DB 角色/Server scope，**不绑定具体 tool + 具体参数**；MCP 2026-07-28 原文 `resource` 指向整个 Server canonical URI。`[FACT]` 但须注意：这是规范层事实，**不是「无人研究过的空白」**——OWASP 已提出参数级审批原则、MCPS 已签名覆盖 `tools/call` 参数。
4. **审计可验证性弱**：MCP08（beta）建议 immutable audit trails；OWASP 同时已推荐集中式审计与日志完整性保护。不能仅以「现有日志不可信」立论，须说明独立验证者能验证什么。
5. **重试重复副作用**（真实场景待证 `[ASSUMPTION]`）：at-least-once runtime 下写操作重试可产生第二副作用；MCP 规范无幂等强制机制。

**诚实边界** `[FACT]`：注入根因本框架不解决；真正对应本框架能力的是第 3、4 项（且第 3 项须与已有工作比对增量），第 5 项依赖工具端幂等。

### 问题 2：我们现有框架能解决哪一部分，不能解决哪一部分？

| 能解决（有条件） | 不能解决 / 不声称 |
|---|---|
| `[INFER]` 独立授权方签发、跨信任域验证、一次性消费的动作凭证：前提是授权方≠执行方、绑定用户确认的具体动作、且**相对 B2（相同跨域条件下的非密码学基线）有可测增量** | `[FACT]` Prompt Injection 根因（LLM 不能区分指令与数据；prompt 防御可绕过） |
| `[FACT/INFER]` 签名可验证的授权→执行→结果关联记录：前提是独立验证方，且价值落到「验证者能验证什么」 | `[FACT]` 合法权限内的恶意查询（如 Text-to-SQL 泄露性 SQL；需 RLS/SQL rewriting） |
| `[INFER]` 跨调用状态机与幂等恢复（GAP-3）：依赖真实工具幂等 | `[FACT]` 外部工具/API 的 exactly-once；全局 dispatch at-most-once；跨存储原子性 |
| `[INFER]` 请求级确定性预算准入（GAP-4）：须证明相对现有 quota 的增量 | `[FACT]` Journal 单独证明外部副作用真实性；同信任域内签名的额外保证；**消息签名≠用户批准**（MCPS §11.2 provenance not safety） |

**关键风险** `[ASSUMPTION]`：①若绑定的是「模型输出参数」而非「用户确认的具体动作」，注入场景下恶意参数会被合法签名；②若授权方=执行方（同信任域），密码学绑定无增量；③若 C 组相对 B2（相同跨域条件下的非密码学基线）无可测增量、或 B2 无法合理定义，则密码学框架没有存在必要。这三点构成「能解决」与「不能解决」的分界线，是 H1 与 A/B1/B2/C 要验证的核心。

### 问题 3：如果开展 E3，最小可行实验应该是什么，能得到什么研究价值？

**最小可行实验（MVP）**：在 MCP 场景做**受控的 A / B1 / B2 / C 四组对照 + MCPS 扩展对照**，不接真实生产 Agent，用本地 MCP Server 与测试工具。各组设计详见 §4.1，核心问题如下：

- **A 普通 MCP Host/HITL**：现有人工确认能做到什么？（基线）
- **B1 共享信任域基线**（普通审批 + 共享状态原子消费）：已有机制在最优条件下的能力上限，不与 C 做严格密码学对照。
- **B2 跨信任域非密码学基线**（可信通道 / 共同托管方完成跨域验证）：**真正有归因价值的对照**——同样跨域隔离下，不用密码学凭证能否达到同等保证？
- **C 跨信任域密码学凭证**（独立签发 + 本地验证签名与请求绑定 + 一次性消费）：相对 B2 到底增加了什么？
- **MCPS 扩展对照**：逐消息签名能拦下什么、拦不下什么（区分「消息没被改」与「调用被授权」）。

**攻击注入**：①TLS 终止后 C2 参数篡改（须明确攻击者位于哪个信任边界，见 THREAT_MODEL C2）；②经工具 description 注入诱导模型产生恶意参数（复现 tool poisoning/shadowing）；③凭证重放与并发重复消费。

**测量指标**（不止拦截率）：未授权参数执行率、审批凭证重放成功率、并发重复消费成功率、授权与执行记录的可验证性、**误拒率与合法任务完成率**。

**能得到的研究价值** `[INFER]`：
- **正向**：若 **B2 被完整实现**，且 C 相比 **B2** 在「授权来源验证 / 请求完整性 / 授权服务不可用时独立验证 / 误拒率」上有可测且可归因的独立增量，则证明独立授权凭证相对非密码学跨域方案的真实研究价值——这是有来源支撑的差异，不是「接入了 MCP」，也不是「发现了参数空白」，更不是与共享域 B1 的能力对比。
- **负面**：若 C 与 B2 无显著差异、或 B2 无法合理定义、或误拒率高——**证伪密码学机制在这一问题上的必要性**，明确 E1/E2 框架边界。这同样是有价值结论，避免错误创新声张。
- **诚实结论**：即使正向，也只能说「受控 MCP 环境下、独立授权方签发且跨信任域本地验证时，凭证相对非密码学跨域方案提供了可测增量」，**不能**说「解决了 Prompt Injection」「实现了 Agent exactly-once」或「Ed25519 本身防重放」（防重放靠执行方原子消费状态）。

## 3. 场景选择理由

| 场景 | 决策 | 理由 |
|---|---|---|
| MCP 工具调用 Agent | **首选** | 规范无 token↔tool+参数绑定是事实；`tools/list`/`tools/call` 提供明确实验切入点；有 MCPS/OWASP 相关工作可作强对照与品质基准；C2 参数篡改与重放可干净归因 |
| 数据访问 Agent | 次选 | 存在「授权决策 ↔ 具体 SQL 查询」的关联问题，但**参数级审批已有成熟设计原则**，不能把「参数级审批」本身说成空白；「SQL 文本能否提取授权语义」仍存疑、Binding 对象模糊；DB 层 RLS/RBAC 已强。**不能从 MCP OAuth 的 Server 级 `resource` 语义推导 Text-to-SQL 也存在同样的协议缺口**；独立授权方与 DB 执行方跨信任域验证是否带来额外保证，尚待验证 `[ASSUMPTION]` |
| GitHub Agent | 观察 | 执行前权限/sandbox/hooks/审计已完整，重复度最高；除非发现真实「授权方≠执行方」场景（如跨组织 agent 委派），否则不优先 |

## 4. 前置假设、强对照与门槛

### 4.1 强对照设计：A / B1 / B2 / C（★E3-0.3 重构，解决 B/C 混杂变量）

**★先说为什么必须重构（E3-0.2 的实验方法缺陷）**：E3-0.2 的 B/C 对照**同时改变了两个变量**——①凭证机制（普通应用层审批记录 vs Ed25519 签名）；②信任架构（授权方与执行方共享应用信任域 vs 信任隔离）。若 C 成功而 B 失败，无法把结果归因于：是签名提供了额外能力？是部署结构不同？还是 B 本来就没被设计成能跨信任域工作？**这会让结论无法归因。** 因此必须把「共享信任域基线」与「跨信任域基线」拆开——真正有归因价值的不是 B1 vs C，而是**在相同跨域条件下**的 B2 vs C。

**★再区分两类保证**（不可混为一谈，见 RESEARCH_GAP §3）：
- **跨信任域验证** `[INFER 待证]`：执行方能验证「凭证由独立授权方签发」且「与当前调用一致」，而不必信任授权方内部状态/数据库——这是**唯一可能的候选增量**。
- **一次性消费 / 防重放** `[FACT 已有]`：需共享状态 + 原子操作；OWASP Transaction Authorization CS 已明确提出。**把内部授权记录换成 Ed25519 签名，不产生新的防重放能力**。

| 组别 | 机制 | 授权方/执行方信任假设 | 要回答的问题 |
|---|---|---|---|
| **A** | 普通 MCP Host + HITL（现有人工确认） | 同一 Host 内，人工确认 | 现有人工确认已能做到什么？误拒率如何？ |
| **B1 共享信任域基线** | 精确参数审批 + 共享状态 + 原子消费，不使用密码学凭证（成熟应用层授权，OWASP 原则） | 授权服务与执行服务**共享同一应用信任域**，可互信内部状态/数据库；原子消费由共享状态实现 | 已有机制在最优条件下的**能力上限**：普通应用层授权已解决多少（含防重放）？仅作能力展示，**不与 C 做严格密码学对照** |
| **B2 跨信任域非密码学基线** | 明确指定一种可复现的非密码学跨域验证机制（如执行方经**可信通道**实时远程查询授权服务的授权记录 + 原子消费回调，或由**共同可信第三方**托管授权状态） | 授权服务与执行服务**不共享应用信任域、不互信内部数据库**，但双方共用一个可信通道或共同可信托管方 | **真正有归因价值的基线**：在同样跨域隔离条件下，不用密码学凭证能否达到同等保证？ |
| **C 跨信任域密码学凭证** | 独立授权方签发一次性凭证 + 执行方**本地验证签名与请求绑定** + 一次性消费 | 授权服务与执行服务**不共享应用信任域、不互信内部数据库**；执行方仅凭凭证独立验证授权来源与内容 | 在同样跨域条件下，本地可验的密码学凭证相对 B2 增加了什么？ |
| **扩展** | MCPS 逐消息签名（含 `tools/call` name/arguments） | Agent 签名消息完整性 | 区分「调用消息没被改」与「调用确实被授权」；Agent 可合法签恶意调用 |

**★归因规则（必须遵守）**：B1 与 C 部署假设不同（共享域 vs 跨域），二者的差异**不能**归因于密码学凭证，只能展示「不同部署假设下的能力上限」。**只有 B2 vs C 才是严格对照**：两者处于相同的跨域隔离条件，系统差异收敛为「靠可信在线通道 / 共同托管方验证」还是「靠本地验证签名凭证」。任何声称「密码学凭证带来增量」的结论都必须来自 B2 vs C，且须证实 B2 的非密码学机制被完整实现（不能故意弱化 B2 制造差异）。

**★B2 定义困难本身是研究结论**：若找不到合理、可复现的 B2（例如任何跨域非密码学方案都要引入一个双方共同信任的在线服务，等价于把信任集中到该服务），这**本身是研究发现**——须先澄清密码学凭证究竟解决哪一种保证：①授权来源验证（谁批准的）；②请求完整性（批准内容是否被改）；③授权服务不可用 / 不可达时的**独立离线验证**能力。若最终 B2 与 C 只是「信任锚位置不同」而非「能力不同」，应诚实接受 NO-GO，而不是把信任锚迁移包装成密码学创新。

**★C 组一次性消费的状态主体与信任假设**（签名本身不能阻止同一有效凭证被重复提交，Ed25519 只保证来源与内容，不保证「没用过」）：
- C 组的消费状态**必须由执行方维护**，并与执行动作**原子关联**（同一事务内标记凭证已消费 + 提交副作用）；否则防重放仍依赖外部共享状态，密码学凭证不产生独立防重放能力。
- 该状态只在执行方信任域内可信，因此 C 的防重放声明**限定为「同一执行方处的原子消费」**，不得写成全局 exactly-once；跨多个独立执行方时同一凭证仍可能各消费一次，这是 C 与 B1/B2 共有的局限（与 E2.3「Sink 幂等≠全局保证」一致）。
- 实验中须显式标注：谁维护消费状态、谁信任该状态、是否与副作用同事务提交。

**测量指标**：未授权参数执行率、审批凭证重放成功率、并发重复消费成功率、授权与执行记录的可验证性、误拒率、合法任务完成率。**重放/并发消费指标若 B1/B2 已达标，不得计为 C 的优势；增量只能来自 B2 vs C 的差异。**

**★停止门槛（可归因版）**：只有当 **B2 被完整实现且 C 相对 B2 有可测量独立增量**（在相同跨域条件下，授权来源验证 / 请求完整性 / 授权服务不可用时独立验证 / 误拒率上 C 显著优于 B2，且差异可归因于密码学凭证），才进入下一步。若 **B2 无法合理定义**（须先明确密码学凭证解决哪类保证并记为研究发现）、或 **C 相对 B2 无可测增量**、或 **B1 在真实部署中已足够**，则 **不为保留密码学框架而继续**，诚实 NO-GO，把 E1/E2 定位为「本地/受控执行链的可信化」而非「通用 Agent 安全方案」。E1/E2 的既有投入不构成继续做 E3 的理由。

### 4.2 前置假设与门槛（H1–H4）

进入 E3 集成前必须验证；任一失败则调整或 NO-GO：

- **H1 动作授权可信传递可行性** `[ASSUMPTION 核心]`（★E3-0.1 重写）：**不**研究「自动把用户自然语言意图转成结构化授权对象」（那引入自然语言理解这一独立难题，且易变成「让另一个 LLM 判断用户想做什么」）。改为：由**可信授权界面展示完整、规范化的具体动作**（Server + tool name + 规范化参数 + 有效期），用户确认该动作，**独立授权服务签发一次性凭证**，执行方跨信任域验证并原子消费。要验证的是**动作授权的可信传递**与授权方/执行方分离，不是 NLU。→ 决定 GAP-1 能否落地。
- **H2 在途篡改真实性** `[ASSUMPTION]`：C2 不是线路中间人（TLS 已保护传输）；须明确攻击者位于 TLS 终止后的哪个信任边界（被攻陷 Host middleware / 不可信工具路由 / 本地执行链），并说明为何 TLS、Host HITL（SHOULD）、MCP Server 输入校验都不能解决。若只能人为构造，须标注为实验假设，价值降为机制验证。
- **H3 差异可归因 + C 相对 B2 增量** `[ASSUMPTION 核心]`（★E3-0.3 重写以保证可归因）：B2（跨信任域非密码学基线）必须被完整实现，且在**与 C 相同的跨域隔离条件**下比较；能否证明增量来自「本地验证独立授权凭证」而非①普通审批已能拦下、②B1/B2 与 C 的部署结构差异、③注入偶然失败？重放/并发消费若 B1/B2 已达标则不得计为 C 的优势（防重放靠原子消费状态，不靠签名）。**只有 B2 vs C 的差异才能归因于密码学凭证**；B1 vs C 仅展示不同部署假设下的能力上限。若 B2 无法合理定义，或 C 相对 B2 无可测增量，则差异不可归因，诚实 NO-GO。
- **H4 与现有机制共存** `[FACT]`：Gateway 能否与 OAuth audience / HITL consent / MCPS 签名共存而不破坏语义（MCP 插入 Gateway 会改 audience，需重新设计信任锚）？

## 6. 最终建议

`[INFER]` **有条件 GO，但暂不进入实际集成**：先做「H1 动作授权可信传递的可行性验证 + A/B1/B2/C 强对照实验设计」，不做接入工程。若 H1 通过、B2 被完整实现、且 **C 相对 B2 有可测增量且差异能干净归因于密码学凭证**，再决定是否进入 E3 实际集成；若 H1 失败、B2 无法合理定义或 C 相对 B2 无增量，诚实 NO-GO，把 E1/E2 框架定位为「本地/受控执行链的可信化」而非「通用 Agent 安全方案」，避免把数月投入到一个最后只能证明「成功接入了某 Agent」或「密码学机制无必要」的项目。

本阶段结论均为 `[INFER]` / `[ASSUMPTION]` 级别的决策建议；`[FACT]` 级技术事实（MCP 规范无 token↔tool+参数绑定、参数审批与消息签名已有相关工作、MCPS 自我定位为 provenance 而非 authorization）来自一手来源，已逐字二次核实。
