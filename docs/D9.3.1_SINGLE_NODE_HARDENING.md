# D9.3.1 — Single-node Online Coordinator hardening

**Status:** Targeted remediation package; not an Online v1 freeze record
**Base source commit:** `cfa1dd5c7cf9b4152345f3779890fe80743c2454`
**Review record:** `docs/D9.3_ONLINE_V1_SECURITY_BOUNDARY_REVIEW.md`
**Scope:** F-01 through F-04 from the D9.3 source review

## 1. Purpose

D9.3.1 closes four bounded implementation gaps identified in the source review. It does not change Online v1 quota semantics, the database linearization point, the signed Grant formats, or the frozen Offline repository.

## 2. Remediations

### F-01 — Gateway disable state and transaction ordering

- Coordinator startup enrollment inserts a newly configured Gateway, but does not change `enabled=0` for an existing Gateway with the same key.
- An existing Gateway ID configured with a different public key remains a configuration error; automatic key rotation is not introduced.
- Registration, revocation, consumption, Lease lookup and operation lookup re-check the Gateway's enabled state while holding a SQLite transaction.
- Consumption, registration and revocation use `BEGIN IMMEDIATE`; the Gateway disable operation also uses `BEGIN IMMEDIATE`. Their commit order now defines the result. If a consume has acquired the write transaction and passed the enabled check first, that consume commits before disable. If disable commits first, a subsequent mutation is denied.
- The HTTP authentication lookup still verifies the Gateway signature before dispatch. The in-transaction check closes the time-of-check/time-of-use gap between signature verification and the protected Coordinator operation.

Gateway disabling remains a trusted local administrative operation. There is no remote Gateway enrollment, rotation or re-enable API in this stage. Disabling is persistent for this Coordinator database and epoch.

### F-02 — Startup integrity checks

Before the Coordinator constructor returns and the HTTP service can start, it runs:

1. `PRAGMA integrity_check`;
2. `PRAGMA foreign_key_check`;
3. the existing accounting invariant checker, including usage totals, operation/receipt counts, sequence continuity, per-Lease caps and Coordinator receipt signatures.

Any failed check raises `CoordinatorIndeterminate` and prevents service startup. The implementation does not attempt automatic repair or counter reconstruction. A logical ledger mismatch is marked `INDETERMINATE` by the existing invariant checker. A physical database failure also prevents startup.

The full SQLite integrity check is performed at process startup. This is appropriate for the single-node reference implementation; larger deployments may need a separately designed maintenance/verification policy.

### F-03 — Receipt lookup identity pinning

`OnlineBudgetClient` now requires both `coordinator_id` and `global_budget_id`. `lookup_operation()` verifies these values, the local Gateway ID and requested operation ID against the signed Budget Receipt. `OnlineBudgetExecutionAdapter` rejects a Client configured for a different Coordinator or budget epoch.

All in-repository Client call sites and subprocess worker configurations are updated to supply the expected budget epoch explicitly.

### F-04 — Strict built-in HTTP bind address

The built-in HTTP server accepts only an explicit loopback IP literal. Hostnames such as `localhost` are rejected rather than checked as strings and later resolved independently by the socket bind operation. Remote Gateway deployments still require a separately configured TLS reverse proxy forwarding to loopback.

## 3. Added regression tests

Six additional tests are added to the D9.2 adversarial test module:

1. disabled Gateway state persists across Coordinator restart and blocks registration, revocation, consumption and HTTP authentication;
2. an admitted consume and a concurrent Gateway disable serialize in the same SQLite write-lock order;
3. Coordinator startup fails closed when the ledger counters disagree with committed operation/receipt rows;
4. operation receipt lookup rejects a wrong Coordinator ID or budget epoch;
5. Adapter construction rejects a Client pinned to another budget epoch;
6. `localhost` binding and chunked `Transfer-Encoding` requests are rejected.

The expected complete suite count after applying this package is **31 tests**: 15 D9.1 tests, 10 D9.2 tests and 6 D9.3.1 tests.

## 5. Remaining trust boundaries

This stage does not add an authenticated administrative API, Gateway key rotation, KMS/HSM storage, TLS termination, rate limiting, audit export, rollback-resistant external anchoring, Coordinator replication or consensus. Database snapshot rollback by a trusted-host administrator remains outside the threat model.

The Coordinator still validates a Gateway-supplied request digest; it does not independently reconstruct the real tool call and prove that the executed tool arguments match a tool schema. That assurance depends on the trusted Gateway Adapter and its tool execution binding. These limits must remain explicit in any research claim.
