# D9.3 — Online v1 Security Boundary Review

**Status:** Source review completed; remediation required before treating Online v1 as a hardened reference baseline
**Reviewed repository:** `kaikai-cao/online-agent-budget-lab`
**Reviewed commit:** `cfa1dd5c7cf9b4152345f3779890fe80743c2454`
**Scope:** Gateway identity lifecycle, Coordinator startup integrity, receipt lookup binding, HTTP bind boundary, and explicit protocol trust assumptions

## 1. Executive summary

D9.1 and D9.2 provide useful implementation evidence for a single-node Online Coordinator. The user-run Windows suite reports 25/25 tests passing, including concurrent final-unit admission, cross-process idempotency, post-commit response loss, one controlled pre-commit process termination point, Consume/Revoke ordering, expiry, receipt tampering, and HTTP request framing checks.

This review did not identify a demonstrated path that bypasses the normal `BEGIN IMMEDIATE` global-budget admission transaction under the tested single-Coordinator model. However, source inspection found two material hardening gaps and one recovery-verification gap:

1. Gateway disable state is not restart-persistent, and disable is not serialized with authenticated state-changing operations.
2. Startup does not automatically run the Coordinator's logical ledger/receipt invariant checker before serving requests.
3. `OnlineBudgetClient.lookup_operation()` verifies the receipt signature, Gateway ID, and operation ID, but does not pin the configured Coordinator ID or the expected budget epoch.

There is also a lower-priority loopback-hostname validation weakness. These findings do not invalidate the 25 passing regression tests; the tests currently do not cover these cases.

## 2. Findings

### F-01 — Gateway disable is neither restart-persistent nor atomic with admission

**Severity:** High if `disable_gateway()` is intended as an emergency identity-revocation control; otherwise this capability must be treated as unsupported and not relied upon.

**Evidence:**

- `OnlineBudgetCoordinator.__init__()` calls `enroll_gateway()` for every Gateway in the startup configuration.
- `enroll_gateway()` uses `INSERT ... ON CONFLICT(gateway_id) DO UPDATE SET enabled=1`.
- `disable_gateway()` persists `enabled=0`, but the next Coordinator construction with the same static Gateway configuration changes that row back to `enabled=1`.
- `register_lease()`, `revoke_lease()` and `consume()` check Gateway enablement through `_assert_gateway_allowed()` before opening their main write transaction. The HTTP envelope verifier also reads the Gateway key before dispatch. A concurrent `disable_gateway()` can therefore commit after the preflight check and before the state-changing transaction commits; the transaction does not re-check `enabled` while holding its write lock.
- There is no authenticated administrative HTTP endpoint for disable/enable or Gateway key rotation. The method is currently an in-process API, not a complete operator lifecycle.

**Impact:** A caller must not assume that `enabled=0` is a durable, linearizable revocation. After restart the identity can become active again. During a race, a request that passed the preflight check can still register/revoke/consume after a disable operation has committed.

**Required remediation:**

1. Make startup enrollment insert-only for unknown Gateway IDs; do not set an existing disabled row back to enabled implicitly.
2. Provide an explicit operator-controlled enable/re-enrol operation, separate from process startup, with documented authorization and audit requirements.
3. Re-check Gateway `enabled` inside the same `BEGIN IMMEDIATE` transaction that performs register, revoke, consume, and any sensitive lookup. The database commit order then defines whether the request or disable wins.
4. Add tests for disable → restart → request rejection, and for a deterministic disable/consume race.

Until this is implemented, document Gateway disable as non-productionized and do not claim runtime Gateway revocation support.

### F-02 — Coordinator startup does not validate logical ledger invariants

**Severity:** High for automatic fail-closed recovery from logical ledger damage; medium within the explicitly trusted-database prototype boundary.

**Evidence:**

- The constructor runs `_init_schema()`, `_initialize_meta()`, and Gateway enrollment, then returns.
- It does not call `assert_invariants()` before the HTTP service begins accepting requests.
- `assert_invariants()` checks that Lease usage sums to the global counter, committed operation and receipt counts match global usage, sequences are contiguous, Lease caps hold, and stored receipts match their signatures and operation fields. On mismatch it marks `budget_meta.health='INDETERMINATE'` and raises `CoordinatorIndeterminate`.
- The existing tests call `assert_invariants()` explicitly after operations, but `run_coordinator.py` does not perform this check as part of startup.

**Impact:** A database that remains structurally readable but contains inconsistent logical counters/rows can be opened and served without the available invariant check having run. This weakens the intended fail-closed recovery behavior after accidental logical corruption or an unsafe restore.

**Required remediation:**

1. Run SQLite structural checks (`PRAGMA quick_check` or an appropriately selected integrity check) during startup.
2. Run the logical ledger/receipt invariant check before the server starts listening. Any mismatch must leave the Coordinator unavailable/INDETERMINATE.
3. Add startup tests that alter a usage counter, receipt row, or sequence metadata while leaving the SQLite file readable; construction/startup must fail closed.

A full historical ledger scan is O(number of operations). That cost should be measured and documented before the prototype is scaled. A future checkpointed verification design may be appropriate, but must not silently omit the invariant check.

### F-03 — Operation lookup does not pin Coordinator identity or budget epoch

**Severity:** Medium; primarily affects recovery and callers that use the lookup result as authorization evidence.

**Evidence:**

- `OnlineBudgetClient` stores `coordinator_id`, but `lookup_operation()` calls `verify_budget_receipt()` with only `expected={"gateway_id": ..., "operation_id": ...}`.
- The receipt contains both `coordinator_id` and `global_budget_id`, but neither is compared with the Client's configured Coordinator identity / expected budget epoch on this path.
- `consume()` does check the full expected binding, including Coordinator ID and budget epoch. The lookup path is weaker.

**Impact:** If a signing key is reused across Coordinator identities or budget epochs, a validly signed receipt for the wrong epoch may be accepted by `lookup_operation()`. Key reuse across epochs is not prohibited by the current type/API. The current adapter does not use this lookup method for its local cache replay, but the public lookup API is an obvious recovery surface.

**Required remediation:**

1. Always require `coordinator_id == self.coordinator_id` on lookup.
2. Pin the expected `global_budget_id` as Client configuration or an explicit required lookup argument.
3. Add a test that returns a correctly signed receipt from the same test signing key but with a different Coordinator ID or budget ID; lookup must reject it.

### F-04 — `localhost` is accepted by name without verifying its resolved bind addresses

**Severity:** Low; configuration hardening.

**Evidence:**

`CoordinatorHTTPServer.__init__()` accepts either a literal IP for which `ipaddress.ip_address(host).is_loopback` is true, or any hostname string exactly equal to `localhost`. The socket server later resolves that name through the operating system. The implementation does not verify that the resolved address is loopback.

**Impact:** The loopback-only guarantee relies on the local hostname resolution configuration when `localhost` is used. The default `127.0.0.1` is not affected.

**Recommended remediation:** Accept literal loopback IP addresses only, or resolve the hostname and require every candidate bind address to be loopback. Add a test for the hostname path. Keep the default numeric loopback bind.

## 3. Protocol trust assumptions — not implementation defects under the declared model

### T-01 — Tool request semantics are trusted at the Gateway adapter

The Coordinator receives `request_digest` as an opaque SHA-256 digest. It validates the digest shape, authenticates the Gateway envelope, and binds the digest into the operation tuple and signed Budget Receipt. It does not receive or independently validate the selected `tool_name`, selected `schema_hash`, canonical tool arguments, or their relationship to that digest.

The Online Lease Grant and Execution Grant bind an allowed-tools list, but the Coordinator currently binds the complete Execution Grant digest rather than proving which member of that list was used for a specific invocation. `OnlineBudgetExecutionAdapter.consume_for_grant()` accepts the digest from its caller; it does not derive the digest from a typed tool-call object itself.

This is consistent only with the declared trust assumption that the Gateway and Tool Adapter are trusted to validate the actual tool call and compute the correct digest. It is **not** a cryptographic proof to an external verifier that a particular tool name/schema/argument tuple was executed. Any paper or report must state this boundary precisely.

A future protocol extension could carry a canonical `ToolCallBinding` containing tool name, schema hash, and canonical-arguments digest, then bind that structure into the Gateway-signed request and Coordinator receipt. That should be versioned as a protocol change, not slipped into the current v1 implementation.

### T-02 — A consistent historical database rollback is not detectable from the database alone

The current invariant checker can detect many internally inconsistent states, but a restore to an older, fully consistent database snapshot may still satisfy every in-database invariant. Detecting that form of rollback requires an external monotonic anchor, remote witness, append-only external log, or equivalent anti-rollback mechanism.

D9.0 explicitly excludes malicious database administrators, whole-database rollback, and hardware anti-rollback. This remains a real limitation, not a test failure. Do not claim anti-rollback protection for the Online v1 Coordinator.

### T-03 — Key lifecycle and deployment hardening remain incomplete

Gateway enrollment is static at startup; there is no authenticated administrative API for key rotation, disable/enable, audit export, or rate limiting. The built-in HTTP listener is loopback-only and plaintext; remote Gateways require a correctly configured TLS reverse proxy. Coordinator and Gateway private keys are software-held in this prototype.

These are documented prototype limitations. They must remain explicit until a separately scoped management-plane and deployment-hardening stage is completed.

## 4. D9.2 test coverage gaps identified by this review

The implementation rejects any `Transfer-Encoding` header and restricts binding, but the current HTTP adversarial test explicitly exercises duplicate `Content-Length`, oversized bodies, wrong content type, unauthenticated access, and `0.0.0.0`; it does not explicitly exercise:

- `Transfer-Encoding: chunked` alone;
- simultaneous `Transfer-Encoding` and `Content-Length`;
- the accepted `localhost` hostname path.

Add those as regression cases when addressing F-04 / HTTP-boundary work. D9.2's 25/25 result remains accurate for the tests that were run; it should not be described as coverage of these omitted cases.

## 5. Recommended bounded remediation stage

The next implementation package should remain a single-node hardening pass and contain only:

1. Gateway enrollment/disable lifecycle fix and transaction-atomic enabled checks (F-01).
2. Startup structural + logical integrity verification, fail closed on mismatch (F-02).
3. Coordinator ID and budget-epoch binding on receipt lookup (F-03).
4. Literal-loopback or resolved-address validation plus explicit Transfer-Encoding tests (F-04 and D9.2 HTTP test gaps).
5. Regression tests for each of the above.

Do not add Coordinator replicas, Raft, TLS implementation, admin HTTP endpoints, KMS/HSM, external rollback anchors, or ToolCallBinding protocol changes in this remediation stage. Those require separate decisions and versioned boundaries.

## 6. Review conclusion

The D9.1/D9.2 implementation is a credible single-node reference model for transactional global budget accounting under the tested concurrency, retry, and selected crash scenarios. It is not yet a hardened production Coordinator.

F-01 and F-02 should be fixed before making stronger claims about Gateway revocation or fail-closed database recovery. F-03 should be fixed before relying on the operation-lookup API for recovery decisions. F-04 is a small bind-boundary hardening item. T-01 and T-02 are trust-model limitations and should remain explicit rather than being presented as solved by the current test suite.

This source review is not a formal verification, penetration test, or proof against a malicious Coordinator, Gateway host, operating-system administrator, or database administrator.
