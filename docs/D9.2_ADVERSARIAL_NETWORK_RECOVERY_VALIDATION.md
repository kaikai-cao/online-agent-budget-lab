# D9.2 — Adversarial Network and Recovery Validation

**Status:** Validation stage; not an Online freeze record
**Baseline:** `c8f0a659501cd64fadd19e9109b433db80309086` (D9.1)
**Scope:** Single-node Coordinator fault injection, crash recovery, admission races, configuration drift and HTTP boundary hardening

## 1. Objective

D9.2 validates the D9.1 Online Coordinator at failure boundaries that ordinary successful requests do not exercise. It does not introduce replicas, consensus, multi-region writes, offline spending, or a new quota policy.

The database commit remains the linearization point. A request whose response is lost is an unknown outcome; the Gateway must retry the same `operation_id` with the exact same authorization and request binding. A process terminated before commit must leave no partial accounting state after SQLite recovery.

## 2. Changes in this stage

### 2.1 HTTP request boundary

The built-in HTTP server is now explicitly loopback-only. It rejects non-loopback bind addresses. A remote deployment must terminate TLS at a reverse proxy and forward to the Coordinator over loopback; this repository does not implement TLS termination.

POST endpoints require exactly one `Content-Length`, reject `Transfer-Encoding`, enforce the 1 MiB request-body limit, and require `Content-Type: application/json`. Early framing/size/media-type rejections close the connection so unread request bytes cannot be interpreted as a subsequent HTTP/1.1 request. Oversized requests return HTTP 413; unsupported media types return HTTP 415.

The unauthenticated `/health` response intentionally exposes only `ok`, Coordinator ID, budget epoch ID and health state. It does not expose usage counts, public-key material or database paths.

### 2.2 Adversarial validation cases

The new test module adds evidence for:

1. Per-Lease cap enforcement without an extra global charge.
2. Two independent OS processes issuing the same operation ID and exact binding; both obtain the same stored receipt while only one unit is charged.
3. Response loss after Coordinator commit; exact retry returns the stored receipt and does not allocate a second sequence.
4. Delayed first response arriving after a later operation's response; receipt sequence reflects commit order, not response arrival order.
5. Coordinator process termination after uncommitted accounting writes and before receipt insertion/commit; restart recovers the pre-operation state, then exact retry commits once.
6. Consume/Revoke race; either Consume commits first and remains exactly replayable, or Revoke commits first and the new Consume is denied.
7. Expiry crossing while Consume is paused at the in-transaction time check; a request at `now == expires_at` is denied.
8. Coordinator quota, Issuer key, Coordinator signing key and enrolled Gateway key drift; configuration mismatch is rejected.
9. A wire-tampered Coordinator receipt is rejected by the Gateway client; caller-side dispatch does not proceed without a verified receipt.
10. HTTP body framing, maximum size, content type, request authentication, health-data minimization and loopback-only bind policy.

## 3. Fault-injection boundaries

The dropped-response and reordered-response harness intercepts responses only after the Coordinator dispatch has returned. Thus the simulated response loss/delay occurs after the transaction's commit path, not before it.

The process-kill worker pauses in SQLite's SQL trace callback immediately before `INSERT INTO receipts`, after the Lease usage, global counter and operation-row writes have executed inside the still-open transaction. The parent terminates that process, reopens the same SQLite database using a new Coordinator instance, asserts all accounting and sequence state returned to the pre-operation state, then retries the exact operation.

The crash test is intentionally narrow: it validates one controlled pre-commit interruption boundary. It does not exhaustively test every CPU instruction or filesystem failure point.

## 4. Commands and acceptance

Run from the repository root in the existing virtual environment. First apply the idempotent test-only cleanup patch for the D9.1 `HTTPError` test fixture, then run the complete suite with strict ResourceWarning handling:

```powershell
python scripts/fix_d91_test_http_error_cleanup.py
$env:PYTHONWARNINGS = "error::ResourceWarning"
try {
    .\run-tests.ps1
    if ($LASTEXITCODE -ne 0) { throw "D9.2 test suite failed" }
}
finally {
    Remove-Item Env:PYTHONWARNINGS -ErrorAction SilentlyContinue
}
```

Acceptance criteria:

- The original D9.1 tests remain green.
- The new adversarial tests are discovered by the existing test runner.
- The process-kill test proves zero partial operations/receipts/usage after restart, then exactly one committed result after retry.
- Lost-response retry and cross-process duplicate tests preserve one operation, one receipt and one global unit.
- Revoke/expiry outcomes match the transaction ordering and Coordinator time rules.
- No malformed or unauthenticated HTTP request changes budget state.
- `git diff --check` reports no whitespace errors.

Test results are implementation regression evidence only. They are not a formal proof, a production certification, a multi-host availability claim, or evidence against a malicious Coordinator/host administrator.

## 5. Remaining limitations

- One Coordinator process and one authoritative SQLite database remain the deployment model.
- Built-in HTTP is loopback-only and is not encrypted. Remote Gateways require a correctly configured TLS reverse proxy and secure key enrollment.
- The server still relies on the operating system, SQLite and filesystem durability assumptions.
- Slow-client/header-level denial-of-service defenses, rate limiting, key rotation workflows and audit export remain outside this stage.
- No arbitrary external tool can be guaranteed exactly once without provider-side idempotency or authoritative result lookup.
